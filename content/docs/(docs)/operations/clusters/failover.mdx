When a server of a [cluster](/operations/clusters) stops answering, its apps start on another
server of the cluster. Nobody clicks anything.

- **Failover starts at two servers.** On a cluster of one, nothing moves.
- **It is on by default.** An admin can [turn it off](/operations/clusters#turn-failover-off) per
  cluster: then everything waits for its own server to come back.
- **With two servers, failover works only while Deplo is up.**
- **With three or more, it also works while Deplo is down**, as long as more than half of the
  cluster's servers are up and the [leader](/operations/clusters/leader) runs on one of them. A
  moved app is served at its generated address only once Deplo is back. See
  [If Deplo was down](#if-deplo-was-down).
- **It survives losing Deplo or the leader's server, not both at once.** With both down, nothing
  moves until one of them is back.

See [When a cluster is cut in two](#when-a-cluster-is-cut-in-two) for what that means.

## When a server stops [#when-a-server-stops]

| After | What happens |
| --- | --- |
| About 5 seconds of silence | The cluster's leader starts moving that server's apps without stored data |
| About 10 seconds | The server reads **Offline** on the Servers page. Its apps read **Moving to server-b** from the moment the leader decides to move them, or say why they cannot move yet |
| About 31 seconds | The silent server has stopped, by itself, everything that must never run twice: its databases, its apps with stored data and its running cron jobs. The leader starts moving those, each app with data on its own, so a slow one holds none of the others. 41 seconds for a server whose agent is older than 0.5.3-canary.43 |

**Nothing that keeps data moves earlier than that**, on purpose. A server that is only cut off from
the network is still running. The leader waits until that server has stopped its own databases
before it starts them somewhere else. That is the first promise, **"Never two writers"**. Apps
without stored data do not wait: two copies of those harm nothing, and the server removes its own
when it is back.

**Nothing moves at all** when the trouble looks like the cluster's own, not the server's:

- the leader lost its own connection
- too few servers answer the leader: half of them or fewer, unless it is exactly half and Deplo
  answers too. See [When a cluster is cut in two](#when-a-cluster-is-cut-in-two)

<Callout type="info">
  31 seconds is when moving **starts** for anything with data, not when visitors are served again.
  That also takes the app's own start and a restore. See [How long it takes](#how-long-it-takes).
</Callout>

### What the app reads meanwhile [#what-the-app-reads-meanwhile]

| The app's status | When |
| --- | --- |
| **Moving to server-b · 34 s** | From the moment the leader decides to move it until server-b answers for every one of its domains with a valid certificate, then **Running** |
| **Offline: no up-to-date copy** | Its server is off and no other server holds an up-to-date copy of its data yet, so it waits for its server |
| **Offline: waiting for a majority of servers** | Too few servers of the cluster answer each other to move anything safely |

**A server takes a moved app only once it holds a valid certificate for every one of its domains**,
and an up-to-date copy of its data when it keeps data. So the first answer from the new server
already has the right certificate.

### How long it takes [#how-long-it-takes]

Measured on test clusters, counting from the moment a server lost its power. The app and database
rows are 3 runs on three servers, with the server agent at 0.5.3-canary.13 and the leader at
0.1.0-canary.6:

| What ran on the stopped server | Measured |
| --- | --- |
| Replicas of an app on a Cloudflare domain, spread over both servers | **No downtime.** Cloudflare stopped sending visitors to the stopped server within about 5 seconds: one request in that time failed |
| An app without stored data, on that server only | Running on the other server after **about 10 seconds** |
| An app with a Volume, with [replication](/operations/clusters/replication) on | Visitors served again after **about 38 seconds**, putting its copy in place included; **about 50 seconds** when the server lost also ran the cluster's leader, which the next server in line takes over first (Deplo 0.8.2-canary.98, server agent 0.5.3-canary.58, leader 0.1.0-canary.23). Each server keeps going 20 seconds without its leader, so losing the leader's server stops nothing elsewhere. A Compose app with 3.3 GB of images and a database: about 47 seconds, every image already there (canary.97). With Deplo down, only once Deplo is back: see [If Deplo was down](#if-deplo-was-down) |
| A database with a standby copy | The standby took over: writes taken again after **25 to 26 seconds** |
| A database with a 4 MB backup | Its restore took 17 to 24 seconds, on top of the wait |
| The server comes back | About 20 seconds after it answers, its old copies stop, and what its database still held is saved as a backup |

A bigger database takes longer to restore. Its card says how long, from the speed of its last
restore. See [Databases](/operations/clusters/databases).

A bigger app does not: its copy is moved into place, never copied again, and its images are already
on the other server. An app with 2 GB in its Volume was served again 32 seconds after its server
lost power (server agent 0.5.3-canary.46, with the 5 second lease of then).

## What moves, and what waits

Order: **databases first, then apps with a domain, then the rest**, oldest first.

| What ran on the server | What happens |
| --- | --- |
| An app with no stored data | Starts on another server, exactly as its last deploy left it: same version, variables, files, ready check and automatic restart |
| Replicas of an app | Start on the other servers. See [Replicas across servers](/operations/clusters/replicas-and-architectures#replicas-across-servers) |
| A database | Restored on another server from its latest backup, or its standby copy takes over. See [Databases](/operations/clusters/databases) |
| An app with a Volume or Files | With [replication](/operations/clusters/replication) on, starts on another server with the copy of its data kept there. Otherwise it **waits for its server**. See [Apps with stored data](/operations/clusters/apps-with-stored-data) |
| An app with a Bind | Never moves: the folder lives on that one machine |
| A pull request preview | Never moves. See [Pull request previews](/operations/clusters/logs-metrics-and-previews#pull-request-previews) |
| A cron job that was running | Marked **Lost: its server stopped**, and never run again on its own. See [Cron jobs](/operations/clusters/logs-metrics-and-previews#cron-jobs) |

An app keeps answering under its domain only if the domain follows it. See
[Addresses and Cloudflare](/operations/clusters/addresses).

### What cannot move yet

Activity says why, once a day, until it is fixed:

- **An app that was never deployed since it joined the cluster.** The leader has nothing to start
  it from: `web cannot fail over yet: Deplo has no saved copy of its last deploy to give the
  cluster's leader. It is sent with the next deploy. Cluster eu will not move it to another server
  until that is fixed.` Deploy it once.
- **A server whose server agent is too old never takes work over**: `The server agent on server-b
  is too old to take over Apps when another server in cluster eu stops. Deplo updates it on its
  own.` Nothing to do: wait.
- **A Compose app that builds its own images**: `web does not fail over yet: its compose file
  builds images, and they exist only on the server that built them. A compose file that names
  published images does.`

**A move uses the images the other server already has.** Since server agent 0.5.3-canary.13 and
Deplo 0.8.2-canary.31:

- A start on another server downloads only an image that server does not have yet.
- **Every image a cluster app or database runs is already on every server of the cluster**, a
  Compose app's too (server agent 0.5.3-canary.57 and Deplo 0.8.2-canary.96). Each server holds
  them ahead, at the deploy and whenever they change, one image at a time and only while a tenth of
  its disk stays free, and keeps them. A move then needs no registry at all.
- **A server takes a missing image from another server of the cluster**, over the cluster's private
  network, not from the registry (server agent 0.5.3-canary.58). Only when no server has it does one
  server, the cluster's first, download it from the registry, at 4 MB a second so the apps and the
  name servers sharing the line keep answering; the others then take it from that server. An image
  behind [registry credentials](/operations/servers/container-registries) is copied over the
  private network too.

<Callout type="warn" title="Known limit: a server that is new to the cluster">
  - A server that joined a moment ago, or whose disk has no room for an image, downloads it at the
    move, and a registry that refuses then stops that move.
  - Docker Hub allows a few downloads an hour per address to anyone not signed in: use images from
    a registry Deplo is signed in to.
  - A server that asks for an image while the one holding it sends another may still download it
    from the registry itself.
</Callout>

## Waiting for room [#waiting-for-room]

What finds no server waits, and Deplo tries again **every 30 seconds**.

- The app's header and its **Settings -> General -> Server** card say **Waiting for room in
  eu**. A database says it on its **Failover** card.
- Inside the cluster on the Servers page, the banner **2 Apps waiting for room** lists them, with
  "Deplo tries again every 30 seconds."
- **The fix**: add a server to the cluster, or lower the app's memory.

**One alert per failover that left something waiting**, on by default:
**Apps waiting for room after a failover**. Its title is `web waiting for room in eu`, or
`3 Apps waiting for room in eu`, and it says: "server-a stopped answering. No other server has
room for web yet. Deplo tries again every 30 seconds."

**Room is not the only reason to wait.** Activity and the alert name the real one:

| Activity says | The alert says |
| --- | --- |
| `web is waiting in eu: server-a stopped answering and it did not start on another server` | "web did not start on another server." |
| `web is waiting in eu: server-a stopped answering and no other server has its image yet` | "No other server has the image of web yet." |
| `web is waiting in eu: server-a stopped answering and no other server is online and ready` | "No other server is online and ready for web." |
| `web is waiting in eu: server-a stopped answering and no other server has taken it yet` | "No other server has taken web yet." Read back after Deplo reconnected to the leader |

With any of those the alert's title reads `web waiting to move in eu`, or `2 Apps waiting to move
in eu`.

**A database waits the same way** when its standby copy could not take over and there is no
backup to restore: `pg is waiting in eu: server-a stopped answering and it did not start on another
server`, with the same alert. The leader tries the standby again. Before leader 0.1.0-canary.6 it
waited without a word.

## What Activity says

Every entry is **by Deplo**, in the team that owns the app or database:

| Entry | When |
| --- | --- |
| `Moved web to server-b: server-a stopped answering` | An app moved |
| `Started a replica of web on server-b: server-c stopped answering` | A lost replica was replaced |
| `Restored db on server-b from the backup of 14:15` | A database came back from a backup |
| `Moved web to server-b with its data replicated there: server-a stopped answering` | An app with stored data moved with its replicated copy |
| `web is waiting for room in eu: server-a stopped answering and no other server has room yet` | Nothing had room. See [Waiting for room](#waiting-for-room) for the other reasons |
| `web moved to another server of its cluster, so its generated address is now web-calm-fox-cb007118.deplo.site` | Its `deplo.site` address changed |
| `Did not move web to server-c: the cluster's leader placed it on server-b since` | A move the leader replaced before Deplo applied it. The app stays where it runs |

## If Deplo was down [#if-deplo-was-down]

Deplo catches up when it is back: the same Activity entries, the new address and the alert.

- **Each entry carries the time it happened**, not the time Deplo read it. A server that stopped at
  05:45 and came back at 05:54 reads `server-c is not responding in cluster eu.` at 05:45 and
  `server-c answers again in cluster eu.` at 05:54, even when Deplo only came back at 05:55.
- **Nothing that happened meanwhile is skipped.** While its own machine stood in for the leader,
  Deplo remembers the last event it read from that leader. When it hands the cluster back, it
  reads on from there: every server that stopped or came back, every move, every copy set aside.

- **Until then, a moved app runs but is not reached at its generated address.** Only Deplo makes
  the new one: the old address names the server the app left.
- **So it is served again only after Deplo is back**, however early it started on its new server.
  The longer Deplo is down, the longer that takes.
- **A domain on Cloudflare keeps answering** the whole time. See
  [Addresses and Cloudflare](/operations/clusters/addresses#a-generated-address).

| What moved | Running on its new server | Served at its new address, Deplo up | Served at its new address, Deplo down |
| --- | --- | --- | --- |
| An app without stored data | After 9 to 11 seconds | After 10 to 12 seconds | 25 to 28 seconds after Deplo was back |
| An app with a Volume, with replication on | After 35 to 36 seconds | After 33 to 35 seconds | 33 to 37 seconds after Deplo was back: **289 to 292 seconds** after the power loss |

Measured 3 times each way on a cluster of three servers. One of them lost its power, the leader ran
on another, and Deplo on a machine of its own. "Deplo down" means Deplo stopped just before the
power loss and started again 254 to 256 seconds after it. **A database with a standby copy took
writes again after 25 to 26 seconds either way**: it does not wait for Deplo.

### While Deplo cannot reach the cluster [#while-deplo-cannot-reach-the-cluster]

When **no server of the cluster answers Deplo**, Deplo does not know what they decide. It says so
and shows the last state it knew, with its time:

| Where | What it reads |
| --- | --- |
| The cluster, on top | **Deplo cannot reach this cluster since 05:32 UTC: its servers decide on their own**, then "What this page shows is how the cluster stood at 05:32 UTC." |
| An app's status | `Offline: Deplo cannot reach its cluster since 05:32 UTC` |
| An app's **Failover** card | "Deplo cannot reach this cluster since 05:32 UTC: its servers decide on their own. This is how web stood then." The copies read as they stood at 05:32 |
| Activity | Once: `Deplo cannot reach cluster eu since 05:32 UTC: its servers decide on their own. What Deplo shows of it is how it stood then.` Back: `Deplo reaches cluster eu again`, then what happened meanwhile |
| A backup, or anything else Deplo asks a server of the cluster | `Deplo cannot reach cluster eu since 05:32 UTC, so it could not take this backup: its servers keep running without Deplo`, never "This server is offline" |

- **Meanwhile Deplo writes no guess.** No server reads "not responding", no app reads "Not copied
  yet" and nothing reads "cannot fail over yet" because of the silence alone.
- **The servers go on without Deplo.** The leader keeps renewing them and moves what a stopped
  server ran, as long as more than half of them answer it. See
  [When a cluster is cut in two](#when-a-cluster-is-cut-in-two).
- **The time is when Deplo last heard any of them.** A server that is really off and one Deplo
  cannot reach look the same from Deplo.
- **Deplo coming back changes nothing that runs.** No app is paused, restarted or moved because
  Deplo reaches the cluster again.

## The slower case [#the-slower-case]

The times above are for a leader that was already leading. When **the leader ran on the server
that stopped**, the server next in line takes over first, about 10 to 13 seconds after it stopped
(see [The line of succession](/operations/clusters/leader#the-line-of-succession)), or Deplo's own
machine in 25 to 40 seconds when no server of the line can. Then the same waits apply.

With the line, measured on a cluster of three with a power cut (Deplo 0.8.2-canary.80): the app
with a Volume and a slow start (fise) was served again after 40 to 55 seconds, a small one with a
Volume after 30 to 40, and an app on a server that stayed up, stopped while nobody led, after 9 to
31 seconds. The measurements below are from Deplo's machine taking over:

| What ran on it | Starts elsewhere after |
| --- | --- |
| Apps without stored data | About 40 seconds: Deplo's machine takes over, then 5 seconds. Measured: served again at its generated address after 45 to 93 seconds |
| Databases, and apps with a Volume | About a minute, then the restore. Measured: a database with a standby copy took writes again after 58 to 67 seconds; an app with a Volume and replication on was served again at its generated address after **68 to 100 seconds**, and took writes after 80 to 110 |

Measured 3 times on a cluster of three servers and Deplo's machine, with Deplo up, server agent
0.5.3-canary.13 and leader 0.1.0-canary.6. The server that lost its power ran the leader, a
database with a standby copy, an app with a Volume and an app without stored data. With leader
0.1.0-canary.4, the app with a Volume was served again after 108 to 165 seconds.

- **The wait after "running elsewhere" is Deplo**, pointing each moved app's generated address at
  its new server. Since Deplo 0.8.2-canary.30 it does that for every app at once, and waits at most a
  second for a server the leader said is not answering.
- **A domain on Cloudflare does not wait for Deplo.** See
  [Addresses and Cloudflare](/operations/clusters/addresses).

<Callout type="info" title="Which leader">
  Deplo 0.8.2-canary.31 and later install the leader 0.1.0-canary.6 on their own. Older versions
  install 0.1.0-canary.3 or 0.1.0-canary.5. With 0.1.0-canary.3, databases and apps with a Volume
  start elsewhere only after **about 7 minutes**: it always waits out the 5 more minutes a planned
  update gives.
</Callout>

**About 7 minutes in two cases.** Just before a planned update, a leader gives every server 5 more
minutes, and tells every server first. The leader that takes over asks the servers that are left
whether that happened. It waits those 5 minutes, instead of risking the same database running on
two servers, when:

- the leader had given those 5 minutes, and its server never came back
- the servers that are left cannot tell yet: they joined the cluster, or got a server agent that
  keeps count, less than about 6 minutes before. Deplo updates the server agent on its own

"Bring it back" from a backup is refused for the same time. A server that has answered the new
leader even once is back on the usual times.

**The 5 minutes end with the update.** Once the updated leader has renewed every server again,
about a second after it is back, it tells them the extra time is over: a server lost after that
moves on the usual times. While a server of the cluster is off, the extra time runs out on its own.

## When a cluster is cut in two [#when-a-cluster-is-cut-in-two]

A network cut can split a cluster. Neither side can tell whether the other is down or only out of
reach, so **only one side may go on**. That is how nothing ever runs twice.

**The rule.** The leader keeps leading only while it is answered by:

- **more than half** of the cluster's servers, or
- **exactly half** of them **and Deplo itself**

Otherwise it moves nothing, and the servers it still reaches stop their databases and their apps
with a Volume within about half a minute. The side that goes on is the one with more than half of the
servers. When the sides are equal, it is the side Deplo is on.

### Servers lost one after another [#servers-lost-one-after-another]

A server gone for **2 minutes** stops counting for the majority, as long as the leader still hears
more than half of the others. Activity says it: `eu-3 has been gone from cluster eu for 2 minutes,
so the others no longer count it for a majority: if another server stops, the last ones keep
serving.`

So with three servers, losing one and then another leaves the last one serving:

1. eu-3 stops. Its apps move, as above.
2. 2 minutes later the cluster counts two servers, eu-1 and eu-2.
3. eu-2 stops. eu-1 is one of two, exactly half, and **Deplo breaks the tie**: the side Deplo
   answers keeps or takes the apps, and its DNS zone keeps answering from eu-1.

Why 2 minutes: a server that is only cut off stops its databases within about half a minute.
Two minutes is well past that, so it has stopped them before the others stop counting it.

- **The leader's own server counts too.** When the server lost first runs the leader, the server
  that takes over goes on from when that leader last heard each server: the 2 minutes run from
  the moment eu-3 stopped, not from the takeover, and the next server in line learns who is gone.
- **Two servers lost at the same moment** still stop the cluster, as below.
- **The cost**: if Deplo is unreachable when the second server stops, there is no tie-break and
  nothing moves until a server is back.
- **A server that comes back** first catches up: it hosts no app and does not count until it has
  answered for 2 minutes. Activity says `eu-3 caught up and counts for a majority of cluster eu
  again.`

### What it means for your cluster

| Cluster | What to expect |
| --- | --- |
| One server | Nothing changes |
| Two servers | **Failover needs Deplo up.** If one server stops while Deplo is down too, or restarting for longer than about 8 seconds (Deplo's word holds 8 seconds since Deplo 0.8.2-canary.80, 20 before), the other server's databases and apps with a Volume stop as well. They start again by themselves within seconds of Deplo being back, and the stopped server's work moves then |
| Three servers or more | Failover works with Deplo down as long as more than half of the servers are up and the leader's server is one of them: one of three may stop, two of five. **Not the leader's server while Deplo is down too**: then nothing moves until one of them is back |
| More than half of the servers lost at once (two of three at the same moment; one after another, see [above](#servers-lost-one-after-another)) | With Deplo up or not, the servers that are left stop their databases and apps with a Volume within about half a minute, until one of the others is back. If they are gone for good, the rest start again once those servers are [removed from the cluster](/operations/clusters/manage-servers#remove-a-server) |

**Apps without a Volume keep running the whole time**, in every row.

**What a server stopped comes back by itself.** Once the others are back and it is part of a majority
again, it starts the databases and apps it stopped, whatever their restart setting. One that moved to
another server meanwhile stays stopped there, and its copy is cleaned up as below.

**On a cluster, a container with no restart setting is kept up**, so it starts again after a crash or
a power cut like the others. One whose compose file says `restart: "no"`, and a step another
container waits to finish, run as their file says.

**For failover that does not depend on Deplo being up, use three servers or more**, with the
[leader on one of them](/operations/clusters/leader#run-the-leader-on-another-server).

### What a split looks like

| Where | What happens |
| --- | --- |
| The smaller side | Its servers stop their databases and apps with a Volume within about half a minute |
| The larger side, its leader already leading | Brings them up from the latest backup, or promotes the standby copy, after about **18 seconds** (25 with a server agent older than 0.5.3-canary.43) |
| The larger side, when Deplo's machine had to take over as leader first | The same about **18 seconds** after Deplo's machine started leading, except in the cases of [The slower case](#the-slower-case) |
| Both sides | Apps without a Volume keep running. The server that was cut off removes its copy when it is back |

When the leader is on the larger side and Deplo on the smaller one, Deplo shows its own side's
servers as offline and cannot see the other side until the split heals.

### What you read meanwhile

- **Inside the cluster**, the banner **Failover is not working right now**: "Only 1 of 3 servers
  answers this leader, so nothing moves. Failover works again once 2 do."
- **Activity, one silent server**: `server-b is not responding in cluster eu.`, then `server-b has
  not responded for a minute in cluster eu, so it stopped the databases and Apps with files that
  must never run twice.`
- **Activity, more than half of the servers silent**: `Too few servers answer in cluster eu, so
  nothing moves and server-b no longer counts as answering.`, then `Too few servers answer in
  cluster eu, so server-b stopped the databases and Apps with files that must never run twice.`
  Said only while the leader really does not lead: one that leads has a majority.
- **Bringing an app back from a backup** is refused meanwhile: "The cluster's leader cannot reach
  its servers right now. Try again in a minute."

## When a server comes back [#when-a-server-comes-back]

A restart, or a network cut that healed. The server:

1. **Starts nothing of the cluster's until it has heard from the leader.** Anything that started
   by itself at boot is stopped again, a few seconds later. See the known limit below.
2. **Stops and removes its own copy** of every app and database that moved away while it was
   gone, the app's Cloudflare connector included.
3. **Starts again what is still its own.** Work that found no room elsewhere goes back to it.

Until it has heard from the leader, a deploy or a start of a cluster app on it fails with: "this
server has not heard from its cluster's leader, so it starts nothing of the cluster's yet".

**One Activity entry and one alert per return**, per team, naming only that team's own apps and
databases:

- `server-a is back in cluster eu. Its copy of web was stopped: web runs on another server now.`
- Several: `Its copies of api, web and worker were stopped: they run on other servers now.`
- The alert is **Server back in its cluster**, on by default.
- A return that stopped nothing only says `server-a answers again in cluster eu.`

Replicas go back to an even spread at the app's next deploy, not at once.

<Callout type="warn" title="Known limit: old copies run for a few seconds after a power loss">
  - When a server comes back from a **power loss**, its databases and apps with a Volume start by
    themselves at boot. They run for **2 to 4 seconds** (measured) before the server stops them,
    while the copies that moved are live on another server.
  - **A visitor who reaches that server in those seconds can be served by the old copy**, for
    example at the app's old generated address.
  - What the old copy writes then never reaches the live database. It is kept only in the backup
    labelled **Left on server-a**, described below.
  - After a **network cut** this does not happen: the server had already stopped its copies itself.
</Callout>

**The leader's server coming back right after its apps moved away** takes the lead back, and the
leader first asks every server what it runs: each database and app with a Volume stays where it
runs, and the server that came back stops its own copy. Since server agent 0.5.3-canary.12 and
leader 0.1.0-canary.6, installed by Deplo 0.8.2-canary.31: in 6 runs, 3 of them with the server
back 55 seconds after it lost its power, **no write was taken by two servers and no second copy ran
for even a second**. With older versions both copies ran and took writes, for 93 to 96 seconds.

<Callout type="warn" title="Known limit: a server restarts its databases once after a boot">
  - A few seconds after a server boots, it can stop its databases and apps with a Volume and start
    them again 3 to 4 seconds later. Seen in 12 of 14 boots of a test server that does not run the
    leader.
  - Nothing runs twice: it only costs those seconds. Server agent 0.5.3-canary.12 logs why, and the
    fix follows once the logs show the cause.
</Callout>

## Data left on the server [#data-left-on-the-server]

A server that comes back may still hold data that the moved database or app wrote **before it
stopped** and that never reached a backup. Deplo does not throw it away silently.

**Before its copy is removed, what the server still held is saved as a backup.** This covers a
database and an app with a Volume. The server does it by itself, also while Deplo is down.

It goes where the backups of that database or app already go, **a bucket or another server's
disk**:

| Where its backups are kept | What happens |
| --- | --- |
| A **bucket** | Saved, and listed with its backups as **Left on server-a after the failover at 14:32** |
| **Another server of the cluster** | Saved the same way. The returning server sends it to that server directly |
| A server that is **not in the cluster** | **Not saved.** The data stays on the returning server. Keep the backups in a bucket, or on a server of the cluster |
| Nowhere (no backup schedule) | **Not saved.** The data stays on the returning server |

Without a bucket, Deplo keeps a cluster's backups on another server of the cluster, so the default
setup is covered.

- **It is encrypted before it leaves the returning server**, with the destination's key. The
  server that stores it never sees the data in the clear and holds no key to open it.
- **A server only accepts such a backup from a server of its own cluster**, and only the one file
  the cluster expects from it.
- **The data is removed from the returning server only once the destination has confirmed it
  holds the whole backup**, and only while the database or app still runs on another server. One
  that was moved back to that server meanwhile keeps its data there, untouched, and nothing is
  saved.

### It keeps trying

If the destination cannot be reached when the server comes back, the data stays on the server and
the server tries again on its own: **after 1 minute, then 2, 4, 8 and so on, never more than an
hour apart**, for as long as it holds the data. A restart of the server does not stop it. Nobody
has to press anything.

- **When a later try succeeds**, the backup appears with the same label, and Activity gets one
  line by Deplo. There is no second alert.
- **A repeat never leaves two files**: a try that was cut short is written over by the next one.

### What Activity and the alert say

| Sentence | When |
| --- | --- |
| `What it still held of db was saved as a backup, labelled "Left on server-a".` | Saved |
| `What it still held of db could not be saved as a backup, so it stays on server-a: the backup failed`, then the server's own error in brackets | The try failed |
| `What it still held of db could not be saved as a backup, so it stays on server-a: its backups are kept on server-b, and server-a could not send it there.` | The other server could not be reached |
| `server-a tries again on its own, and Activity says when it is saved.` | Added once after either of the two above |
| `What it still held of db could not be saved as a backup, so it stays on server-a: its backups are kept on server-x, which is not in cluster eu.` | Its backups are outside the cluster. Nothing is retried |
| `What it still held of db could not be saved as a backup, so it stays on server-a: the cluster had no backup destination for it.` | No backup schedule. Nothing is retried |
| `server-a saved what it still held of db as a backup, labelled "Left on server-a".` | A later try succeeded |
| `server-a saved what it still held of db, but Deplo could not match the file to db's backups, so it is not listed.` | Saved, but not where that database's backups go |

A failed try can name the other server: `reach the server that holds the backups`, `the server
that holds the backups did not confirm it`, or `the server that holds the backups refused it: this
server was not told to keep that`. The last one means the two servers have not both heard from the
cluster yet. The next try passes.

### What you can do with it

The backup is in the **Backups** tab of the database or app, with **Download**, **Restore** and
**Delete** in its menu.

- **It is never deleted by "keep the last N"**, and it does not count towards N.
- **Deplo never restores it on its own.** A later failover restores the newest ordinary backup.
- **Restoring it costs everything written since the failover.** The dialog says: "This overwrites
  db in place with what server-a still held when it came back." and "The database is stopped and
  its current data is wiped: everything written since the failover is lost."
- **Deplo does not merge it into the live data.** Download it to look at what is in it.
- It is a copy of the data folder as the old server left it, not a dump. A PostgreSQL database
  restored from it recovers by itself, as after a crash, and takes a new base backup before its
  change log counts again.
- **Restore** needs **Restore backups**, **Delete** needs **Delete backups**, and downloading an
  app's also needs **Reveal secret values**.

The row's date is when it was saved. The label carries when the failover happened: the
time alone when it was today, `3 Mar, 14:32` otherwise, and "Left on a removed server" once that
server is gone.

An app with only a Bind, and an app that keeps nothing, have nothing to save.

## Set-aside copies [#set-aside-copies]

**The returning server never deletes what it held.** Before its copy of a database or an app with
a Volume goes, it moves each volume, and the app's **Files**, to a **dated copy on itself** (on the
same disk this is instant whatever the size: 2.9 GB in 0.3 s on a test cluster), with
or without a backup, so writes the [replication copy](/operations/clusters/replication) had not
received yet when the server was cut off are still somewhere.

- **Nothing runs from it**, and Deplo never puts it back on its own.
- **Activity** says it on the return: `server-a kept a dated copy of what it held of web (12 MiB),
  with any writes its copy had not sent yet: it is listed on web's page until an admin removes it.`
- **The app's Settings -> Storage** lists each copy under **Set-aside copies**: when it was made, on
  which server, the volume (or **Files**) and its size.
- **Remove** deletes one for good. It needs **Delete backups**. Activity:
  `Removed the copy of web's data that server-a set aside on 2026-11-23 04:05 UTC (12 MiB)`.
- **It stays until removed**, and takes room on that server's disk meanwhile.

A database's dated copies are made the same way, and are not listed on its page yet.

### A move never writes over a newer copy [#newest-copy-wins]

When an app with a Volume moves between two servers of the cluster (you move it, a server is
removed, or a move is continued), **its data comes before it starts** on the new server, and **the
copy that ran last wins**:

- **The old server ran it last** (the usual move): its data is copied over, and whatever the new
  server held of the app is set aside on it first.
- **The new server ran it since** (a move that stopped half-way and was continued): nothing is
  copied. The old server's copy is set aside on the new one, listed with the others, and goes from
  the old server only after. Activity: `Kept web's data on server-b, which ran it after server-a
  did. server-a's older copy was set aside on server-b (12 MiB), never copied over it.`

### Deploy anyway [#set-aside-copies-deploy-anyway]

**Deploy anyway** on an app whose move is held (its old server could not be reached to copy the
data) **deploys it at once** on empty storage, and **sets the old server's copy aside instead of
deleting it**. Activity, in order:

1. `Accepted that web starts without the data its previous server still holds: Deplo sets that copy aside, never deletes it`
2. `Deploying web`, as soon as the old copy is stopped, or at once when its server does not answer
3. `Deployed web without the data its previous server still holds`, only once that deploy is ready

Where the old copy goes:

- **The old server answers:** its copy, Files included, is set aside on the server the app runs on,
  listed with the others, and goes from the old server only after. Activity: `What server-a held of
  web was set aside on server-b (12 MiB).`
- **It does not answer:** Deplo deletes nothing there, and says only what it knows:
  `server-a does not answer, so what it holds of web stays on it for now: Activity says where it is kept once server-a answers again.`
  Once back, it sets its copy aside itself, as any returning server does, and Activity says so.

Measured on canary.80: the app answered again 13 seconds after the click, with its old server off.

### Deleting the app [#set-aside-copies-delete]

**Delete removes every set-aside copy** of the app on every server of the cluster, with the rest of
its data, under the same confirmation. Activity: `Removed 2 set-aside copies of web's data: 1 on
server-a, 1 on server-c.` A server that does not answer has the app, its data and its copies
removed as soon as it answers again, usually within a minute, and the line says so:
`server-a did not answer: what it holds of it goes once it answers.` Activity then says
`Finished the teardown of web on server-a`.

**Over the API**: `appSetAsideCopies(appId)` and `removeAppSetAsideCopy(appId, serverId, volumeName)`.
