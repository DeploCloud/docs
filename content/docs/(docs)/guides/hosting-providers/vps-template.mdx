The setup we recommend to every hosting provider: a clean base image, one command at first
boot, and an address you can predict. The customer signs in with the email and password from
your welcome email. No log to read, no key to copy.

<Steps>
<Step>

### Create the base template

Start from a clean, minimal image:

| | Requirement |
| --- | --- |
| OS | <Os name="ubuntu">Ubuntu</Os> 24.04 LTS, 26.04 LTS · <Os name="debian">Debian</Os> 12, 13 |
| Architecture | `x86-64` or `arm64`, with `systemd` |
| Ports | `80` and `443` open from the internet |
| Smallest plan | 2 cores, 4 GB of RAM, 30 GB of disk |
| Comfortable plan | 4 cores, 8 GB of RAM |

More in [what you need](/getting-started/install#what-you-need).

</Step>
<Step>

### Run the installer on first boot

Chain the installer to your provisioning, right after the operating system install finishes.
`--owner-email` and `--owner-password` create the customer's account during the install:

- **The email** is the customer's, the one on their order.
- **The password** is a temporary one you already send them, at least 8 characters. Best is a
  random one generated for each order, like the service password your billing (WHMCS, for
  example) already creates.
- **Only the root password available?** Some panels cannot pass anything else (Virtualizor
  recipes, for example). That works too: it is only used for the first sign-in.
- **At the first sign-in** Deplo makes the customer replace it with a password of their own.
  Until then the account cannot do anything else, so the temporary password, root or not,
  gives no access to the panel.

The command depends on the address the customer's panel starts on:

<Tabs groupId="panel-domain" persist items={['Temporary domain', 'Custom domain']}>
<Tab value="Temporary domain">

The panel starts on an automatic wildcard address, with no DNS to set up and nothing to ask
the customer:

<Tabs groupId="provisioning" persist items={['Using cloud-init', 'Provisioning script']}>
<Tab value="Using cloud-init">

```yaml
#cloud-config
runcmd:
  - curl -fsSL https://deplo.build/install.sh | bash -s -- --yes --owner-email ada@acme.com --owner-password '<temporary password>'
```

</Tab>
<Tab value="Provisioning script">

```bash
curl -fsSL https://deplo.build/install.sh | bash -s -- \
  --yes --owner-email ada@acme.com --owner-password '<temporary password>'
```

</Tab>
</Tabs>

By default that address is on `deplo.site`, Deplo's own wildcard domain. You can use yours
instead: see [Use your own wildcard domain](#use-your-own-wildcard-domain).

</Tab>
<Tab value="Custom domain">

If your order form already asks the customer for a domain, pass it to the installer with
`--domain`. The panel starts directly on that domain, with a Let's Encrypt certificate:

<Tabs groupId="provisioning" persist items={['Using cloud-init', 'Provisioning script']}>
<Tab value="Using cloud-init">

```yaml
#cloud-config
runcmd:
  - curl -fsSL https://deplo.build/install.sh | bash -s -- --yes --owner-email ada@acme.com --owner-password '<temporary password>' --domain panel.customer-domain.com
```

</Tab>
<Tab value="Provisioning script">

```bash
curl -fsSL https://deplo.build/install.sh | bash -s -- \
  --yes --owner-email ada@acme.com --owner-password '<temporary password>' \
  --domain panel.customer-domain.com
```

</Tab>
</Tabs>

<Callout type="info" title="The flow we recommend">
  When you can pass the domain at install time, do it. The customer lands on their own address
  from the very first login, and never has to move the panel later.
</Callout>

The domain's DNS has to point at the VM's IP: the certificate is issued on the first request
to the domain. If DNS is not ready yet, the generated `deplo.site` address still works as a
backup.

</Tab>
</Tabs>

The cloud-init version works as is on any panel that accepts cloud-init user-data: Proxmox VE,
SolusVM 2, Convoy, OpenStack, CloudStack. On VirtFusion, add it as a server provisioner, in
Bash or cloud-init YAML.

<Callout type="info" title="On Virtualizor">
  In a recipe, `{{username}}` is the customer's email and `{{root_pass}}` their root password,
  used as the temporary one: `--owner-email '{{username}}' --owner-password '{{root_pass}}'`.
</Callout>

</Step>
<Step>

### Build the customer's address

<Tabs groupId="panel-domain" persist items={['Temporary domain', 'Custom domain']}>
<Tab value="Temporary domain">

`deplo.site` is wildcard DNS: a name that carries an IPv4 in hexadecimal resolves to that IP,
with no DNS setup. So the panel address is predictable:

```
https://deplo-<ip-in-hex>.deplo.site
```

Each octet becomes two hex digits. `203.0.113.10` gives `cb00710a`:

```
https://deplo-cb00710a.deplo.site
```

<Tabs items={['Bash', 'JavaScript', 'PHP']}>
<Tab value="Bash">

```bash
IP=203.0.113.10
echo "https://deplo-$(printf '%02x' ${IP//./ }).deplo.site"
```

</Tab>
<Tab value="JavaScript">

```js
const panelUrl = (ip) =>
  `https://deplo-${ip.split(".").map((n) => (+n).toString(16).padStart(2, "0")).join("")}.deplo.site`;
```

</Tab>
<Tab value="PHP">

```php
$url = "https://deplo-" . bin2hex(inet_pton($ip)) . ".deplo.site";
```

</Tab>
</Tabs>

With your own wildcard domain, replace `deplo.site` with it.

</Tab>
<Tab value="Custom domain">

The address is the customer's domain, nothing to compute:

```
https://panel.customer-domain.com
```

</Tab>
</Tabs>

</Step>
<Step>

### Send it

- **Where**: in the welcome email or the VPS detail page, next to the email and temporary
  password they sign in with.
- **When**: the install takes a few minutes after boot; until then the address does not answer.
- **What they see**: a sign-in page, then a short setup that replaces the temporary password and
  names their team.

On a temporary domain, the customer can later move the panel to their own from
**Settings -> Deplo**: see [the panel's own address](/operations/panel-address-and-certificates).

</Step>
</Steps>

## Use your own wildcard domain

`deplo.site` is optional. To put the panel under your brand, run wildcard DNS on a domain of
yours and pass the hostname with `--domain`, filling in the VM's IP:

<Callout type="warn" title="Use a dedicated domain">
  Keep the wildcard on a domain separate from your main one, the way Deplo keeps `deplo.site`
  apart from `deplo.build`. Customer servers answer on it, so abuse reports, blocklists and
  cookies stay away from your website and your billing panel.
</Callout>

```bash
curl -fsSL https://deplo.build/install.sh | bash -s -- \
  --yes --owner-email ada@acme.com --owner-password '<temporary password>' \
  --domain deplo-cb00710a.example-vps.net
```

The address becomes `https://deplo-cb00710a.example-vps.net`, with a Let's Encrypt
certificate.

- **We recommend self-hosting [nip.io](https://github.com/exentriquesolutions/nip.io)**: it
  resolves the hex form of the IP out of the box. Set it as the nameserver of
  `example-vps.net` at your registrar.
- **Even better, host it on Deplo itself** when you can, on a server of yours: it is a DNS
  server, so that server needs port `53` open on UDP and TCP.
- The generated `deplo.site` address stays on as a backup. The customer can turn it off from
  **Settings -> Deplo**.
