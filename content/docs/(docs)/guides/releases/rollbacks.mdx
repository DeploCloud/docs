Every build Deplo performs leaves an image on the server, recorded on the deployment row. A
rollback tells the agent to run that image again, so going back takes seconds and rebuilds
nothing. Rolling back needs the `rollback_apps` capability.

Three things follow from re-running an image rather than rebuilding:

- **There is no rebuild.** No clone, no dependency resolution, no waiting, and no chance that the
  dependency tree resolves differently than it did in February.
- **Only the code goes back.** Environment variables, domains, volumes and resource limits are
  re-rendered from your **current** settings. A rollback is not a time machine for configuration.
- **It is a real deployment.** It gets its own row, its own logs and its own activity entry,
  marked as a rollback of the deployment it came from, and it does not consume a retention slot.

The app is serving the older image within seconds.

A deployment can be rolled back to only when it still qualifies. Deplo refuses when the target
ran on a **different server** than the app is on now, when it belongs to a **preview** rather than
production, and when the target **is itself a rollback**. Each refusal says which it was.

## Retention

<Image
  src={`${basePath}/screenshots/rollbacks/03-retention.png`}
  alt="Keep rollbacks, the number of old deployments kept ready to go back to"
  width={1728}
  height={1080}
  className="w-full rounded-lg"
/>

**Settings -> Deployments**, the **Rollbacks** card, field **Keep**.

| | |
| --- | --- |
| Default | `3` |
| Maximum | `20` |
| `0` | Hides the action for this app. The save toast confirms it |

The host is told to keep `Keep + 1` images per app, and the rest are removed by the server's disk
cleanup after a deploy. A kept image is a tag sharing layers with the others, not a full copy, but
it is still disk.

This number is the real retention. Deplo pushes to no registry, so once an image is pruned from
the host, that deployment can never be rolled back to again, even though its row is still in the
list.

## Good to know

- **Only sources Deplo builds can roll back.** A Docker image app has no image Deplo owns, and a
  Compose stack has no single image. Neither offers the action.
- **A rolled-back app still auto-deploys.** The next push builds and releases over the top. Turn
  off **Deploy on push** first if you are rolling back because the branch is broken.
- **A database migration does not roll back with the code.** The image goes back; whatever it did
  to your data does not.
- **Rolling back does not pause anything.** If you need the app stopped, use **Stop**.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The **Rollback** action is missing | The source is a Docker image or a Compose stack, **Keep** is `0`, or you do not hold `rollback_apps`. |
| Rollback is refused on a specific deployment | It ran on another server, it is a preview deployment, or it is itself a rollback. |
| Rollback fails with an image that is not found | It was pruned. Raise **Keep**, or exclude that server from unused-image cleanup. |
| It rolled back and the bug is still there | The bug is in configuration or data, not in the code. Neither travelled. |
