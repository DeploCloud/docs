---
title: Apps with stored data
description: On a cluster, an app with a volume waits for its server unless you bring it back from a backup.
---

An app that keeps data on its server cannot simply start somewhere else: its files are not there.
On a [cluster](/operations/clusters) Deplo treats it like a database.

| The app keeps | When its server stops |
| --- | --- |
| Nothing | It moves on its own. See [When a server stops](/operations/clusters/failover) |
| A **Volume**, a **File** written in Storage, or a Compose app's own volume | **It waits for its server**, unless you say otherwise |
| A **Bind** | It never moves |

The app's **Overview** has a **Failover** card that says which one applies. For an app with a
Volume, the card adds, under its sentence:

- "Never two writers"
- "A failover restores the latest backup, and says how old it was"
- "Each backup pauses it for as long as its files take to copy."

## It gets a backup

An app with stored data on a cluster gets the same **Failover backup** as a
[database](/operations/clusters/databases#the-failover-backup): every 15 minutes, to a bucket
first, else another server of the cluster, never the server it runs on.

- It is created when the app is deployed on the cluster, or arrives because its server joined.
- An app that already has a backup schedule keeps its own.

## By default it waits

> web waits for server-a if it stops, so it never starts on old files. You can bring it back on
> another server from its latest backup.

Waiting loses nothing: when the server is back, the app carries on with every file it had.

While the server is stopped, the app's page says **web is waiting for server-a** and offers one
button, naming the backup it would restore:

**Bring web back on another server from the backup of 14:15**

It needs **Restore backups**. The dialog asks "Bring web back from a backup?" and warns:
"Anything it wrote after that backup is lost." Confirm with **Bring it back**.

Activity records `Asked cluster eu to bring web back on another server from the backup of 14:15`,
then by Deplo `Restored web on server-b from the backup of 14:15`.

### When the click is refused

| It says | Why |
| --- | --- |
| "web's server may still be running it. Deplo never starts a second copy next to one that could be writing: try again in a minute." | About 80 seconds have not passed since the server went quiet. In [the slower case](/operations/clusters/failover#the-slower-case) it is longer |
| "web has no backup another server can read." | Its backups are on its own server, or on a server outside the cluster |
| "No other server of the cluster has room for web." | Add a server or lower its memory |
| "No other server of the cluster is online to take web." | Bring one back |
| "The cluster's leader cannot reach its servers right now. Try again in a minute." | The leader cannot reach the servers, or too few of them answer it. See [When a cluster is cut in two](/operations/clusters/failover#when-a-cluster-is-cut-in-two) |

A move that fails later is an Activity entry: `Could not bring web back on another server. web did
not start on another server.`

## Let it fail over on its own

**Settings -> Advanced -> Fail over automatically from the latest backup**. It needs **Configure
apps**, and shows only for an app with stored data on a cluster.

> Off, it waits for its server and loses nothing. On, it comes back sooner and loses what it wrote
> after the backup.

On, the Failover card says: "web moves to another server on its own if its server stops, restored
from its latest backup. Anything written after that backup is lost."

The backup must be one another server can read: in a bucket, or on another server of the cluster.
Otherwise Activity has an entry that starts `web cannot fail over yet:`, with the same reasons as for a
[database](/operations/clusters/databases#when-a-database-does-not-fail-over).

## An app with a Bind never fails over

> web never fails over: it uses a folder that lives on server-a, and only on that machine.

Keep the data in a Volume, or in a database, to change that.

## When the server comes back

What the old server still held is saved as a backup before its copy is removed, where the app's
backups already go: a bucket, or another server of the cluster. See
[Data left on the server](/operations/clusters/failover#data-left-on-the-server).

**Over the API**: `setAppFailoverFromBackup`, `bringAppBack`, `App.failoverFromBackup` and
`App.failover`. Over MCP: `set_app_failover_from_backup` and `bring_app_back`.
