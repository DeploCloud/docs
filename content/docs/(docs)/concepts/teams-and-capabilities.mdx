Deplo is built for several people sharing one instance. Everything belongs to a **team**, every
change is checked against a **capability**, and a **role** is a named set of capabilities.

Alone on your instance? None of this gets in your way: you are the Owner of your own team.

## Team

An isolated workspace. It owns apps, domains, environment variables, databases, backup
destinations, registries, git connections, activity, members and notification settings. A person
can belong to several teams and switches the **active team** from the top bar; every list is
filtered by it.

<Callout type="info" title="Servers are the one exception">
Servers belong to the instance, not to a team. Which teams may deploy to a server is a setting on
the server.
</Callout>

### The team's address

Every page has the team in its address, `deplo.example.com/acme/apps/wiki`, so a shared link
opens in the right team whoever clicks it. The name never changes after creation. A link to a team
you are not in shows a "no access" page listing your own teams.

### Deleting a team

**Settings -> General -> Danger zone**, with `delete_team`. Everything in it goes: apps and
databases with their data, folders, projects, domains, variables, members and backups. Your only
team cannot be deleted.

### The primary owner

The account that created the team. No other owner and no instance admin can remove, demote or
edit them.

Only the primary owner can hand the team over, to a member of the same team, with their password
and second factor: from **Settings -> General -> Danger zone -> Transfer ownership**, or from
**Settings -> Members ->** the member **-> Advanced**. An API token never can.

## Capability

**One capability is one action:** `create_apps`, `deploy_apps`, `delete_apps`,
`open_app_console`, `restore_backups` and so on. There are 46, `view` included, the floor every
member has. Deleting an app is `delete_apps`, not `deploy_apps`.

One to know by name: **`reveal_secrets`** shows a managed database's connection string and a
backup recovery key, downloads a backup, and connects a database to an app. A secret
environment variable is never readable, with any capability.

The full list is in [Capabilities](/reference/capabilities).

**Every capability is checked in the data layer** before the write, for the dashboard, the API and
the MCP server alike. Hidden or disabled buttons are only cosmetic. An id from another team behaves
as if it did not exist.

## Role

A role belongs to a team. Every team starts with **Owner**, **Member** and **Viewer**, which it can
rename, edit and reset to the defaults, and can add as many more as it likes.

- **Owner always has full access** and cannot be reduced.
- **Editing a role changes every member holding it** at once.
- No change may leave the team with nobody holding `manage_members`, `manage_roles` or
  `manage_team`.
- A member with no role has a hand-picked **Custom** set.

## Access inside one folder

A set of capabilities can also be given on a **folder, a project or a single app**. Inside it,
that set **replaces** the team role, and **can be larger**. The most specific grant wins.

This is how someone with a read-only team role can deploy everything in one folder, and nowhere
else.

## API tokens

A token **belongs to the person who created it**: nobody else, not even an instance admin, lists,
edits or revokes it.

- **It has its own capabilities**, chosen at creation and editable later. It never does more than
  its owner can do right now.
- **The team decides where it acts.** It reaches a team only while its owner holds `manage_tokens`
  (**Use API tokens**) there, and drives it over MCP only with **Connect AI agents**. A team takes
  access away through the member, never the token.
- **It can be narrowed** to teams, projects, folders or single apps, and given an expiry. It is
  shown once.

## Two-factor is a policy, not a capability

A team, or a role inside it, can **require** two-factor authentication. A member without it can do
nothing in that team, in the dashboard, over the API or with their tokens: they see a lock screen
to enable it, switch team or sign out. Signing in with a passkey satisfies it.

## Instance admin and instance owner

Per-user grants outside any team, set by an instance admin in **Settings -> Users**:

- **Instance admin** unlocks Servers, Users, Migrations and the Deplo instance settings, and holds
  the three grants below implicitly.
- **Publish ports** (`canExposePorts`) lets a stack publish a port on the server.
- **Bind server folders** (`canMountHostVolumes`) allows every way out of a container: bind mounts,
  `privileged`, added kernel capabilities, devices, host namespaces, foreign networks and volumes.
  See [Host access](/advanced/host-access-and-privileges).
- **Configure Traefik** allows custom proxy labels, which can affect other teams on the server.

**Instance owner** is the level above, held by the account created at first setup. No other admin
can demote, suspend or reset it, and it cannot drop its own admin flag. Only the owner transfers it,
to an active instance admin, with their password. A locked-out owner is recovered only with
`deplo recover` on the host.
