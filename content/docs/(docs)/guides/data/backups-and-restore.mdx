Scheduled, encrypted copies of a database or an app, sent to an S3 bucket or to another server's
disk, with a restore that puts them back.

- A **destination** is where the copies go.
- A **schedule** says what to copy, where, how often and how many to keep.
- A **run** is one execution. It produces one **artifact**.

The backup runs on the server that holds the data. It is compressed and encrypted with `age`
before it leaves the server, with one key pair per destination. Nothing in between can read it.

Then click **Test connection**. An agent runs a real test: a small write and a delete on a bucket,
a write and a free-space check on a folder. A read-only key is reported as failed.

A failed test is a normal result. **Connection log** in the destination's menu shows every step
and the commands to repeat it by hand.

## Save the recovery key

Every destination has one. Download it from **Download recovery key** in the destination's menu.
The card keeps reminding you until somebody does.

You need it when `DEPLO_SECRET` was rotated or lost, or when the control plane itself is gone. With
the file, any artifact from that destination can be decrypted anywhere:

```bash
age -d -i recovery-key.txt backup.sql.gz.age > backup.sql.gz
```

<Callout type="info">
Downloading the key is recorded in the activity log.
</Callout>

**Keep is a count, not a number of days.** `Keep 7` (the default) keeps the seven most recent
successful artifacts. The newest one is never removed, and a failed run does not use a slot. The
maximum is 365.

## Restore

Every finished run is a restore point, listed under **Restore points** on the target's **Backups**
tab. Each row's menu has **Restore**, **Download** and **Delete**.

**A restore replaces the current data.** It asks you to type the target's name.

**Back up -> Restore from file** restores an artifact from your computer. If it is encrypted,
paste the recovery key.

## Download an artifact

**Download** in a restore point's menu. The artifact is decrypted on the way out. This needs
`restore_backups`. An **app** archive also needs `reveal_secrets`, because it contains the app's
environment variables.

## Good to know

- **An app schedule does not include its databases.** Schedule the database separately.
- **Retention counts successes.** Failed runs do not use a slot.
- **A skipped hour on a DST change shows a warning.**
- **`delete_backups` is a separate capability**, because deleting runs can leave a target with no
  restore point.
- **Deleting a schedule does not delete its backups.** They stay until you delete them under
  **Restore points**.
- **Deleting the app or database removes its backups after 30 days.** Until then they can still
  be recovered.
- **A destination on the same server as the data is lost with that server.** Put at least one
  copy elsewhere.
- **Backups are always encrypted.**

## Troubleshooting

- **Test connection fails on a bucket** - usually the key is read-only, or the endpoint and region
  do not match the bucket. Read the **Connection log**.
- **Runs fail with no space** - the destination server's disk is full.
- **Restore refuses** - the checksum did not match, or the artifact is encrypted with a key this
  destination does not hold. Use **Restore from file** with the recovery key.

More in [Databases and backups](/troubleshooting/databases-and-backups).
