---
title: GitLab
description: Connect a GitLab instance, gitlab.com or self-hosted, as a git connection.
---

GitLab connects as a **git connection**: one stored credential per host,
reused by every app that deploys from it. It is marked **Beta**.

## Connect it

<Steps>
<Step>

### Add a connection

**Settings -> Git**, then add a connection.

</Step>
<Step>

### Pick the type

Pick **GitLab** as the **Type**.

</Step>
<Step>

### Set the address

Fill in the **Address**. Leave the default for gitlab.com, or point it at
your self-hosted instance's base URL.

</Step>
<Step>

### Set the username

Fill in the **Username** as **`oauth2`**. GitLab expects this exact value
for token authentication, not your account name.

</Step>
<Step>

### Paste the token

Paste a GitLab personal or project access token with repository read
scope.

</Step>
<Step>

### Test and save

Click **Test connection**, then **Save**.

</Step>
</Steps>

Later, **Replace the token** swaps it without recreating anything, and
**This connection stopped working** appears when a background check finds
it broken. GitLab reports token expiry, so an expiring token surfaces
before it actually breaks a deploy.

An instance admin can also tick **This git server is on my own network**
for a self-hosted address that is not publicly routable. It is
deliberately admin-only, because it turns off a guard that stops Deplo
being used to probe your internal network.

## If it does not work

- **`Authentication failed` in a clone**: the token expired or was
  revoked. **Test connection** confirms it.
- **Saving a self-hosted address is refused**: it resolves to a private
  address, and only an instance admin can allow that.
