**One click updates everything.** On **Settings -> Deplo -> Updates**, click **Update**:

1. Deplo saves a `pg_dump` of its database to `/opt/deplo/backups` (the newest three are kept).
2. The machine Deplo runs on pulls the new version and restarts the panel. Migrations run as it starts.
3. Once it is back, Deplo brings every server to the server agent that version is paired with, one at a time.

Secrets are never rotated and no setting is reset. If the new version does not start, the previous one
comes back on its own: see [An update was rolled back](#an-update-was-rolled-back).

<Callout type="info" title="Your apps keep running throughout">
They are containers on your servers, not part of the panel. While the panel restarts you can't deploy
or read logs for about a minute; your sites stay up.
</Callout>

## Release history

**Settings -> Deplo -> Updates**, instance admins only.

- The top card says where things stand, like **Deplo is up to date** or **A server needs attention**.
  **Update** appears only when there is something to install; **Check now** asks GitHub again.
- **What changed** lists the release notes, marked **Installed**, **Update available** or **Canary**.

## When a new version is out

Instance admins see it without opening Settings:

- **A chip in the top bar** names the new version and opens the Updates tab.
- **A security fix:** when a newer Deplo fixes a security flaw this instance has, the chip turns red
  and reads **Security fix**, and the sidebar shows a **Deplo security fix** card with **Update now**.
  The card can't be dismissed: it goes away once you update.
- **Alerts:** **Deplo update available** and **Deplo security fix** are on by default, under
  **This Deplo instance**. The security alert repeats every 3 days until you update. See
  [Notifications and alerts](/guides/observability/notifications-and-alerts).

## Stable or canary releases

**Settings -> Deplo -> Advanced -> Canary releases**, off by default.

- **Off:** only stable versions show up as updates.
- **On:** every new version does, canaries included. They can have bugs: not for production.

The switch installs nothing by itself, and turning it off never moves a canary panel back to stable.
**Activity** records the change.

## Update the control plane

<Steps>
<Step>
### Open Settings -> Deplo -> Updates
</Step>

<Step>
### Click **Update** and confirm
The confirmation names the version and the servers that follow, for example
**Update Deplo to v0.8.1, then its 3 servers?**. The version is not always the newest: see
[When Update offers an older release](#when-update-offers-an-older-release).

An **offline** server on a server agent the new version no longer supports is named:
`edge-2 is offline on server agent v0.5.1 and will be unusable until its server agent updates.`
</Step>

<Step>
### Wait about a minute
The page reloads itself on the new version. Then the top card counts the servers as they follow, like
`2 of 3 servers are on the latest version.` Nothing to click.
</Step>
</Steps>

**The update did not take** (after 10 minutes) names the log file the machine wrote. **Deplo could not
update itself** shows the command to run: see [If the panel cannot update itself](#if-the-panel-cannot-update-itself).

## The agents follow on their own

Once the panel is back, Deplo updates each server's agent by itself: remote servers first, the
machine Deplo runs on last, one at a time. **Activity** records each one under the name of whoever
clicked **Update**.

A failure on one server does not hold up the others. Its line on the Updates tab says why:

- `Waiting for a deploy to finish, retrying in 4 min`: updating restarts the agent, which would drop the build.
- `Update failed, retrying in 4 min`: the server is unreachable, or the update failed.

Deplo retries after 1 minute, then 2, 4, 8, up to once an hour, for **24 hours** from the first
failure (`Update failed (gave up after 24 h)`).

If a server takes the new agent and **does not come back**, Deplo stops there:
`Waiting for edge-2 to recover before updating the rest.` A broken agent release reaches one server,
not all of them.

A server that hasn't connected to Deplo, or can't, gets no update and holds up nobody. See
[When a server is unusable](#when-a-server-is-unusable).

**Traefik follows too.** When a server connects, Deplo moves its Traefik to the version this release
pins (v3.7.17 since Deplo 0.8.1), on the same release line only: a version you picked on another
line is left alone. Traefik restarts once, and **Activity** records
`Updated Traefik on edge-2 to v3.7.17`. A failure is retried when the server reconnects.

### Retry an update by hand

**Retry now** appears once an update has failed, on the server's page and on its line in the
Updates tab. Instance admins only.

- It tries at once, in place of the scheduled retry, and never while an attempt runs.
- If it fails, the automatic retries carry on. The 24 hours do not start again.
- After the 24 hours it is the only way to retry, except for a server that was offline: it gets one
  more automatic attempt when it comes back.

## When a server is unusable

A server Deplo can't work with is **unusable**: deploys, logs, the console, backups and every other
action on it are refused. **Its apps keep running**, and its apps and settings stay in Deplo.

Its line under **Server agent** on the server's page says which case it is, and so does its line on
the Updates tab. Instance admins also see a banner:

| Its line | Banner | What brings it back |
| --- | --- | --- |
| `Unusable - Deplo is updating it`, or how the update stands, like `Unusable - Update failed, retrying in 4 min` | `edge-2 is unusable until its server agent updates.` | The update: automatic, or **Retry now** |
| `Unusable - it hasn't connected to Deplo yet` | `edge-2 hasn't connected to Deplo yet.` | The server connecting by itself. See [A server hasn't connected to Deplo yet](/troubleshooting/servers-and-agents#a-server-hasnt-connected-to-deplo-yet) |
| `Unusable - reinstall its server agent` | `edge-2 is unusable until its server agent is reinstalled.` | [Reinstalling its server agent](/troubleshooting/servers-and-agents#a-server-agent-needs-to-be-reinstalled) |

Several servers are counted in one banner:
`3 servers are unusable until their server agents update or are reinstalled.` With more than three
behind, **Read more** on the Updates tab lists them all.

### Its server agent is older than Deplo supports

Each Deplo version supports server agents down to a minimum. Below it, every action is refused with
`This server is being updated. Deplo retries on its own; an instance admin can retry it now.` If the
update fails, the **Server unusable until it updates** alert goes out. An agent newer than the paired
one is fine and left alone.

### A server agent too old to connect

A server agent older than `0.5.1-canary.10` can't connect to Deplo, so Deplo can neither reach nor
update it. It shows **Offline** and **Agent too old**, with no **Retry now**, and every action is refused
with `This server can't be used until its server agent is reinstalled. An instance admin can do it from the server's Advanced tab.`
[Reinstall its server agent](/troubleshooting/servers-and-agents#a-server-agent-needs-to-be-reinstalled)
and it comes back as it was. A server [left behind](#leave-a-server-behind) can end up the same way.

## When Update offers an older release

Update can offer an older version than the newest. Some releases have to come after an earlier one
that gets the instance ready first. That earlier release is an **update stop**, and **Update installs
it first**. The tab then says, for example:

- **Deplo v0.6.0 is available**
- `Deplo v0.8.1 has to come after v0.6.0, so Update installs v0.6.0 first.`

Click **Update** as usual. Once v0.6.0 has finished getting ready, the tab offers v0.8.1 on its own.

- **Older than v0.6.0?** That panel predates update stops and may offer v0.8.1 directly. **Update**
  installs v0.6.0 anyway, because the installer routes through the stop.
- A new install is past every stop already, and the **Canary releases** switch never skips one.

## Updating through v0.6.0

v0.6.0 is the first update stop. From v0.7.0 on, Deplo never calls a server: every server agent
connects to Deplo. v0.6.0 waits until each server has connected that way at least once.

### Servers the update is waiting on

On v0.6.0, the tab says **Getting ready for the next update** and names each server it waits on:

`edge-2 hasn't connected to Deplo yet. Check that it's turned on and connected to the internet.`

Usually nothing is needed: Deplo updates each server agent and the server connects moments later. Its
apps keep running meanwhile. When a server stays on the list:

- **It is off or offline:** once back, it updates and connects by itself.
- **Its line says `Unusable - Update failed, retrying in 4 min`:** wait, or click **Retry now**.
- **Settings -> Servers shows it Degraded,**
  `This server can't reach Deplo at deplo.example.com. Check that it's connected to the internet.`:
  its network can't reach the panel's address.

### Leave a server behind

A server you can't bring back would hold the update forever. On v0.6.0, and only there, an instance
admin can click **Leave behind** next to it. **Leave edge-2 behind?** warns
`After the update, edge-2 won't work until its server agent is reinstalled.`

- **Until you update, nothing changes.** If it connects after all, it drops off the list.
- **After the update, it is unusable** until [its server agent is reinstalled](/troubleshooting/servers-and-agents#a-server-was-left-behind).
  Its apps keep running, and it comes back as it was.
- **No undo.** **Activity** records it. The machine Deplo runs on can't be left behind.

[Removing a server](/operations/remove-a-server-or-uninstall) also takes it off the list.

## An update was rolled back

When the new version does not answer within 2 minutes, the previous one is put back on its own. The
Updates tab says so until an update succeeds:

- **The update to Deplo v0.8.1 was rolled back**
- `The new version did not start, so Deplo went back to the one that was running.`

A release that has to come after an update stop refuses to start on an instance that skipped it,
before touching any data. That only happens when it was installed by hand; the reason names the
release to install first:

`Deplo v0.7.0 has to come after v0.6.0. Update to v0.6.0 first and let it finish getting ready.`

Follow what the tab offers. The pre-update dump in `/opt/deplo/backups` is never restored
automatically: a migration is not undone by going back to the old image.

## If the panel cannot update itself

On the machine Deplo runs on:

```bash
deplo update
```

It follows the **Canary releases** switch, never installs a version older than the one running, and
goes through [update stops](#when-update-offers-an-older-release) like the button. Below a stop it
installs the stop and prints:

```text
Deplo v0.8.1 has to come after v0.6.0, so this update installs v0.6.0 first.
Update again once v0.6.0 has finished getting ready.
```

Without the `deplo` command, run the installer: an existing `/opt/deplo/.env` switches it to update
mode. Add `DEPLO_VERSION` for a given version rather than the newest (stops still apply):

```bash
curl -fsSL https://deplo.build/install.sh | bash
curl -fsSL https://deplo.build/install.sh | DEPLO_VERSION=0.8.1 bash
```

## Before you update again

- **Agents only move forward.** You never pick an agent version, and there is no downgrade.
- **Read the release notes for a minor bump.** During `0.x`, minor means a feature, changed behavior,
  a migration or a newer agent.
- **Back up before a big jump:** see [Disaster recovery](/operations/disaster-recovery).

## Troubleshooting

A panel that won't come back, an image that won't pull, or an agent update that fails: see
[Servers and agents troubleshooting](/troubleshooting/servers-and-agents).
