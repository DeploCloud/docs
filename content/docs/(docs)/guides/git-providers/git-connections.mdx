A git connection is one stored token per host, reused by every app that deploys from it. GitLab,
Bitbucket, Gitea / Forgejo and plain Git connect this way, on their cloud or on your own
instance, and are marked **Beta**. GitHub connects differently: see
[GitHub](/guides/git-providers/github).

## Connect it

<Step>

### Add a connection

**Settings -> Git**, then **Connect**. The new-app wizard has the same list under the Git tile's
**Provider** menu, in **Connect a git provider**.

</Step>
<Step>

### Pick the type and fill in the details

Pick the provider, then fill in **Address**, **Username** and **Access token**. **Name** is
optional. The dialog prints the scopes the token needs.

<Image
  src={`${basePath}/screenshots/git-connections/02-provider-menu.png`}
  alt="The provider menu: GitHub, GitLab, Bitbucket, Gitea and any plain git host"
  width={1728}

/>

<Tabs items={['GitLab', 'Bitbucket', 'Gitea', 'Git']}>
<Tab value="GitLab">

- **Address**: `https://gitlab.com`, prefilled, or your own instance, like
  `https://gitlab.example.com`.
- **Username**: `oauth2`, prefilled. Leave it.
- **Access token**: a personal or project access token.

</Tab>
<Tab value="Bitbucket">

- **Address**: `https://bitbucket.org`, prefilled.
- **Username**: `x-token-auth`, prefilled, for a repository, project or workspace access token.
- **Access token**: that access token. An app password works too, with your Bitbucket username
  instead.

</Tab>
<Tab value="Gitea">

- **Address**: your instance, like `https://git.example.com` (Forgejo included).
- **Username**: your Gitea account name. Required.
- **Access token**: a Gitea access token.

</Tab>
<Tab value="Git">

Any other git server, with the credentials you clone with. No repository list and no webhook:
paste the **Repository URL** in the wizard, and deploy on push through the
[deploy hook](/guides/releases/automatic-deployments#the-deploy-hook).

</Tab>
</Tabs>

Click **Connect**. For GitLab, Bitbucket and Gitea, Deplo checks the token right away. A host on
a private network needs **This git server is on my own network**, which only an instance admin
can tick.

</Step>
</Steps>

On the connection's card, **Test connection** checks the token again and **Edit** swaps in a
**New access token** (empty keeps the current one). GitLab tokens also show **Token expires**;
Bitbucket and Gitea do not report an expiry.

## What the token needs

| Provider | On its token page | What it unlocks |
| --- | --- | --- |
| GitLab | **`read_repository`** | Clone your code to build it |
| GitLab | **`api`** | List your projects and register the push webhook |
| Bitbucket | **Repositories: Read** | List and clone your repositories |
| Bitbucket | **Webhooks: Read and write** | Deploy automatically when you push |
| Gitea | **`read:repository`** | List and clone your repositories |
| Gitea | **`write:repository`** | Register the push webhook so a push deploys |

GitLab reports a token's scopes, so a missing one shows **This token is missing access** on the
card. Bitbucket and Gitea do not, so Deplo lists what the token needs only after the host refuses
something.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| `Authentication failed` in a clone | The token expired or was revoked. **Test connection** confirms it. |
| **This token is missing access** | A scope from the table above is not ticked. Create a token with it, then **Replace the token**. |
| **Deplo could not add the push webhook** | Usually a missing scope. The notice lists what the token needs and the webhook URL to add by hand meanwhile. |
| `Address must not point at a private or internal address` | Only an instance admin can connect a host on a private network. |
