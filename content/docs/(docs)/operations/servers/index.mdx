title: Servers
description: Add and manage servers, team access, cleanup, maintenance, and registries.
---

**Settings -> Servers**, then open a server. Servers belong to the instance, so these pages are for
instance admins; container registries are the exception, being per team.

Every action here goes through that server's agent. The control plane never opens a shell on a host.

Each server's card shows its CPU, memory and disk, from its latest reading.

**A disk over 90% full** shows a warning on the server's card and row and a **Disk almost full** badge
on its page, whatever filled it, an app's own files included. It names what takes the most room,
for example `eu-4's disk is 92% full. Biggest: shop (1.6 GB), a copy of web (48.0 MB). Free some
space on it, or Apps there cannot write.` Activity says it once; it says it again only if the disk
went back under 88% in between.

A server's page has these tabs:

- **Overview**: CPU, memory, disk and Docker; the **Server agent** card with its version, where its
  update stands, **Retry now** once an update has failed (see
  [Update](/operations/update#retry-an-update-by-hand)) and **Check readiness**; **Display name**;
  **Concurrent deployments**; and **Team access**.
- **Apps**: every app and database on this server, from every team, refreshed every 5 seconds, with
  team, project, status, CPU, memory, restarts and domain. A row links to its app only if you are in
  that team.
- **Certificates**, **Maintenance**, **Cleanup** and **Advanced**: see the pages below.

**Concurrent deployments** defaults to `1`: deploys to one server run one at a time, and the rest wait
in a queue. Raising it past what the machine can take makes every deploy slower, not faster.

## Team access

A new server is open to **All teams**, so any team adding an app can pick it. On the **Team access**
card, **Who can deploy** is **All teams** or **Specific teams**: pick the teams, then **Save
access**. The same choice is in the **Add a server** dialog, where **Specific teams** with none
ticked is refused.

- **Narrowing access moves nothing.** Apps already on the server keep running; only new placements
  are affected.
- **A team only sees the servers it may use** when adding an app.

## Clusters

Several servers can act as one: when one stops, its apps move to another. A cluster is added from
the same **Add** dialog and has its own card on this page. See [Clusters](/operations/clusters).

Clusters are in **beta**: an instance admin turns them on in
[Settings -> Deplo -> Experiments](/operations/experiments).

## Put them in order [#put-them-in-order]

**Drag a card** to give it a new place: clusters among clusters, servers among servers. Every admin
sees the same order, and a new server or cluster joins at the end. Deplo's own server starts first
until someone moves it.

- **Dropping a server on a cluster** still moves it into that cluster. Between two cards, it only
  takes a new place.
- **While a search or a filter is on**, the order stays as it is.

## Select several servers [#select-several-servers]

**Ctrl+click** a server's card (**Cmd+click** on a Mac), or drag a box around several. A bar opens
at the bottom:

| Action | What it does |
| --- | --- |
| **Check status** | Asks each picked server how it is, now |
| **Copy addresses** | Copies their IP addresses, one per line |
| **Move to cluster** | Moves them all into one cluster. Shown once a cluster exists |
| **Remove from cluster** | Inside a cluster: takes the ticked servers out of it |

- **Dragging one picked card moves them all**: onto the cluster you drop it on, or together to a
  new place.
- **A server that cannot join stays out**, and the confirmation names it and why:
  "server-c stays out: in us". The others join, one at a time.
- **Only servers can be picked**, never a cluster.
- `Ctrl+A` picks every server shown, `Esc` clears the selection.
