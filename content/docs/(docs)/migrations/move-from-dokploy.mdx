A wizard reads your Dokploy installation over its API and recreates it here, data included. The
configuration comes from the API; the data is read by a Deplo agent on each Dokploy machine.

## Before you start

- **An API key per organization.** In Dokploy: **Settings**, **Profile**, **API/CLI**. Create it
  in that dialog, not over Dokploy's API: a key created over the API allows 10 requests a day, and
  an import needs hundreds. A key reads one organization only, so create one for each.

Each organization is one run. Runs are queued on the server, one after another, so you can close
the page.

### On every source machine

- **A snapshot of every machine.** It is the only way back after a takeover.
- **Root on each Dokploy machine**, to run one install command. The agent dials Deplo, so no port
  has to be open.

## Run the migration

<Tabs items={["Take over this server", "From another server"]}>
<Tab value="Take over this server">

<Steps>
<Step>

**Snapshot the server.** The final step removes Dokploy.

</Step>
<Step>

**Run the installer**, the same command as any install:

```bash
curl -fsSL https://deplo.build/install.sh | bash
```

It finds Dokploy and asks whether Deplo may replace it. Answer no and nothing is installed.
`--yes` does not answer this question; `DEPLO_TAKEOVER=dokploy` does.

</Step>
<Step>

**Open the address it prints.** Until the ports move, Deplo answers over http through Dokploy's
own proxy on port 80. When that is not possible, the installer prints an `ssh -L` tunnel instead,
for example `ssh -L 3001:localhost:3001 root@203.0.113.10`.

</Step>
<Step>

**Create your account, then choose.** **Bring your data over**, or **Start clean**. Start clean
deletes Dokploy and everything it runs, and cannot be undone.

</Step>
<Step>

**Connect, Install, Review.** The panel address is filled in. Paste an API key per organization,
run the printed command on any other machine behind the panel, tick what comes over, and press
**Start migration**. Everything lands on this machine.

</Step>
<Step>

**Take over the machine.** It opens once every organization has landed. Tick **I have no other
teams on this Dokploy**, tick any service listed as losing its data, and type `dokploy`.

Deplo stops Dokploy, inherits its certificates, moves Traefik onto 80 and 443, removes Dokploy's
containers, swarm, networks, images and `/etc/dokploy` (keeping files a Deplo app still mounts),
and restarts Docker. The apps' volumes stay on the disk. The page moves to https by itself.

</Step>
<Step>

**Deploy your apps.** Open each app, check it, and press **Deploy**.

</Step>
</Steps>

</Tab>
<Tab value="From another server">

<Steps>
<Step>

**Open Settings -> System -> Migrations**, then **Dokploy or Coolify**. Enter the **Panel
address** and the **API key**. A private address works too, for example `http://172.17.0.1:3000`
on the same machine.

</Step>
<Step>

**Add a key per organization.** Each joins **Teams to bring over** with the team it lands in: the
team with the same name, otherwise a new one.

</Step>
<Step>

**Install the agent on every Dokploy machine.** Run each printed command as root. The row goes
from **Waiting for the agent** to **Connected**. A machine already in your fleet is reused.

</Step>
<Step>

**Review and start.** Tick what comes over, pick where each app runs and is built (**Build all
on** sets every build at once), then press **Start migration**. You can close the tab: a chip on
every page shows the progress.

</Step>
<Step>

**People, then Done.** Members get single-use registration links and join as plain members; the
report names any other role they had. Someone with an account here is added to the team instead.

</Step>
</Steps>

When the run ends, Deplo takes its agent back off the Dokploy machines. Past runs stay under
**History** with their reports.

</Tab>
</Tabs>

## What lands as what

| On Dokploy | Here |
| --- | --- |
| Application built with a Dockerfile | App built from its repository, with that Dockerfile |
| Application built with Nixpacks, Railpack, buildpacks, or static | App built with **Railpack**. A publish directory becomes the **Output directory**, single-page setting included |
| Application from a Docker image | App running that image |
| Compose service | Compose stack |
| PostgreSQL, MySQL, MariaDB, MongoDB, Redis | The same engine, with its data |
| Volumes and directory mounts | Volumes, with their data |
| File mounts | Config files under **Storage** |
| Environment variables | The app's variables, all plain |
| Preview-only variables | The app's preview variables |
| Project and environment variables | Shared variables, linked to the apps that referenced them |
| Domains, with port and path | Domains |
| HTTP basic auth | **Access** |
| Memory and CPU limits | **Resources** |
| Health check, published host ports | **Settings -> Advanced** |
| Schedules | Cron jobs |
| S3 destinations and database backups to S3 | Backup destinations (tested on arrival) and schedules |
| Volume backups | One app backup per schedule, covering every volume |

## What changes on the way

- **Temporary hostnames** (`traefik.me`, `sslip.io`, `nip.io`, `deplo.site`, `localhost`) get a
  new `deplo.site` address, unless the app lands on the same machine. Your own domains come
  across as they are.
- **Connection strings are rewritten** to the database's new host, `db-<name>`. Values an app
  stored itself (a saved `siteurl`) are not: fix them from the app's **Console**.
- **Every variable arrives plain.** Dokploy has no secrets, and Deplo never guesses one from a
  name. Mark them **Secret** under the app's **Environment**.
- **A `${{project.KEY}}` reference** to a variable of the same name becomes a link to that shared
  variable. Otherwise the resolved value arrives, and the report says so.
- **A second service name in one Environment is renamed**: the second `db` becomes `<app>-db`,
  and its `depends_on`, variables and domain follow.
- **A network you created yourself is dropped.** Apps in the same Environment share one network.
- **Security headers stay off** on a moved app's domains. Turn them on under
  [Security headers](/guides/networking/domains-and-https#security-headers-and-cors).
- **Compose middleware labels** come across when their kind is supported, router labels never.
  See [Middlewares in a compose file](/advanced/compose-apps#middlewares-in-a-compose-file).
- **Published ports, host binds, `privileged` and foreign networks or volumes** each need their
  own permission. Without it the report names what stayed behind. A port under 1024 cannot be
  published; use a domain.

## What is left behind

- **LibSQL databases**, named in the report.
- **Deploy keys and connected-source credentials.** Attach a [git connection](/guides/git-providers).
- **Registry passwords.** Add the registry under [Registries](/operations/servers/container-registries).
- **A compose file kept in a git repository.** Dokploy does not return it; paste it in.
- **A custom command on an image app**, and replicas beyond one.
- **A Traefik middleware in an app's own file.** Define it in the proxy here, then add it to the
  domain.

## Backing out

The general rules are in [Migrations](/migrations#stopping-data-and-going-back). For a takeover:

- **Before the ports move:** **Cancel and remove Deplo** starts what the migration stopped, starts
  Dokploy again, removes what Deplo created and uninstalls Deplo. It asks for the API key again.
- **After the ports move:** only the snapshot. If the move itself fails, Deplo puts the ports
  back, starts Dokploy again and offers **Try again** with the reason.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The scan finds nothing | Wrong panel address, or the key belongs to another organization. |
| **Dokploy stopped accepting this API key** | It hit its rate limit or was revoked. Raise or disable the limit under **Settings**, **Profile**, **API/CLI**, then run again. What is already here is skipped. |

Agents, volumes and the takeover: see [Migrations](/migrations#troubleshooting).
