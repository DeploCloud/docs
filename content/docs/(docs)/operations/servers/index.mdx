**Settings -> Servers**, then open a server. Servers belong to the instance, so these pages are for
instance admins; container registries are the exception, being per team.

Every action here goes through that server's agent. The control plane never opens a shell on a host.

A server's page has these tabs:

- **Overview**: CPU, memory, disk and Docker; the **Server agent** card with its version, where its
  update stands, **Retry now** once an update has failed (see
  [Update](/operations/update#retry-an-update-by-hand)) and **Check readiness**; **Display name**;
  **Concurrent deployments**; and **Team access**.
- **Apps**: every app and database on this server, from every team, refreshed every 5 seconds, with
  team, project, status, CPU, memory, restarts and domain. A row links to its app only if you are in
  that team.
- **Certificates**, **Maintenance**, **Cleanup** and **Advanced**: see the pages below.

**Concurrent deployments** defaults to `1`: deploys to one server run one at a time, and the rest wait
in a queue. Raising it past what the machine can take makes every deploy slower, not faster.

## Team access

A new server is open to **All teams**, so any team adding an app can pick it. On the **Team access**
card, **Who can deploy** is **All teams** or **Specific teams**: pick the teams, then **Save
access**. The same choice is in the **Add a server** dialog, where **Specific teams** with none
ticked is refused.

- **Narrowing access moves nothing.** Apps already on the server keep running; only new placements
  are affected.
- **A team only sees the servers it may use** when adding an app.

## Clusters

Several servers can act as one: when one stops, its apps move to another. A cluster is added from
the same **Add** dialog and has its own card on this page. See [Clusters](/operations/clusters).
