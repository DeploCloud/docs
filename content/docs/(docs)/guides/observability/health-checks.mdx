title: Health checks
description: Check that an app is really working, not just running.
---

A running container is not always a working app. A health check asks the app on a schedule and
shows the answer on its status.

| Kind | What it asks | Who asks | Applies |
| --- | --- | --- | --- |
| **HTTP request** | A path, over the server's own network. Under 400 is healthy | Deplo, through the agent | At once |
| **Command** | A shell line inside the container. Exit 0 is healthy | Docker, as a Compose `healthcheck:` | On the next deploy |

**The HTTP check works on any image**: it asks from outside the container, so nothing needs to
be installed inside.

<Callout type="info">
  An HTTP health check never changes routing. An unhealthy app keeps serving, so you see the
  problem instead of losing the app. With
  [zero-downtime deploys](/concepts/what-happens-on-a-deploy#zero-downtime-deploys) on, the proxy
  sends traffic only to a container whose check passes.
</Callout>

## Turn one on

<Steps>
<Step>

### Open the app's Advanced settings

Open the app, then **Settings -> Advanced**, and turn on **Health check**.

</Step>
<Step>

### Pick the kind and fill it in

- **HTTP request**: the **Path** (`/healthz`, or `/`), and a **Port** only if the check answers
  on a port other than the app's own.
- **Command**: anything that exits 0 when things are fine, such as `pg_isready -U app` or
  `test -f /tmp/ready`. Pipes and fallbacks work.

</Step>
<Step>

### Set the timings, then Save

All optional:

| Field | What it means | Default |
| --- | --- | --- |
| **Interval** | Seconds between checks | 30 |
| **Timeout** | Seconds one check may take. Must be shorter than the interval | 5 |
| **Retries** | Failures in a row before the app is unhealthy | 3 |
| **Start period** | Seconds of grace while the app boots, when a failure does not count | 10 |

</Step>
</Steps>

## Reading the result

The answer shows on the app's status badge and in the container breakdown on
[Monitoring](/guides/observability/monitoring).

- **Healthy**: the last answer was good, or the failures so far are under **Retries**. One good
  answer resets the count.
- **Unhealthy**: **Retries** failures in a row. Running, but not working.
- **Starting**: inside the start period, so a failure means the app is still booting.

<Callout type="warn">
  **Error is not unhealthy.** Error means the last deploy failed. An app can be Error and healthy
  at once, because the previous version is still serving.
</Callout>

## Good to know

- **HTTP results live in the panel's memory.** Restarting Deplo clears them; the next check
  starts again.
- **A stopped app has no result.** There is nothing to ask.
- **A failed check sends no alert.** **App keeps restarting** fires on a restart loop, not on a
  check. See [Notifications and alerts](/guides/observability/notifications-and-alerts).
- **A database's health check is the engine's own**, written by Deplo. It is not editable.
