API keys, database URLs, feature flags, `NODE_ENV`. Deplo stores them encrypted, injects them at
build time and at run time, and never shows a secret back.

## The four layers

When the same name is defined in more than one layer, the highest layer wins:

1. **Instance-wide variables**, set by an instance admin for every team and app.
2. **The app's own variables.**
3. **A shared variable** linked to the app.
4. **A preview override**, on previews only.

## Plain and secret

<Tabs items={['Plain', 'Secret']}>
<Tab value="Plain">

Stored and shown back to you. Can be edited, and can be changed to secret at any time.

</Tab>
<Tab value="Secret">

- **Write-only.** Never shown again, in the API or in the panel.
- **Cannot be edited.** To change it, delete it and add it again.

</Tab>
</Tabs>

A `plain` variable can become `secret`. The other direction is not allowed.

**Deplo warns when a name looks like a credential.** A plain `PAYLOAD_SECRET`, `S3_ACCESS_KEY_ID`
or `DB_PASSWORD` gets a **Secret?** badge. It is only a suggestion. Names containing `PUBLIC`,
`FILE` or `VERSION` are not flagged.

**Build time and run time get the same variables.** So `NEXT_PUBLIC_*` or `VITE_*` work with no
extra setting. Docker keeps build arguments in the image history, so anyone with Docker access to
the build server can read them.

## Preview overrides

Once [pull request previews](/guides/networking/pull-request-previews) are enabled, the app's
**Environment** page gets a **Preview overrides** section. A variable set there is used in previews
only, and wins over every other layer. Typical use: point previews at a test database.

<Callout type="warn" title="A preview built from a fork inherits nothing">
For security reasons, a fork preview gets only the preview overrides. If your app needs
`DATABASE_URL` to start, set it there.
</Callout>

## Good to know

- **Nothing applies until the next deploy.**
- **A secret cannot be edited, only replaced.**
- **`reveal_secrets` does not reveal secret variables.** It unmasks basic-auth passwords, backup
  recovery keys, database connection strings and deploy hook URLs. Nothing unmasks a secret
  variable.
- **Names are not checked.** A typo becomes a missing variable at run time.
- **A shared variable's scope does not inject it.** Only the per-app link does. See
  [Shared variables](/guides/config/shared-variables).
- **Compose apps get the variables in every service.**

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The app cannot see a variable | It was added after the last deploy. Redeploy. |
| The value is right in Deplo and wrong in the app | A higher layer defines the same name. Check the app's own variables, then its linked shared variables. |
| A build-time variable is empty in the browser bundle | The framework only inlines prefixed names (`NEXT_PUBLIC_`, `VITE_`). |
| A fork preview starts with no configuration | Expected. Set what it needs as a preview override. |

More in [Deploys and builds](/troubleshooting/deploys-and-builds).
