A **server** is a machine you own that Deplo deploys to. It becomes one by running a small
program, the **server agent**, the only part of Deplo that runs Docker.

Servers belong to the instance, not to a team: one server can serve several teams, and one team
can use several servers. Which teams may deploy to a server is a setting on the server.

## How a server joins

The control plane never connects to your machine. Your machine connects to it.

<Steps>
<Step>
### Get an install command

In **Settings -> Servers**, click **Add**, name the server and pick its role. Deplo shows an
install command with a **one-time token** that expires after about an hour.
</Step>
<Step>
### Run it on the server

The command installs Docker and git if missing, downloads the agent, checks its SHA-256, and
starts it as a systemd service. git matters: the agent clones on the server, so without it a
server cannot build from a repository.
</Step>
<Step>
### The agent gets its certificate

The agent creates its own private key and sends a certificate request with the token. The
control plane signs it and **pins its fingerprint**: from now on only that certificate is
trusted, and the server turns **Online**.
</Step>
</Steps>

## How Deplo reaches a server

The agent keeps one encrypted connection (mutual TLS) open to the panel's address. Every deploy,
log, console session and backup rides it.

- **No port to open on the server.** It works behind a home or office router, on a company
  network, or on a cloud server with a closed firewall.
- **Connected or offline.** When the connection drops, the agent reconnects within seconds.
- **Servers follow the panel.** Change the panel's domain and every connected server learns it.
  An agent installed by an older Deplo closes its old port once it has connected.

**Every server agent must be `0.5.1-canary.10` or later**, the first that connects this way. An
older one cannot reach Deplo, and Deplo cannot reach it to update it: the server is **unusable**
until its agent is
[reinstalled](/troubleshooting/servers-and-agents#a-server-agent-needs-to-be-reinstalled). Its
apps keep running, and its apps and settings stay in Deplo.

## What a server can be used for

You pick the role in the **Add** dialog: **Everything**, **Build** or **Backups**. The
[migration wizard](/migrations) creates a fourth, migration-only kind. See
[Server roles](/advanced/server-roles) for the comparison.

## Health is not readiness

**Health** answers "can Deplo reach and trust this agent right now?". It comes from the last
contact:

<TypeTable
  type={{
    provisioning: {
      description: "No agent has contacted the control plane yet",
      type: "string",
    },
    online: {
      description: "The agent answered and Docker is reachable",
      type: "string",
    },
    warning: {
      description: "The agent answered, but Docker did not, so nothing can deploy there",
      type: "string",
    },
    error: {
      description: "Something answered, but the agent is wrong: untrusted or expired certificate, unsupported version, or an application error",
      type: "string",
    },
    offline: {
      description: "Not connected for about 10 seconds. Usually the machine is off or has lost its internet connection",
      type: "string",
    },
  }}
/>

When the last contact is too old, the Servers page shows **Unknown**. A deploy never relies on
the stored value: it contacts the agent at that moment.

**Readiness** answers "is this server set up well enough to deploy apps to?". Run it live with
**Check readiness** on the server's page. Rows are grouped as agent, docker, routing, capacity,
build methods and Deplo configuration, each `pass`, `info`, `warn`, `fail` or `skip`. **`skip`
means it could not be checked**, which is not a pass.

## The Deplo host is a server too

The machine running the control plane adds itself during installation and deploys through the
same path as any remote server. Its agent connects over the machine itself, so it keeps working
even when the panel's public address does not. It is the one server that cannot be removed.

## Removing a server

Removal is **refused while anything still uses the machine**: an app, a managed database, or a
backup destination on its disk. Each refusal names what is in the way.

Removing a server **deletes the pinned certificate**, so Deplo never talks to it again. Nothing
is uninstalled from the machine: Deplo shows a one-line command to remove the agent, its
Traefik and its data. A migration source is the exception: Deplo uninstalls itself from it once
you are done.

## Two behaviours to know

- **Deploy concurrency.** Each server runs `1` deploy at a time by default; other servers work in
  parallel, and two deploys of the same app never overlap.
- **Pending teardowns.** When a server does not confirm removing a stack, Deplo retries up to
  eight times, from one minute to a day apart. If it gives up, it writes an activity entry and
  raises the **Leftover containers** alert.
