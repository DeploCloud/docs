title: Private network

<Callout type="info" title="Beta">
This feature is currently beta/experimental and subject to change. It is
not recommended for production. Try it out and share your feedback on
[our GitHub](https://github.com/DeploCloud/deplo/issues).
</Callout>

<Callout type="info" title="Experiment">
An instance admin turns them on for every team in [Settings -> Deplo -> Experiments](/operations/experiments).
Until then, clusters stay hidden.
</Callout>

The servers of a [cluster](/operations/clusters) share a **private network**. Deplo sets it up the
moment a server joins, and you configure nothing:

- **Every app reaches its environment's apps and databases by name, on whichever server they run.**
  The same names and ports as on one server: `db-shop`, `deplo-web`, or a Compose service's own
  name like `api` or `redis`.
- **It stays up while Deplo or the cluster's leader is down.** The servers talk to each other
  directly; only adding or removing a server waits for Deplo.
- **It is encrypted end to end** and only the cluster's own servers are on it.

## What reaches what [#what-reaches-what]

| From an app on server-a | To, in the same environment, on server-b | Reachable |
| --- | --- | --- |
| Any app | A database, as `db-shop` | Yes |
| Any app | A single-image app, as `deplo-web` | Yes |
| Any app | A service of a Compose app, as `api` (or its `hostname`) | Yes |
| Any app | Any of those, **on any TCP port** it listens on | Yes |
| Any app | Anything of another environment, team or cluster | No |

Nothing changes in your code after a move or a failover: the name follows the app to its new
server.

<Callout type="info" title="TCP only">
Names carry TCP connections, which is what HTTP, databases, Redis and queues use. UDP between
two servers is not carried.
</Callout>

Two Compose apps of one environment that both have a service called `redis` share that name, as
they would on one server: the deploy warns about it. Across servers, the other server reaches
one of them. Give the services different names to be sure which one answers.

## Direct or relayed [#direct-or-relayed]

Each pair of servers connects **directly** when it can: on the same office network, on public
addresses, and through most home routers. When two servers cannot reach each other at all, their
traffic goes through **Deplo's relay** instead. It still works, with a little more delay.

The server's card in the cluster says when that happens:

| On the card | What it means |
| --- | --- |
| Nothing | It reaches every other server of the cluster directly |
| **Relayed** | "Reaches eu-2 through Deplo's relay, with more delay" |
| **Can't reach a server** | "Cannot reach eu-2 now": both are online, yet nothing gets through |

A pair switches between direct and relayed on its own, without dropping open connections. A
relayed pair needs Deplo's machine to be up; a direct one does not.

<Callout type="info" title="Making a relayed pair direct">
Servers connect directly over UDP port **51820**. When a firewall between two servers blocks it,
let UDP 51820 through between them and the card clears within a few minutes. Nothing else needs
opening, and the port answers no one who is not a server of the cluster.
</Callout>

## Servers that need the relay [#servers-that-need-the-relay]

**A server that needs the relay is never refused.** Deplo says what it costs, in two levels:

| Level | When | What you see |
| --- | --- | --- |
| One server or a few | Without the relayed pairs, more than half of the servers still reach each other directly | A warning icon on each server outside that group, on its row and its page (**Needs Deplo's relay**). Nothing on the cluster |
| The whole cluster | No such majority is left | The cluster itself: **Not OK for production** |

The icon says: "eu-3 reaches some servers of its cluster only through Deplo's relay. If Deplo's
machine stops, eu-3 stops as if its power were cut." Its apps then move to the others, as for a
server that stopped.

The cluster's warning says: "Fewer than half of this cluster's servers reach each other directly:
the rest only through Deplo's relay. If Deplo's machine stops, every App and database of this
cluster stops. To fix it, give the servers a direct path to each other, or a second relay on
another network."

- **Add server** shows the same warning before you add anything.
- **Activity**, by Deplo: `Cluster eu is not OK for production: fewer than half of its servers
  reach each other directly, so if Deplo's machine stops, every App and database of it stops`, and
  `Cluster eu is OK for production again` once the pairs are direct.
- **The leader and the servers next in line** are always picked among the servers that reach each
  other directly. See [The line of succession](/operations/clusters/leader#the-line-of-succession).

To clear a warning, make the pairs direct (below). Both go on their own within a few minutes.

## The database page [#the-database-page]

A database whose apps run on another server says so only when that pair is relayed: "web reaches
this database through Deplo's relay. It is faster on the same server."

## Give a server a new key [#give-a-server-a-new-key]

Each server has its own key on the private network. When a key may have been seen by someone else,
an instance admin gives that server a new one over the API:

```graphql
mutation {
  rotateClusterNetworkKey(serverId: "srv_8f910cc44a95585b")
}
```

- **Nothing goes down.** The server makes its next key, the other servers of its cluster learn it,
  then it switches. Every tunnel stays up and every pair stays direct.
- **It answers `true`** once the switch is done. Run it again at any time: each run gives a new key.

## Older servers [#older-servers]

A server whose agent is too old for the private network stays off it, and its traffic goes
through Deplo's relay as before. Deplo updates every agent on its own. Until then, a Compose app's
services on that server are reachable by name from its own server only.

## Over the API

`ClusterMember.network { relayed unreachable }` lists the servers a member reaches only through the
relay, or not at all, and `ClusterMember.relayWarning` is the icon's sentence. Over MCP,
`get_cluster` returns the same fields for each server.
