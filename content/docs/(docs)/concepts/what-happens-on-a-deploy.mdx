One deploy, from the trigger to a running container: the steps behind most error messages.

<Steps>
<Step>
### Something triggers it

| Trigger | Comes from |
| --- | --- |
| **Deploy** or **Redeploy** in the dashboard | A person |
| A push to the tracked branch, or a new tag | The git provider's webhook |
| A `POST` to the app's deploy hook URL | CI, a script, a provider Deplo cannot register a webhook with |
| A pull request opened or updated | [Previews](/guides/networking/pull-request-previews), if they are on |
| The MCP server or the GraphQL API | A token with `deploy_apps` |

**Watch paths** skip an automatic deploy when the push touched nothing under them. A manual
redeploy always runs.
</Step>

<Step>
### It waits for a slot

Each server runs `1` deploy at a time by default, so deploys to one machine queue while other
servers work in parallel. Two deploys of the same app never overlap. A queued deploy shows its
position in the build log. An app built on a [build server](/advanced/build-servers) waits for a
slot on **that** machine.
</Step>

<Step>
### The agent fetches the source

The control plane hands the job, decrypted credentials included, to the agent on the target
server. A **Git** source is cloned with the git connection's token (submodules too, if asked, from
the same git server only). An **Upload** uses your archive. **Docker image** and **Compose** skip
this step.
</Step>

<Step>
### The build method is picked

On **Automatic**, the default, Deplo looks in the root directory on every deploy: a `Dockerfile`
is built, else a Compose file is deployed as a stack, else Railpack builds the app. The log says
which one ran. A method you picked yourself is used as it is.

Under Railpack, Deplo also recognises the framework from `package.json` and the root config on
every deploy, and shows it on the app. Railpack works out the install, build and start commands
unless you typed your own.
</Step>

<Step>
### The image is built

**Railpack** makes a build plan from the detected language and framework, **Dockerfile** builds
your `Dockerfile` (optionally one stage), **Compose** builds the services of your Compose file.

One build step may use about 75% of the server's memory. Past that the build stops and says so,
and the apps already running there keep theirs. Every environment variable is available during
the build too, so values like `NEXT_PUBLIC_*` work.

The image stays on that server: Deplo pushes to no registry. Build output streams live, survives a
page reload or a control plane restart, and is capped at 20,000 lines of 4,000 characters.
</Step>

<Step>
### The environment is resolved

Four layers, lowest priority first:

1. **Shared variables injected everywhere** (owned by the instance or reaching several teams)
2. **The app's own variables**
3. **A shared variable the app has linked**
4. **A preview override** (previews only)

The highest layer that defines a name wins. A preview built from a **fork** gets only the plain
preview overrides, never the app's own values.
</Step>

<Step>
### The stack is rendered

On the control plane, never on the server:

- **The Compose file:** one service for a single-image app, or your stack with Deplo's entries.
- **The Traefik labels:** one route per domain; path routes win over whole-host ones, longest
  first.
- **The port, the volumes, the resource limits and the mounts.**

The agent receives finished YAML: no routing logic lives on the server.
</Step>

<Step>
### The agent starts it

The agent writes the stack and a private environment file next to it, then runs Compose. The
containers join the app's **Environment network** (`deplo-env-<id>`), the team's
`deplo-team-<id>` when the app is in no Environment, or `deplo-preview-<key>` for a preview. Traefik
sees the new labels and starts routing.
</Step>

<Step>
### It checks that the app runs

A deploy is ready only when the app really runs:

- **It stays up** for 10 seconds after it starts: no exit, no restart.
- **An app with a domain answers on its port.** An app with none only has to stay up, so a
  background worker deploys fine.
- **A slow starter gets up to 3 minutes.**

A crash, a restart loop, or an app that never listens (or listens only on `127.0.0.1`) fails the
deploy; the log says why and shows the app's last lines. If it listens on another port, for
example `8080` instead of `3000`, Deplo routes to `8080`, saves it as the app's port and says so.
See [The port is the one people get wrong](/guides/releases/build-settings#the-port-is-the-one-people-get-wrong).
</Step>

<Step>
### The result is recorded

The deployment gets its final status, image, duration and logs. The app's status becomes
`active`, or `error` if the build or the start failed.

Images older than the app's **rollbacks kept** setting (default `3`) can be removed by the
server's disk cleanup, and a removed image is gone. An app from a repository can still roll back
by rebuilding that commit.
</Step>

<Step>
### A picture is taken

Once the deployment is live, the app's server opens it in a private browser and takes a picture
in light and dark. It becomes the cover of the **Production Deployment** card and of the
deployment's page.

- **Cookie banners** are dismissed with **Reject** for the consent tools Deplo knows. For any
  other, hover the cover and use **Retake screenshot**.
- **Ads and analytics** are not loaded, so the picture never counts as a visit.
- **Basic auth**: Deplo signs in with the app's credentials, never for a fork's pull request.
- **No picture** when the page errors, stays blank, or the app has no domain. Deplo retries once a
  minute later, then waits for the next deploy.
- **No private network**: the browser goes out only through the server, which refuses private
  addresses.

Turn it off in **Settings -> Advanced -> Deployment screenshots**, which also deletes the saved
ones.
</Step>
</Steps>

## What a deploy does not do

- **It does not touch your data or identity.** Volumes are reattached, never recreated; the slug
  and volume names stay.
- **It does not roll back on failure.** A failed build leaves the previous version running. An
  app that fails the start check has already replaced it: [roll back](/guides/releases/rollbacks)
  to the last version that worked. See
  [App status](/concepts/apps-projects-and-environments#app-status-is-intent-not-observation).

## A rollback is much shorter

Steps 3 to 5 are skipped: no fetch, no build. Deplo runs an existing image again with the
**current** configuration, so the code goes back while the variables, domains, volumes and limits
do not. It is recorded as a real deployment with its own logs.
