Deplo reads the packages inside every image it runs for your team and checks them
against public lists of known security flaws. When there is something you can fix,
the app says so, and tells you what to do.

Nothing to set up: it is on for every team.

## What you see

- **A banner on the app's Overview**: "2 security updates available". It appears only
  when there is something critical to apply, and disappears once it is fixed.
- **A shield on the app's card**, next to its status dot. Hover it for the count.
- **A notice at the top of the Overview** naming every app and database that needs updates, red
  when one of them runs something already used in attacks. **Show these apps** filters the grid
  to them.
- **A notice at the top right**, next to your avatar, on every page. Click it for the list, or
  **Dismiss** it: it comes back only when something new needs updating.
- **Details**: every update, with what to do. Also in the app's menu (the three dots at the top right ->
  **Security updates**), where it says "Up to date" when there is nothing. Each advisory shows its
  scores and the advisory's own summary, which often names the condition it needs; click it to read
  it on OSV.dev.
- **Checking the new deploy**: right after a deploy, Details says so while the new image is read,
  and the previous image's updates are left out. It takes about a minute.

Managed databases get the same banner and shield on **Storage**. Pull request previews
get the shield on their row.

One security update is one package of your app's to move, or one image to update. If a package
has 25 known flaws and one new version fixes them all, that is one update. An image with ten
flawed packages and a newer build that fixes them is one update too.

## How serious it is

| Level | What it means |
| --- | --- |
| **Used in attacks** | The flaw is on CISA's list of flaws already exploited in real attacks |
| **Critical** | A critical flaw (score 9.0 or more) |
| **Important** | A high-severity flaw (score 7.0 to 8.9) |

Only **Used in attacks** and **Critical** count in the badge, the notices and the alerts.
**Important** ones are listed in **Details** under **Less urgent**. Lower levels are not shown.

Next to each advisory, **EPSS** is the chance it is exploited in the next 30 days, as
[FIRST](https://www.first.org/epss/) estimates it: a high score is worth looking at first.

## How to fix it

Each update says how you get the fix:

| What Details says | What to do |
| --- | --- |
| Update minimist to 1.2.6 in your code | Bump the dependency in your repository and push |
| A newer build of this image fixes 3 known flaws: update to get it | Press **Update** on the banner. An app redeploys and pulls its image again; a database asks first, then restarts on the new build with its data |
| Version 1.60.2 is available and fixes 2 known flaws | Change the image version in **Settings -> Deployments** |

Deplo offers **Update** only after reading the newer build: the image's server downloads it,
reads its packages like any other image, and removes it again. A newer build that still has the
flaw is listed under **Waiting on the image's maintainers**, never counted; while it is being
read, Details says Deplo is checking it.

## What is checked

Deplo shows only what you chose:

- **An app Deplo builds from your code**: the dependencies your code installs, such as the
  packages in `package.json` or `requirements.txt`.
- **An image you deploy as it is** (a database, a template, a Compose service with `image:`):
  the software the image ships, when a newer build or version of that image exists.

It leaves out what you never picked: the system packages under your app (glibc, openssl), the
runtime Deplo builds with, tools a dependency carries inside it, and flaws nobody has fixed yet.
Those come up to date with Deplo updates and new builds of the images.

Every kind of app is checked:

- Apps of every source: from git, an upload, a Docker image, a Compose file or a template.
- Managed databases.
- Stopped apps and databases, from the image they will start with.
- Pull request previews.

Deplo's own components are not listed here: their fixes come with Deplo updates.

## When it is checked

- **After a deploy**: the new image is checked as soon as the deploy is live, usually within a
  minute.
- **Every 6 hours**: every image is matched again against the latest lists, because new
  flaws are found in software that has not changed.
- **Every day**: Deplo refreshes CISA's list of flaws used in attacks.

## Alerts

**Security update available** is on by default in every channel. It fires:

- once per update, never again for the same one;
- only for running apps and databases, never for a stopped app or a preview;
- only for **Used in attacks** and **Critical** updates.

## What Deplo sends

To match an image, Deplo sends [OSV.dev](https://osv.dev) the name and version of each
package it checks, for example `npm minimist 1.2.5`. System packages are never sent, since they
are never shown. Nothing else: no app name, no server, no domain, nothing that names this Deplo.

Once a day it also sends [FIRST](https://www.first.org/epss/) the CVE ids behind your updates
(for example `CVE-2021-44906`), to read their EPSS scores, and nothing more.

Three more downloads happen, all read-only:

- CISA's public list of exploited flaws, once a day, by the Deplo panel.
- The package reader the servers use, once per server, from its official release, with
  its checksum verified.
- A newer build of an image you run, by its own server from the image's registry, to see
  whether it has the fix before Update is offered. It is removed again afterwards.

Package names from a private registry, such as an internal npm scope, are sent like any
other name.

## Ignore an update

Sometimes a team decides not to apply one: the flaw is not reachable, or the fix comes with the
next release. In **Details**, press **Ignore** on the update, write why, and pick 30, 90 or 180
days.

- It moves to **Ignored**, stops counting and never alerts until then.
- **Activity** records who ignored it, until when, and why.
- When the time is up it counts again. A **new** flaw in the same package shows right away.
- **Stop ignoring** brings it back at once.

Ignoring needs the **Ignore security updates** capability. Team owners have it; give it to a role
in **Settings -> Roles**.

## When an image cannot be checked

Details says why:

| Message | What happened |
| --- | --- |
| An image is too large to check on its server | Reading it needed more memory than Deplo allows itself on that server |
| Its server is too low on disk space | Deplo needs about twice the image size free to read it |
| Its server is too low on memory | Deplo waits until enough memory is free |
| Its server cannot check images yet | The server cannot cap the reader's memory, so Deplo does not run it there |

Your apps are never at risk: Deplo reads one image at a time per server, never during a
deploy, at the lowest priority.

## Turn it off

An instance admin can turn checks off for the whole instance:

<Steps>
<Step>

### Open Deplo settings

Go to **Settings -> Deplo -> Advanced**.

</Step>
<Step>

### Flip Security updates

Under **Privacy**, turn **Security updates** off. Nothing is checked and nothing is sent
from that moment. The line under the switch shows when the last check ran, or since when
OSV.dev could not be reached.

</Step>
</Steps>
