API keys, database URLs, feature flags, `NODE_ENV`. Deplo stores them encrypted and injects them
at build time and at run time.

## The four layers

When a name is set in more than one layer, the highest one wins:

1. **A shared variable added automatically**: one shared with two or more teams, or an
   instance-wide one. It shows on the app, read-only.
2. **The app's own variables.**
3. **A [shared variable](/guides/config/shared-variables)** the app has linked.
4. **A preview override**, on previews only.

## Plain and secret

| | Plain | Secret |
| --- | --- | --- |
| Shown again | Yes | Never, in the panel or the API |
| Edit or rename | Yes | No: delete it and add it again |
| Change the type | To secret: **Edit**, or **Make Secret** on selected rows | Never back to plain |

**A plain name that looks like a credential gets a warning icon**: `DB_PASSWORD`, `API_TOKEN`,
`S3_ACCESS_KEY_ID`. A name holding `PUBLIC`, `FILE` or `VERSION` is not flagged.

## Build time

A Railpack build gets every variable, so `NEXT_PUBLIC_*` and `VITE_*` work as they are. Two limits:

- **A Dockerfile build sees only the names it declares**, like `ARG NEXT_PUBLIC_API_URL`. Docker
  keeps build arguments in the image history, readable with Docker access to the build server.
- **Names that configure the build host never reach it:** `PATH`, `HOME`, and `DOCKER_*`,
  `BUILDKIT_*`, `BUILDX_*`, `COMPOSE_*`, `LD_*`, `XDG_*`, among others.

## Preview overrides

With [pull request previews](/guides/networking/pull-request-previews) on, the app's
**Environment** page gets a collapsed **Preview overrides** section: values used by previews only,
above every other layer. Typical use: point previews at a test database.

<Callout type="warn" title="A preview built from a fork inherits nothing">
For security reasons it gets only the plain preview overrides. If your app needs `DATABASE_URL` to
start, set it there as plain.
</Callout>

## Good to know

- **No secret variable can be revealed**, not even with `reveal_secrets`. That capability covers
  database connection strings, backup recovery keys and app backup downloads.
- **Deplo does not know which names your app reads.** A typo is a missing variable at run time.
- **Compose apps get the variables in every service.** A key the compose file sets itself keeps
  the compose value.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The app cannot see a variable | It was added after the last deploy. Redeploy. |
| The value is right in Deplo and wrong in the app | A higher layer sets the same name: a linked shared variable, a preview override, or the compose file. |
| A build-time variable is empty in the browser bundle | The framework only inlines prefixed names (`NEXT_PUBLIC_`, `VITE_`). With a Dockerfile, declare it with `ARG`. |

More in [Deploys and builds](/troubleshooting/deploys-and-builds).
