title: Authentication
description: Session cookie, API token or OAuth access token. All three resolve to one identity acting in one team.

Three credentials, one model: every request resolves to a **principal** (a person or a token) acting in **one team**, and every query and mutation is filtered to that team.

<Tabs items={['API token', 'Session cookie', 'OAuth access token']}>
<Tab value="API token">

**For CI, scripts and your own tooling.** Create one under **Settings -> API tokens**. It is shown once. Send it as a bearer token:

```bash
curl https://<deplo>/api/graphql \
  -H "Authorization: Bearer deplo_xxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -H "X-Deplo-Team: acme" \
  -d '{"query":"{ viewerTeam { slug } apps { slug status } }"}'
```

**Picking the team.** `X-Deplo-Team` takes a team id or slug. Without it, the first team in the token's scope is used. A team the token does not hold is ignored, not honoured. `myTeams` lists the ones it may switch between.

**What it can do.** The capabilities chosen at creation, capped by what its owner can still do in that team. A token that names no capabilities is view-only. The full lifecycle is on [API tokens](/api-reference/api-tokens).

**What it can never do.** A token is a principal of its own, never a stand-in for the person who minted it. Every personal-account operation on [Account](/api-reference/account) answers `An API token can't access <that resource>`, whatever the token holds.

</Tab>
<Tab value="Session cookie">

**The browser.** The dashboard calls the API same-origin and the session cookie (`deplo.session_token`, `__Secure-` prefixed over HTTPS) goes along automatically. The active team comes from the `deplo_team` cookie, set by `switchTeam`.

The cookie is minted by the sign-in mutations on [Account](/api-reference/account): `login` (then `verifyTwoFactorLogin` when the account has two-factor on) or `passkeyChallenge` + `verifyPasskeyLogin`.

A session is what the REST byte streams (upload, logs, console, backup download) accept. They do not take a bearer token.

</Tab>
<Tab value="OAuth access token">

**Web AI clients.** A hosted client (Claude, ChatGPT) cannot be handed a token, so Deplo is also an OAuth 2.1 authorization server. The client registers itself (RFC 7591), the user approves a consent screen, and that approval mints an ordinary API token. The `dplo_at_` access token the client then sends points at that token, so everything on the API token tab applies unchanged: same capabilities, same cap, same revocation.

```bash
curl https://<deplo>/api/graphql \
  -H "Authorization: Bearer dplo_at_xxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"query":"{ me { username } }"}'
```

Discovery starts from the MCP endpoint's `401`, which carries `WWW-Authenticate: Bearer resource_metadata="<url>"`. The documents are `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`.

The team is fixed at consent time: `X-Deplo-Team` cannot move a connection. One consent can grant several teams. Connections are listed and revoked under **Settings -> MCP Server**, and `revokeToken` on the minted token ends the credential everywhere it reached.

</Tab>
</Tabs>

## Unauthenticated requests

`me` resolves to `null`. Anything else that needs a login fails with `Not authorized to resolve <field>`. The only public operations are the sign-in and registration mutations, listed as such on their pages.

## Gates

Every operation in this reference states who may call it, in one of four forms:

| Line | Meaning |
| --- | --- |
| Needs `deploy_apps` | The principal must hold that [capability](/reference/capabilities) in the active team. Some add "or instance admin". |
| Instance admin only | A global instance admin. For a token, instance admin is opt-in per token, never inherited from its owner. |
| Any signed-in principal | A session or a token, any capabilities. |
| Public, no authentication | Sign-in and registration. |

A capability gate is the same one the dashboard button behind it uses. A token or a role narrowed to part of a team (a folder, a project, an app) is refused by team-wide operations in that team, members and roles included.
