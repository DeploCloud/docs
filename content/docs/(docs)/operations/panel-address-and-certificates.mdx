title: The panel's own address
description: Change the panel address, certificate, and backup address safely.
---

**Settings -> Deplo -> General**, instance admins only.

The panel answers on two addresses, over **HTTPS**:

- **Your domain**, when you gave one, with a Let's Encrypt certificate.
- **The backup address**, generated like `deplo-cb00710a.deplo.site`. It needs no DNS and keeps
  working when your domain breaks. On by default.

Port `3000` on the machine is bound to `127.0.0.1` only, so `http://203.0.113.10:3000` never answers.

## Change the address

<Steps>
<Step>
### Point DNS at this server
Point the new hostname at this server first. The **Panel address** card shows the record to create,
and whether it resolves here yet.
</Step>

<Step>
### Enter the new address and save
In **Panel address**, type the hostname, like `deplo.example.com`, and press **Save**. An IP address
is refused: no certificate authority issues for one.
</Step>

<Step>
### Read the impact, then confirm
**Move the panel to deplo.example.com?** lists what breaks, each as **Critical**, **Fix by hand** or
**Minor**:

- passkeys stop working: everyone registers a new one
- deploy hooks and invite links keep the old address: copy them again
- browser notification subscriptions stop: each person turns them back on
- connected AI clients must reconnect
- every sign-in ends, yours included

Press **Change address**. The certificate issues on the first request to the new address.
</Step>
</Steps>

The backup address keeps working throughout. Your servers learn the new address by themselves; one
that was off finds the panel again through the backup address (see
[A server was off while the panel's address changed](/troubleshooting/servers-and-agents#a-server-was-off-while-the-panels-address-changed)).
New install commands and git webhooks use the new address; re-point existing webhooks.

Behind a home or office router, where this server is not reachable from the internet, serve the panel through a
[Cloudflare Tunnel](/operations/cloudflare-tunnel) instead. While it is on, the address is changed
from the tunnel's setting.

## HTTPS is not optional

There is one exception: **Settings -> Deplo -> Advanced -> HTTPS**, for a panel on an internal network
where no certificate can be issued. Turning it off sends every password and session cookie across the
network in clear, passkeys stop working, and browsers that loaded the panel over https refuse plain
http there for months. The confirmation says so.

## Turn the backup address off

**Settings -> Deplo -> Advanced -> Backup address**, only if you don't want the generated public
hostname. Your domain is then the only route to the panel; your servers forget the backup address,
and learn it again when you turn it back on.

<Callout type="info" title="It can't be turned off while it IS the address">
On an instance with no domain of its own, the generated host is what the panel answers on: Deplo
refuses until you set a domain.
</Callout>

If the domain breaks, restore the address from the machine Deplo runs on, then restart so Deplo makes
the move:

```bash
deplo recover panel-address -                 # back to the generated address, backup address on
deplo recover panel-address deplo.example.com # or straight onto a domain that works
deplo restart
```

See [Break-glass recovery](/operations/break-glass-recovery).

<Callout type="info" title="The generated address gets a real certificate too">
Let's Encrypt issues for it when the server is reachable on port 80 from the internet. Behind NAT or
a firewall, the browser gets Deplo's self-signed certificate instead and warns once.
</Callout>

## The certificate account email

The **Certificates** card holds the address Let's Encrypt uses for the ACME account and its expiry and
revocation notices, on every server. The installer seeds it from `ACME_EMAIL`, or uses
`admin@<panel-host>`. Changing it restarts the proxy on every server: sites blink for a few seconds.

## Troubleshooting

A certificate warning on the new address, a panel unreachable after the change, or "No server accepted
the change": see [Domains and TLS troubleshooting](/troubleshooting/domains-and-tls).
