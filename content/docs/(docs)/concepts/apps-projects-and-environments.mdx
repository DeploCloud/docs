An **App** is the thing that runs. A **Folder** groups apps. A **Project** is a folder with
environments. An **Environment** is one isolated copy of a project's apps. None of it is
required: a flat list of apps is a normal setup.

<HierarchyDiagram />

## App

The unit you deploy: a repository, an image, an archive or a Compose file, run as a Docker stack
named `deplo-<slug>` behind Traefik. It owns its source, build settings, domains, variables,
volumes and deployment history, and lives in one place only: the team's top level, a Folder, or
one Environment of one Project.

The **slug** is set from the name at creation and never changes: it names the stack, the volumes
(`deplo-<slug>-<volume>`) and the generated hostname. The display name can change.

### App status is intent, not observation

The status is the last thing Deplo was **asked** to do: `queued`, `building`, `starting`,
`active`, `error`, `stopping`, `idle` or `restoring`. The interface shows `active` as
**Online** or **Running**, `idle` as **Stopped**, and an app never deployed as **Not deployed**.

- **`error` means the last deploy failed**, not that the app is down. The previous version keeps
  running.
- **Live state is added on top** of `active`: an app whose containers are restarting, failing
  their health check or gone shows **Restarting**, **Unhealthy** or **Not running**.

## Folder

A team-wide group with a name, a colour and an owner. Folders can nest, and are how you
delegate: share one with a member and their permissions **inside it** can exceed their team role.
See [Access inside one folder](/concepts/teams-and-capabilities#access-inside-one-folder).

## Project

**A folder whose apps are split per environment.** It has an owner, a colour and an order like a
folder, plus Environments, each with its own apps and shared variables.

- **A Project never nests** in another Project, and **Folders never live inside one**.
- **A Project has no page of its own.** You browse it on the Overview, at
  `/?project=<id>&env=<envId>`. Old `/projects/<slug>` links redirect there.

## Environment

An isolated deploy target inside a Project: its own containers, URLs, git branch and variables.
A new Project starts with **Development**, **Preview** and **Production**, all renamable, and holds
up to ten. Names like `pr-12` are reserved for pull request previews.

- **It is a network boundary.** Apps and managed databases in the same Environment, on the same
  server, reach each other by name. Nothing else reaches them: not other environments, projects
  or teams. Apps outside any project share their team's network. See
  [Network isolation](/advanced/network-isolation).
- **It is a scope of a [shared variable](/guides/config/shared-variables).** A variable scoped to
  an environment is *suggested* to its apps; each app still links it on purpose.

## Which one do I want

| Situation | Use |
| --- | --- |
| A handful of apps, one of everything | Nothing. Leave them at the top level. |
| "These six apps belong to the marketing site" | A **Folder** |
| "Sara should manage those six and nothing else" | A **Folder**, shared with her |
| "Staging and production of the same three apps" | A **Project** with two **Environments** |
| "Every pull request should get its own copy" | [Pull request previews](/guides/networking/pull-request-previews) |

A pull request preview is neither an App nor an Environment: a temporary stack with no domains,
console, backups or monitoring of its own, removed when the pull request closes.

## Good to know

- **An app moves between teams, its folder does not.** Folders, projects and shared variables stay
  behind; variables, domains, deployments, volumes and basic-auth users go with the app.
- **Deleting a folder keeps its apps** unless you choose otherwise in the confirmation. Deleting an
  app is final, but a [Bind](/guides/data/persistent-storage) folder on the server stays.
