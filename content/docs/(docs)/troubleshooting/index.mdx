## Check these first

1. **Open the log:** the deployment's build log, the app's **Logs** tab, or a destination's
   **Connection log**.
2. **Check the server:** **Check readiness** on its **Overview** tab in **Settings -> Servers**.
3. **Separate the app from its domain:** try its generated address, like
   `https://blog-otter-cb00710a.deplo.site`. It works: look at DNS or the certificate. It fails:
   look at the app or the server.

If it worked before, compare with the last good deploy. The change is usually a variable, a
dependency, a Git credential, a certificate or a full disk.

## Statuses people often misread

| What you see | What it means |
| --- | --- |
| A deploy failed, the site still works | A failed deploy changes nothing: the previous version keeps serving |
| Preview **Over the limit** (grey) | Stopped at the app's **Live previews** limit. **Redeploy** brings back the same URL |
| Cron run **Skipped** | It never started: the container was not running, the previous run was still going, or Deplo stopped first |
| Cron run **Unknown** | Deplo lost track of it when the server agent restarted. The command may have completed |
| Server **Unknown** | The health reading is stale. Press **Refresh** |
| Readiness **skipped** | Deplo could not evaluate that check. It is not a pass |

## If you still need help

Note the app, the server, the deploy time, the exact error and the last good deploy.

- **Bugs:** the [issue tracker](https://github.com/DeploCloud/deplo/issues).
- **Security issues:** never in a public issue. Open a
  [private security advisory](https://github.com/DeploCloud/deplo/security/advisories/new), or
  email `security@deplo.build`.
