---
title: Empty or remove a server, delete a cluster
description: Retire a server of a cluster without downtime, remove it, or delete the cluster and keep everything running.
---

Three actions for **instance admins**, all on the cluster's card under **Settings -> Servers**.
None of them is offered over MCP.

| You want to | Do this |
| --- | --- |
| Retire a server | [Empty](#empty-a-server) it, then [Remove](#remove-a-server) it |
| Take a cluster apart and keep everything running | [Delete](#delete-a-cluster) it |

## Empty a server [#empty-a-server]

Emptying moves a server's apps and databases to the cluster's other servers, **one at a time**.
Nothing new is placed on it meanwhile.

On the server's row, **Empty**. The dialog, **Empty this server**, says: "Its Apps and databases
move to the other servers, one at a time. Anything with stored data pauses while it is copied."

- **Order**: databases first, then apps, oldest first. The cluster picks where each one lands.
- **Each move is an ordinary server move**: the app is deployed on the new server, then its
  stored data is copied from the old one. So the server being emptied must be online.
- **An app without stored data is up on the new server before the old copy is removed.** An app
  with a Volume, or a database, is stopped for the length of the copy.
- It starts within about 15 seconds of the click, and goes on if Deplo restarts. While Deplo is
  being [moved to another machine](/operations/move-deplo) nothing moves; it goes on afterwards.

### Refused before anything moves

When the other servers cannot take everything, in the cluster's own words:

- "No server in cluster eu has 512 MB free. Add a server to it or lower web's memory."
- "No server in cluster eu is online and ready right now, so web has nowhere to run. Bring a
  server back or add one."

Room is each app's or database's memory limit (256 MB when none is set), added up for everything
on the server.

### Progress, and when it stops

| The row shows | Meaning |
| --- | --- |
| **Emptying**, "2 of 5 moved, moving web" | It is going. The card refreshes on its own |
| **Emptying stopped**, with a reason, **Continue** and **Stop emptying** | Something could not move. Nothing is retried on its own |
| **Empty**, with **Use again** and **Remove** | It holds nothing. It takes no new work until **Use again** |

The reasons you can meet when it stops:

- one of the two room sentences above
- "web could not be moved, so it is still on this server. Its last deployment says why."
- "web did not finish moving to its new server. Its last deployment says why."
- the cluster's leader not answering

**Continue** tries again from where it stopped.

**Stop emptying** works at any time: the server takes work again, whatever is moving right now
finishes its move, and what already moved stays where it is. Nothing moves back.

Activity records the start, every move ("Moved web to server-b: server-a is being emptied", in
the team that owns the app) and the end ("Emptied server server-a of cluster eu").

## Remove a server [#remove-a-server]

**Remove** shows on a server's row once the server holds nothing, and always on the last server
of a cluster.

The dialog, **Remove this server**, says: "server-a leaves eu at once and is an ordinary server
again." With two servers it warns: "With one server left, eu stops failing over."

- **It is cut off at once.** The cluster stops naming it and its server agent is told to leave. A
  renewed or re-issued server certificate cuts the old one off the same way.
- **A server that still runs work is refused**: "server-a still runs 2 Apps and 1 database. Empty
  it first."
- **An offline server can be removed when it holds nothing.** Deplo tells it that it left as soon
  as it answers again. One that still runs work and does not answer is refused: "server-a does not
  answer, and 1 App still runs on it. Bring it back online, or empty it, before removing it from
  eu."
- **A server that runs the cluster's leader cannot be removed from Deplo**: "Move the leader of
  cluster eu to another server first." See [The leader](/operations/clusters/leader).

### The last server

The last server shows no **Empty**: there is nowhere to move its work. Its dialog says: "It is
the last server of eu, so its Apps have nowhere to move." and offers a checkbox:

**Keep its Apps on this server** - "Its Apps and databases keep running here. Nothing restarts."

They stay on that server as ordinary apps and databases. The cluster stays, empty. Activity:
`Removed server server-a from cluster eu, keeping 1 App and 1 database on it`.

## Delete a cluster [#delete-a-cluster]

**Delete** is in the card's menu, beside **Manage**. The dialog, **Delete eu**, says: "Its
servers stay connected and everything keeps running where it is."

**Nothing is stopped, redeployed or deleted.** Every app and database stays on the server it runs
on, as an ordinary one that nothing moves when a server stops.

The dialog lists what is on the cluster:

- your team's apps and databases by name: "web stays on server-a"
- every other team's as a count: "2 Apps and 1 database of Acme". An admin never reads another
  team's app names there
- with failover on, a warning: "These stop failing over, and an App stops reaching a database on
  another server by name. If a server stops, what runs on it stays down."
- an empty cluster: "Nothing runs on it."

What changes for what ran on it:

| It was | Afterwards |
| --- | --- |
| An app spread over several servers | Stays on its first server, and its copies on the others stop: "web stays on server-a, stops on server-b" |
| An app waiting for room | Listed as "not running, stays on server-a". Start it by hand afterwards |
| A domain on the app's own Cloudflare Tunnel | Points back at the server the app runs on, and the tunnel is deleted |
| A **Failover backup** schedule | Kept as an ordinary schedule: still on, still every 15 minutes, with every backup it took. Edit or delete it under **Backups** |
| A leader on another server | Removed from it, unless it leads another cluster. If that server is offline, it is removed once the server answers |

**Deplo never deletes a backup or a schedule because a cluster went away.** The same holds for a
last server kept with its apps.

**Refused while a server that still runs work does not answer**: "server-a does not answer, and 1
App still runs on it. Bring it back online, or empty it, before deleting eu."

Activity: `Deleted cluster eu: this team's 1 App and 1 database stay where they run and no longer
fail over`. Every other team with work on the cluster gets the same line with its own count.

## Over the API

`emptyClusterMember(clusterId, serverId)` (also continues), `stopEmptyingClusterMember`,
`removeClusterMember(clusterId, serverId, keepWorkloads)`, `deleteCluster(id)` and
`clusterDeletion(id)` for the list. All need an instance admin. `get_cluster` over MCP shows how
far an emptying has got.
