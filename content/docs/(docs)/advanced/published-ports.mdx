A **published port** binds a port of the server straight to a port of your container, so
clients connect to `203.0.113.10:16379` instead of a domain. Use it for what is not HTTP: game
servers, SMTP, raw TCP or UDP.

## The rules

- **It needs the Publish ports grant** (`canExposePorts`), like a database's **Host port**.
  Without it the section is read-only. See
  [Host access](/advanced/host-access-and-privileges#publishing-a-port-is-a-separate-grant).
- **Ports under 1024 are refused.** They belong to the host, and 80 and 443 to Deplo's proxy.
  Publish 8025 and let your DNS or firewall do the rest.
- **A host port has one owner per server.** A port another app or database on that server
  already publishes is refused, even one in another team, because servers are shared. A Compose
  stack's own `ports:` and processes Deplo did not start are not checked: that clash shows up
  as Docker's own error at deploy.
- **Pull request previews never publish.** They would fight production for the same port.
- **A Compose app publishes its own.** The section is not offered: write `ports:` in the
  Compose file, which needs the same grant.

<Callout type="warn">
  A published port is open to whatever can reach the server, and to every container on it. It
  carries no certificate, no basic auth and none of a domain's middlewares. Put a firewall in
  front of it, and use a domain whenever the protocol is HTTP.
</Callout>

## When not to use one

| You wanted | Do this instead |
| --- | --- |
| A website or an API reachable from outside | [Add a domain](/getting-started/add-a-domain). HTTPS is handled for you. |
| One app to reach another | Nothing. Apps in one environment, on one server, reach each other by name. |
| An app to reach its database | Nothing. The database answers as `db-<name>`. |
| A game server, a mail server, a raw TCP or UDP protocol | A published port. This is what it is for. |
