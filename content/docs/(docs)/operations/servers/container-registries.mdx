**Settings -> Registries**, with the **Manage container registries** capability.

<Callout type="info" title="Beta">
This feature is currently beta/experimental and subject to change. It is
not recommended for production. Try it out and share your feedback on
[our GitHub](https://github.com/DeploCloud/deplo/issues).
</Callout>

One entry per registry, per team, encrypted. Every deploy in that team carries the credentials to
its server, which uses them on every pull:

- the image an app of source **Docker image** runs,
- every image a **Compose stack** brings up,
- the base image a **Dockerfile** build starts `FROM`.

Nothing is set per app: connect the registry once and every private image from that host pulls, on
every server the team deploys to. The token is write-only, with no way to reveal it.

## Add one

<Steps>
<Step>

### Open registries settings

**Settings -> Registries**, then **Add registry**, and give it a **Name**.

</Step>
<Step>

### Pick the type

Pick the **Type**: **GitHub (ghcr.io)**, **Docker Hub**, **GitLab** or **Generic / self-hosted**.
It fills in the default **Registry host**.

</Step>
<Step>

### Create a credential on the provider, then fill in the form

Deplo issues no credential: create a read-only one on the provider's own site first. What goes in
**Registry host**, **Username** and **Token** differs per provider:

<Tab value="ghcr">

- **Registry host**: `ghcr.io`.
- **Username**: your GitHub username.
- **Token**: a **classic** personal access token with `read:packages`, from GitHub's **Settings ->
  Developer settings -> Personal access tokens -> Tokens (classic)**. For an organization's image, the
  org may also have to grant the token access in its package settings.

<Callout type="warn" title="Classic token, not fine-grained">
Fine-grained tokens have no `packages` permission, so a pull with one fails with `unauthorized` even
if the token looks valid.
</Callout>

See GitHub's [Container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

</Tab>
<Tab value="dockerhub">

- **Registry host**: `docker.io`.
- **Username**: your Docker Hub username.
- **Token**: an access token with **Read** permission, from Docker Hub's **Account settings ->
  Personal access tokens**. Not your account password.

See Docker's [personal access tokens](https://docs.docker.com/security/access-tokens/).

</Tab>
<Tab value="gitlab">

- **Registry host**: `registry.gitlab.com`, or your own instance's registry host.
- **Username**: the deploy token's username, shown by GitLab when the token is created.
- **Token**: a deploy token with the `read_registry` scope, from the project or group's **Settings ->
  Repository -> Deploy tokens**.

See GitLab's [deploy tokens](https://docs.gitlab.com/ee/user/project/deploy_tokens/).

</Tab>
<Tab value="generic">

For anything else, such as Harbor, a cloud provider's registry or one you run yourself:

- **Registry host**: the registry's own host.
- **Username** and **Password or access token**: whatever it issues for read-only pulls, like a robot
  account or an IAM token. The one type where a real password is a normal answer.

</Tab>
</Tabs>

</Step>
<Step>

### Add it

Click **Add registry**.

</Step>
</Steps>

Then reference the image in an app whose source is [a Docker image](/guides/deploy/docker-image), a
Compose stack, or as the base image of a Dockerfile build.

## Before using a registry

- **Registries are per team.** Another team needs its own entry.
- **Tokens expire.** A pull that used to work and now fails with `unauthorized` is almost always this.
- **Deplo only pulls, and pushes nothing.** Images it builds stay on the server that built them, which
  is why [rollbacks](/guides/releases/rollbacks) depend on local retention.

## Troubleshooting

- **`pull access denied`**: no credential matches that image's host, or the token can't see that
  repository.
- **One image works and another doesn't**: same host, different repository permissions on the provider.
- **Nothing changed after connecting the registry**: credentials are read at deploy time. Deploy again.
- **A registry on a private address**: the server pulls from it fine. Only the image search in the app
  form can't reach it, so type the image reference in full.

See [Deploys and builds](/troubleshooting/deploys-and-builds) for more.
