**One update, one click.** From **Settings -> Deplo -> Updates**, Deplo updates the panel,
restarts it, and then brings every connected server to the agent that version is paired with,
on its own, one server at a time.

- The **control plane** (this panel) goes first.
- The **server agents** - one per host - follow once the panel is back.
- Database migrations run automatically at startup.

**Every Deplo version is paired with one agent version.** You never pick an agent version, and
agents only ever move forward: there is no downgrade path.

## Release history

**Settings -> Deplo -> Updates** shows the installed version, available
releases, release notes, and agent versions across the fleet.

- **Check now** refreshes the release list. It is always there.
- The installed release is marked **Installed**.
- The page shows which agents are behind, and where each update stands.

When the panel and every agent are current, the page says **Everything is up to date** and shows
no update button at all. A button only appears when there is something to install, or a failed
update to retry.

## Update the control plane

<Steps>
<Step>
### Open Settings -> Deplo -> Updates
</Step>

<Step>
### Click the **Update** button
It names the version it will install. That is not always the newest one: see
[When Update offers an older release](#when-update-offers-an-older-release). Confirm, and
the machine Deplo runs on pulls the new image and restarts the panel.

If an **offline** server runs a server agent the new version no longer supports, the confirmation
names it: `edge-2 is offline on server agent v0.3.0 and will be unusable until its server agent updates.`
</Step>

<Step>
### Wait about a minute
The page reloads itself when Deplo answers again on the new version.
</Step>

<Step>
### Watch the servers follow
The **Server agents** card counts them as they come up to date. Nothing to click.
</Step>
</Steps>

Three things happen around it that are worth knowing:

- A `pg_dump` of the panel's database lands in `/opt/deplo/backups` first, and the newest three are kept.
- **Secrets are never rotated**, and no setting is reset.
- If the new version does not come up, the previous one is put back automatically. The panel says
  so instead of leaving you on a spinner: see [An update was rolled back](#an-update-was-rolled-back).

<Callout type="info" title="Your apps keep running throughout">
They are containers on hosts, not part of the control plane. A panel that's
down means you can't deploy or read logs for a minute, it does not mean your
sites are down.
</Callout>

## When Update offers an older release

Update can offer an older version than the newest. Some releases have to come after an earlier
one, which gets your instance ready first: for example, it moves every server over to connecting
to Deplo by itself. Skipping it could leave servers Deplo can no longer reach.

So **Update installs the earlier release first**. That release is an **update stop**.

For example, v0.7.0 has to come after v0.6.0, and you are on v0.5.0. The Updates tab says:

- **Deplo v0.6.0 is available**
- `Deplo v0.7.0 has to come after v0.6.0, so Update installs v0.6.0 first.`

Click **Update** as usual. Once v0.6.0 has finished getting your instance ready, the tab offers
v0.7.0 on its own.

- A new install is past every update stop already.
- Canary releases follow the same rules, so the **Canary releases** switch never skips a stop.

### Servers the update is waiting on

On the update stop, Update offers nothing until every server has connected to Deplo by itself
at least once. The tab says:

- **Getting ready for Deplo v0.7.0**
- `Deplo v0.7.0 becomes available once v0.6.0 has finished getting this instance ready.`

Below it, the tab names each server it is still waiting on:

`edge-2 hasn't connected to Deplo yet. Check that it's turned on and connected to the internet.`

Usually there is nothing to do. Deplo updates each server agent on its own, and the server
connects moments later. The tab offers v0.7.0 as soon as the last server has connected.

When a server stays on the list:

- **Check that it's turned on and connected to the internet.** Once it is back, Deplo updates
  its server agent and it connects by itself.
- **Check the Server agents card.** `Update failed, retrying in 4 min` means its server agent has
  not updated yet. Wait for the retry, or click **Retry now**.
- **Check Settings -> Servers.** A server that shows **Degraded** with
  `This server can't reach Deplo at deplo.example.com. Check that it's connected to the internet.`
  answers Deplo but can't reach it back.

[A server hasn't connected to Deplo yet](/troubleshooting/servers-and-agents#a-server-hasnt-connected-to-deplo-yet)
covers each case.

### Leave a server behind

A server you can't bring back, such as one switched off for good, would hold the update forever.
An instance admin can leave it behind:

1. On **Settings -> Deplo -> Updates**, click **Leave behind** next to the server.
2. Read the confirmation. **Leave edge-2 behind?** says
   `Deplo stops waiting for edge-2 to connect. Its apps and settings stay in Deplo.`
   and warns `After the update, edge-2 won't work until its server agent is reinstalled.`
3. Click **Leave behind**.

The row then reads `edge-2 was left behind: it needs its server agent reinstalled after the update.`,
with **Manage** to open the server. Once no server is left waiting, the tab offers v0.7.0.

- **Until you update, nothing changes for it.** If it connects after all, it drops off the list
  and works normally.
- **After the update, it won't work until its server agent is reinstalled.** Its apps keep
  running, and its apps and settings stay in Deplo. Reinstalling brings it back as it was:
  see [A server was left behind](/troubleshooting/servers-and-agents#a-server-was-left-behind).
- **There is no undo.** It only matters until the server connects.
- **Activity records it** under your name: `Left server edge-2 behind, so Deplo can update without it`.
- **The machine Deplo runs on can't be left behind:**
  `hq-1 is the machine Deplo runs on, so it can't be left behind. It connects on its own once its server agent is up to date.`

Removing a server takes it off the list too. See
[Remove or uninstall](/operations/remove-a-server-or-uninstall).

## An update was rolled back

When a new version does not start, the previous one is put back on its own and your apps keep
running. The Updates tab then says so, with the reason:

- **The update to Deplo v0.7.0 was rolled back**
- `The new version did not start, so Deplo went back to the one that was running.`

A release that has to come after an update stop refuses to start on an instance that has not
been through the stop. Update installs the stop first, so this is rare: it means the newer
version was installed some other way. The reason then names the release to install first:

`Deplo v0.7.0 has to come after v0.6.0. Update to v0.6.0 first and let it finish getting this instance ready.`

- **Nothing was changed.** A refused release stops before it touches your data.
- **Follow what the tab offers.** It installs v0.6.0 first, or shows what v0.6.0 is still
  waiting on.

The notice stays until an update succeeds.

## If the panel cannot update itself

On the machine Deplo runs on:

```bash
deplo update
```

It follows the **Canary releases** switch (**Settings -> Deplo -> Advanced**): on, it takes the
newest release, canary or not; off, only stable ones. It never installs a version older than the
one running, so turning canaries off does not move a canary panel back to stable.

It goes through [update stops](#when-update-offers-an-older-release) like the button. Below one,
it installs the stop and prints:

```text
Deplo v0.7.0 has to come after v0.6.0, so this update installs v0.6.0 first.
Update again once v0.6.0 has finished getting this instance ready.
```

On the stop, before it has finished, it installs nothing and prints:

```text
Deplo v0.7.0 becomes available once v0.6.0 has finished getting this instance ready.
Settings > Deplo > Updates shows what it is still waiting on.
```

Without the `deplo` command, run the installer instead:

```bash
curl -fsSL https://deplo.build/install.sh | bash
```

The existing `/opt/deplo/.env` switches the installer to update mode.

To pin a version rather than take the newest:

```bash
curl -fsSL https://deplo.build/install.sh | \
  DEPLO_VERSION=0.1.0 bash
```

A pinned version goes through update stops too.

## The agents follow on their own

Once the panel is back, Deplo walks the fleet by itself: remote servers first, the machine
Deplo runs on last, one at a time. The **Server agents** card on the Updates tab counts
them down, and every agent it updates is recorded in **Activity** under your name.

An update can fail for a server without holding up the others:

- **A deploy is running on it.** An update restarts the agent, which would drop the build.
- **It is unreachable** right now.
- **Its agent is too old to update itself.**

Deplo retries a failed server on its own: after 1 minute, then 2, 4, 8, up to once an hour,
for **24 hours** from the first failure. The card shows each one, for example
`Update failed, retrying in 4 min`.

If a server takes the new agent and **does not come back**, Deplo stops updating the rest
until that one recovers. A broken agent release reaches one server, not all of them.

### Retry an update by hand

The **Retry now** button appears only once an update has failed, on the server's page and on
its row in the **Server agents** card. It is for instance admins.

- It runs an attempt at once and cancels the retry that was scheduled.
- It is disabled while an attempt is running, so two never run on one server.
- If it fails too, the automatic retries carry on. The 24 hours do not start again.
- After the 24 hours, Deplo stops retrying and the button is the way to try again. A server
  that was offline gets one more automatic attempt when it comes back.

## When a server is unusable

Each Deplo version supports agents down to a minimum. A server whose agent is older than that
is **unusable** until its agent updates:

- Deploys, logs, the console, backups and every other action on it are refused with
  `This server is being updated. Deplo retries on its own; an instance admin can retry it now.`
- **The apps on it keep running.** Nothing is stopped.
- Instance admins see a banner across the dashboard, and the **Server unusable until it
  updates** alert goes to your notification channels.

The fix is the agent update itself: automatic, or **Retry now**. An agent newer than the one
Deplo is paired with is fine and left alone.

## Before you update again

- **Agents cannot be downgraded.** An agent newer than the panel's own is left as it is.
- **Some features need a newer agent.** When one is missing, Deplo says so rather than silently doing something else.
- **Re-running the installer is safe.** It is what the button does, so running it by hand is never a workaround.
- **Read the release notes for a minor bump.** During `0.x`, minor means something you notice: a feature, changed behavior, a database migration, or a newer agent required.
- **Back up before a big jump.** Migrations apply at boot and are not reversed by rolling the image back.
