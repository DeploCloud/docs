How your source becomes a container image: which builder runs, what commands it runs, and which
port the result listens on. Most apps never need to touch any of it. A Docker image or a Compose
source has nothing to build, so none of this page applies to them.

## The four build methods

Pick one under **Build method**, on the **Build & output** card in **Settings -> Deployments**.

<Image
  src={`${basePath}/screenshots/build-settings/01-build-methods.png`}
  alt="The four build methods on Settings -> Deployment"
  width={1728}
  height={1080}
  className="w-full rounded-lg"
/>

| Method | Use it when | Fields it adds |
| --- | --- | --- |
| **Railpack** (default) | Normal application code, any common language | **Framework**, **Railpack version** |
| **Nixpacks** | The same job, a different builder. Try it if Railpack mis-detects | **Framework**, **Publish directory** |
| **Dockerfile** | You already have a `Dockerfile` and want it used exactly | **Dockerfile path**, **Build context path**, **Build stage (target)** |
| **Static** | The build produces plain files to serve | **Single-page application** |

**Single-page application** makes unmatched paths fall back to `index.html`, which is what a
client-side router needs. Dockerfile and Static skip framework detection entirely: you have
already said what happens.

Changing the build method leaves domains, variables and volumes untouched.

## Framework detection, and overriding it

For Railpack and Nixpacks, Deplo re-derives the framework from `package.json` and the root
configuration **on every deploy** and records what it found on the app, so upgrading your
framework changes the build without you editing anything. The **Framework** select overrides that:
a value you pick is stored in its own column, survives every redeploy, and carries the framework's
default container port with it.

Detection fills in the build command, a deploy command for the few frameworks that publish exactly
one, and the container port. It never copies your `start` script: in most projects that script is
the dev server.

Anything you type by hand is stored and wins from then on; clearing a field hands it back to
detection. The greyed text in an empty field is the builder's generic default (`npm ci`,
`npm run build`, `npm run start`, `dist`), not the value detection actually found, so an empty
field means "let the builder decide", not "it will run this".

Click **Save build settings**. Saving does not deploy: click **Redeploy** when you want the change
to take effect.

## The port is the one people get wrong

Deplo routes traffic to exactly one port per app, and detection sets a default per framework. The
ones that surprise people:

| Framework | Port | | Framework | Port |
| --- | --- | --- | --- | --- |
| Vite, Preact, Svelte | `4173` | | Astro | `4321` |
| Angular | `4200` | | AdonisJS | `3333` |
| Gatsby | `9000` | | Strapi | `1337` |
| Eleventy, Vue CLI | `8080` | | Everything else | `3000` |

If the container starts fine and the URL times out, this is nearly always why. Your process must
also listen on `0.0.0.0`, not `127.0.0.1`: a server bound to localhost inside a container is
unreachable from outside it.

A single hostname can override the port for itself, which is how one app serves an API on one
domain and a dashboard on another. That override lives in **Domains**, not here.

## Build cache

<Image
  src={`${basePath}/screenshots/build-settings/03-build-cache.png`}
  alt="Build cache and where the build runs, on Settings -> Advanced"
  width={1728}
  height={1080}
  className="w-full rounded-lg"
/>

**Settings -> Advanced**, on the **Build & triggers** card. **Build cache** is on by default. The
cache lives on the **server**, one BuildKit cache shared by every app on that host, which is why a
first build is slow and later ones are not.

The switch turns caching off for this app only. **Clear cache** arms a one-shot clear, applied on
the next build; it does not prune anything on disk, which is
[disk cleanup](/operations/servers/cleanup)'s job.

The same card carries **Build server** (beta: compile on a different machine than the one that
runs the app), **Extra compose flags** (passed to `docker compose up` exactly as typed, additive
only - anything that would change the project name, the stack file or the env file is refused),
and the **Deploy hook** URL.

If a build server is set and cannot take the job, Deplo does not fail: it falls back to another
build server in the fleet, then to the app's own server.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| `command not found` during the build | Detection guessed wrong, or the command belongs to a dependency that is not installed. Set **Build command** explicitly, or pick the **Framework** by hand. |
| The build passes, the site does not answer | Wrong **Container port**, or the process is bound to `127.0.0.1` instead of `0.0.0.0`. |
| The build is slow every single time | The cache is off for this app, or a cleanup sweep is removing it. Check **Build cache** and the server's cleanup scopes. |
| A setting saved but nothing changed | Saving is not deploying. Nothing changes on the server until the next build. |

More in [Deploys and builds](/troubleshooting/deploys-and-builds).
