Deplo reads the packages inside every image it runs for your team and checks them against public
lists of known security flaws. When there is something you can fix, the app says so and tells you
what to do. Nothing to set up: it is on for every team.

One security update is one package to move, or one image to update. A package with 25 known flaws
that one new version fixes is one update.

## What you see

- **A banner on the app's Overview**: "2 security updates available", with **Details**. Only when
  something critical is there to apply; it goes away once fixed.
- **A shield on the app's card**, next to its status dot. Hover it for the count. Databases get it
  on **Storage**, pull request previews on their row.
- **A notice at the top of the Overview** naming every app and database that needs updates, red
  when one runs something already used in attacks. **Show these apps** filters the grid.
- **A notice next to your avatar**, on every page. **Dismiss** hides it until something new needs
  updating.
- **Details**: every update and what to do, also in the app's menu (three dots, top right) -> **Security updates**
  ("Up to date" when there is nothing). Each advisory shows its scores and summary, and opens on
  OSV.dev.

Right after a deploy, Details reads **Checking the new deploy** for about a minute and leaves the
previous image's updates out.

## How serious it is

| Level | What it means |
| --- | --- |
| **Used in attacks** | On CISA's list of flaws already exploited in real attacks |
| **Critical** | Score 9.0 or more, and it needs nothing special to be exploited |
| **Important** | Score 7.0 to 8.9, or a critical one that works only when the package is set up a certain way |

Only **Used in attacks** and **Critical** count in the badge, the notices and the alerts.
**Important** ones are listed under **Less urgent**. Lower levels are not shown.

**Only when the package is set up a certain way** marks a flaw whose CVSS score says attack
complexity high. For example, a critical DOMPurify flaw that needs `SAFE_FOR_TEMPLATES` with
`RETURN_DOM` is **Important**. Deplo reads this from the advisory, not from your code. A flaw on
CISA's list stays **Used in attacks** whatever its setup.

**EPSS** is the chance of exploitation in the next 30 days, as [FIRST](https://www.first.org/epss/)
estimates it. A high one is worth looking at first.

## How to fix it

Details groups updates under **To apply**, **Waiting on the image's maintainers**, **Less urgent**,
**Build only** and **Ignored**. Each says how to get the fix:

| What Details says | What to do |
| --- | --- |
| Update minimist to 1.2.6 in your code | Your `package.json` names it: bump it and push |
| Pulled in by monaco-editor ← @payloadcms/ui: add an override for dompurify 3.4.17 | [Add an override](#add-an-override) and push. Without the chain, it reads **Pulled in by another package** |
| Update @payloadcms/richtext-lexical: the fix for happy-dom is a new major version, which an override could break | Update the package your app names to a version that brings the fix |
| Only used to build the app: it never runs | Nothing urgent: it comes from `devDependencies`, listed and never counted |
| A newer build of this image fixes 3 known flaws: update to get it | Press **Update**. An app redeploys and pulls its image again; a database asks first, then restarts on the new build with its data |
| Version 1.60.2 is available and fixes 2 known flaws | Change the image version in **Settings -> Deployments** |

### Add an override

An override makes every package that pulls in a dependency use the version you pick. Add it to
`package.json`, run an install so the lockfile follows, and push:

<Tabs items={["bun", "pnpm", "npm"]}>
<Tab value="bun">

```json title="package.json"
{ "overrides": { "dompurify": "3.4.17" } }
```

Then run `bun install`.

### Update an image

**Update** appears only after Deplo has read the newer build: the image's server downloads it,
reads its packages, and removes it again. While that runs, Details says Deplo is checking it. A
newer build that still has the flaw goes under **Waiting on the image's maintainers**, never
counted.

## What is checked

Only what you chose:

- **An app Deplo builds from your code**: the dependencies it installs (`package.json`,
  `requirements.txt`, `Gemfile`, `go.mod`), and a `RUN pip install` in your `Dockerfile`.
- **An image you deploy as it is** (a database, a template, a Compose service with `image:`): its
  software, when a newer build or version exists. A pinned `grafana/grafana:8.3.0` is compared with
  the newest release on its line.

Every source counts: git, upload, Docker image, Compose, template, managed databases, pull request
previews, and stopped apps (from the image they will start with).

Left out, because you never picked them: system packages (glibc, openssl) and the Python packages
the system installs for itself; the toolchain (Go's standard library, pip, setuptools, wheel, npm);
copies a package bundles inside itself (like `next/dist/compiled`); the client tools a database
image bundles (like MySQL Shell); flaws nobody has fixed yet; and Deplo's own components, fixed by
Deplo updates.

## When it is checked

- **After a deploy**, as soon as it is live, usually within a minute.
- **Every 6 hours**, every image against the latest lists, since new flaws are found in software
  that has not changed.
- **Every day**, CISA's list of flaws used in attacks is refreshed.

## Alerts

**Security update available** is on by default in every channel. It fires once per update, only
for running apps and databases (never a stopped app or a preview), and only for **Used in
attacks** and **Critical**.

## What Deplo sends

- **To [OSV.dev](https://osv.dev)**: the name and version of each package it checks, for example
  `npm minimist 1.2.5`, private registry names included. Never system packages, and nothing that
  names this Deplo: no app, server or domain.
- **To [FIRST](https://www.first.org/epss/)**, once a day: the CVE ids behind your updates (for
  example `CVE-2021-44906`), to read their EPSS scores.

Three read-only downloads also happen:

- CISA's public list of exploited flaws, daily, by the panel.
- The package reader, once per server, from its official release, checksum verified.
- A newer build of an image you run, by its own server from its registry, then removed.

## Ignore an update

When a flaw is not reachable, or the fix comes with the next release: in **Details**, press
**Ignore**, write why, and pick 30, 90 or 180 days.

- It moves to **Ignored**, stops counting and never alerts until then.
- **Activity** records who, until when, and why.
- When the time is up it counts again. A **new** flaw in the same package shows right away.
- **Stop ignoring** brings it back at once.

It needs the **Ignore security updates** capability. Team owners have it; give it to a role in
**Settings -> Roles**.

## When an image cannot be checked

Details says why:

| Message | What happened |
| --- | --- |
| An image is too large to check on its server | Reading it needed more memory than Deplo allows itself there |
| Its server is too low on disk space | Deplo needs about twice the image size free |
| Its server is too low on memory | Deplo waits until enough is free |
| Checking an image took too long | Reading it hit its time limit |
| Its server cannot check images yet | The server cannot cap the reader's memory, so Deplo does not run it |

Your apps are never at risk: one image at a time per server, never during a deploy, at the lowest
priority.

## Turn it off

An instance admin can turn checks off for the whole instance: **Settings -> Deplo -> Advanced**,
under **Privacy**, switch **Security updates** off. Nothing is checked or sent from then on. The
line under the switch shows when the last check ran, or since when OSV.dev could not be reached.
