The setup we recommend to every hosting provider: a clean base image, one command at first
boot, and an address you can predict. The customer signs in with the email and password from
your welcome email. No log to read, no key to copy.

<Steps>
<Step>

### Create the base template

Start from a clean, minimal image:

| | Requirement |
| --- | --- |
| OS | <Os name="ubuntu">Ubuntu</Os> 24.04 LTS, 26.04 LTS · <Os name="debian">Debian</Os> 12, 13 |
| Architecture | `x86-64` or `arm64`, with `systemd` |
| Ports | `80` and `443` open from the internet |
| Smallest plan | 2 cores, 4 GB of RAM, 30 GB of disk |
| Comfortable plan | 4 cores, 8 GB of RAM |

More in [what you need](/getting-started/install#what-you-need).

</Step>
<Step>

### Run the installer on first boot

Chain the installer to your provisioning, right after the operating system install:

<Tabs groupId="provisioning" persist items={['Using cloud-init', 'Provisioning script']}>
<Tab value="Using cloud-init">

```yaml
#cloud-config
runcmd:
  - curl -fsSL https://deplo.build/install.sh | bash -s -- --yes --owner-email ada@acme.com --owner-password '<temporary password>'
```

</Tab>
<Tab value="Provisioning script">

```bash
curl -fsSL https://deplo.build/install.sh | bash -s -- \
  --yes --owner-email ada@acme.com --owner-password '<temporary password>'
```

</Tab>
</Tabs>

- **`--owner-email`** is the customer's, the one on their order.
- **`--owner-password`** is a temporary one, at least 8 characters, new for every order: the
  service password your billing (WHMCS, for example) already generates.
- **At the first sign-in** Deplo makes the customer replace it. Until then the account can do
  nothing else.
- **`--domain panel.customer-domain.com`** (optional) starts the panel on the customer's own
  domain, with a Let's Encrypt certificate. If your order form asks for a domain, pass it: the
  customer never has to move the panel later. Its DNS must point at the VM; until it does, the
  generated `deplo.site` address answers.

<Callout type="warn" title="Treat the temporary password as seen">
  The install transcript hides it, but it is readable in the process list while the install
  runs, and cloud-init keeps it in the stored user data. Tell the customer to sign in right away:
  the first sign-in replaces it.
</Callout>

The cloud-init version works as is on any panel that accepts cloud-init user data: Proxmox VE,
SolusVM 2, Convoy, OpenStack, CloudStack. On VirtFusion, add it as a server provisioner, in Bash
or cloud-init YAML.

<Callout type="warn" title="On Virtualizor: the root password as a fallback">
  A recipe can pass only the root password: `{{username}}` is the customer's email and
  `{{root_pass}}` their root password, so use
  `--owner-email '{{username}}' --owner-password '{{root_pass}}'`. It works, but until the first
  sign-in the root password also opens the panel. Tell the customer to sign in right away.
</Callout>

</Step>
<Step>

### Build the customer's address

With `--domain`, the address is that domain: `https://panel.customer-domain.com`.

Without it, the panel answers on `deplo.site`, a wildcard DNS where a name carrying an IPv4 in
hexadecimal resolves to that IP. Each octet becomes two hex digits, so `203.0.113.10` gives:

```
https://deplo-cb00710a.deplo.site
```

<Tabs items={['Bash', 'JavaScript', 'PHP']}>
<Tab value="Bash">

```bash
IP=203.0.113.10
echo "https://deplo-$(printf '%02x' ${IP//./ }).deplo.site"
```

</Tab>
<Tab value="JavaScript">

```js
const panelUrl = (ip) =>
  `https://deplo-${ip.split(".").map((n) => (+n).toString(16).padStart(2, "0")).join("")}.deplo.site`;
```

</Tab>
<Tab value="PHP">

```php
$url = "https://deplo-" . bin2hex(inet_pton($ip)) . ".deplo.site";
```

</Tab>
</Tabs>

An IPv6-only VM gets its IPv6 instead: `2001:db8::10` gives `deplo-v6-2001-db8--10.deplo.site`.

</Step>
<Step>

### Send it

- **Where**: in the welcome email or the VPS detail page, next to the email and temporary
  password.
- **When**: the install takes a few minutes after boot. Until then the address does not answer.
- **What they see**: a sign-in page, then a short setup that replaces the temporary password and
  names their team.

The customer can later move the panel to their own domain from **Settings -> Deplo**: see
[the panel's own address](/operations/panel-address-and-certificates).

</Step>
</Steps>

## Use your own wildcard domain

`deplo.site` is optional. To put the panel under your brand, run wildcard DNS on a domain of
yours and pass the VM's hostname on it, built the same way, with `--domain`:

```bash
curl -fsSL https://deplo.build/install.sh | bash -s -- \
  --yes --owner-email ada@acme.com --owner-password '<temporary password>' \
  --domain deplo-cb00710a.example-vps.net
```

The panel answers on `https://deplo-cb00710a.example-vps.net`, with a Let's Encrypt certificate.

<Callout type="warn" title="Use a dedicated domain">
  Keep the wildcard apart from your main domain, the way Deplo keeps `deplo.site` apart from
  `deplo.build`. Customer servers answer on it, so abuse reports, blocklists and cookies stay
  away from your website and your billing panel.
</Callout>

- **We recommend running your own [nip.io](https://github.com/exentriquesolutions/nip.io)**: it
  resolves the hex form of the IP out of the box. Set it as the nameserver of `example-vps.net`
  at your registrar.
- **Even better, host it on Deplo itself**, on a server of yours. It is a DNS server, so that
  server needs port `53` open on UDP and TCP.
- **The generated `deplo.site` address stays on as a backup.** The customer can turn it off in
  **Settings -> Deplo -> Advanced**, **Backup address**.
