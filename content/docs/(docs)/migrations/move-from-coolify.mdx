A wizard reads your Coolify installation over its API and recreates it here: applications,
one-click services, databases, domains, variables, volumes and backup destinations, data included.
The data is read by a Deplo agent on each Coolify server.

## Before you start

- **Turn the API on** in Coolify's **Settings**. If it only accepts listed IPs, add the machine
  Deplo runs on.
- **A token per Coolify team.** In **Keys & Tokens**, **API tokens**, tick **`root`**, from an
  account that is an **admin or owner** of the team. Without root, the token needs **`read`**,
  **`read:sensitive`** and **`deploy`**: tick `deploy` first, because Coolify clears the list
  when you tick it. Deplo checks at **Connect** and refuses a token that would import blanks.

A token only sees the team it was created in: switch team in Coolify for the next one. Each team is
one run, queued on the server, so you can close the page.

### On every source machine

- **A snapshot of every machine.** It is the only way back after a takeover.
- **Root on each Coolify server**, to run one install command. The **Install** step lists every
  server. The agent dials Deplo, so no port has to be open.

## Run the migration

<Tabs items={["Take over this server", "From another server"]}>
<Tab value="Take over this server">

<Steps>
<Step>

**Snapshot the server.** The final step removes Coolify.

</Step>
<Step>

**Run the installer**, the same command as any install:

```bash
curl -fsSL https://deplo.build/install.sh | bash
```

It finds Coolify and asks whether Deplo may replace it. Answer no and nothing is installed.
`--yes` does not answer this question; `DEPLO_TAKEOVER=coolify` does.

</Step>
<Step>

**Open the address it prints.** Until the ports move, Deplo answers over http through Coolify's
own proxy on port 80. When that is not possible, the installer prints an `ssh -L` tunnel instead,
for example `ssh -L 3000:localhost:3000 root@203.0.113.10`.

</Step>
<Step>

**Create your account, then choose.** **Bring your data over**, or **Start clean**. Start clean
deletes Coolify and everything it runs, and cannot be undone.

</Step>
<Step>

**Connect, Install, Review.** The panel address is filled in. Paste a token per Coolify team, run
the printed command on any other Coolify server, tick what comes over, and press **Start
migration**. Everything lands on this machine.

</Step>
<Step>

**Take over the machine.** It opens once every team has landed. Tick **I have no other teams on
this Coolify**, tick any service listed as losing its data, and type `coolify`.

Deplo stops Coolify, inherits its certificates, moves Traefik onto 80 and 443, removes Coolify's
containers, networks, images, `/data/coolify` and its SSH key in root's `authorized_keys`, and
restarts Docker. The apps' volumes and Coolify's database backups (`/data/coolify/backups`) stay
on the disk. The page moves to https by itself.

</Step>
<Step>

**Deploy your apps.** Open each app, check it, and press **Deploy**.

</Step>
</Steps>

</Tab>
<Tab value="From another server">

<Steps>
<Step>

**Open Settings -> System -> Migrations**, then **Dokploy or Coolify**. Enter the **Panel
address** and the token. A private address works too, for example `http://172.17.0.1:8000` on the
same machine.

</Step>
<Step>

**Add a token per team.** Each joins **Teams to bring over** with the team it lands in: the team
with the same name, otherwise a new one.

</Step>
<Step>

**Install the agent on every Coolify server.** Run each printed command as root. The row goes from
**Waiting for the agent** to **Connected**. A machine already in your fleet is reused.

</Step>
<Step>

**Review and start.** Tick what comes over, pick where each app runs and is built (**Build all
on** sets every build at once), then press **Start migration**. You can close the tab: a chip on
every page shows the progress.

</Step>
<Step>

**People, then Done.** Members get single-use registration links and join as plain members; the
report names any other role they had. Someone with an account here is added to the team instead.

</Step>
</Steps>

When the run ends, Deplo takes its agent back off the Coolify servers. Past runs stay under
**History** with their reports.

</Tab>
</Tabs>

## What lands as what

| On Coolify | Here |
| --- | --- |
| Application, `dockerfile` | App built from its repository, with that Dockerfile |
| Application, `nixpacks` / `static` | App built with **Railpack**. A publish directory becomes the **Output directory**, single-page setting included |
| Application, `dockerimage` | App running that image |
| Application, `dockercompose` | Compose stack |
| Service (one-click) | Compose stack, from the compose its author wrote |
| PostgreSQL, MySQL, MariaDB, MongoDB, Redis, ClickHouse | The same engine, with its data |
| Persistent storage | Volume, with its data |
| File storage | Config file under **Storage** |
| Environment variables | The app's variables, magic `SERVICE_*` values resolved |
| Preview-only variables | The app's preview variables |
| Shared variables (team, project, environment) | Shared variables at the same level, linked to the apps that used them |
| Domains, with port and path | Domains |
| HTTP basic auth | **Access** |
| Memory and CPU limits | **Resources** |
| Health check, published host ports | **Settings -> Advanced** |
| Scheduled tasks | Cron jobs |
| S3 storages and database backups to S3 | Backup destinations (tested on arrival) and schedules |

## What changes on the way

- **Temporary hostnames** (`sslip.io`, `traefik.me`, `nip.io`, `deplo.site`, `localhost`) get a
  new `deplo.site` address, unless the app lands on the same machine. Your own domains come
  across as they are.
- **Connection strings are rewritten** to the database's new host, `db-<name>`. Values an app
  stored itself (a saved `siteurl`) are not: fix them from the app's **Console**.
- **A volume keeps the name you gave it.** Coolify's `<resource id>-<name>` arrives as `<name>`.
- **A volume pinned with `external: true` or `name:` was never the one running**: Coolify renames
  every volume. Deplo copies what actually ran and names the pinned one in the report.
- **The compose is the one its author wrote**, not Coolify's rendered copy. When Coolify only
  returns the rendered one, the report says so.
- **A variable Coolify shows once arrives as a secret.** When Coolify's API returns no value for
  it, it arrives empty and the report names the key: fill it under **Environment**.
- **A `{{team.KEY}}` reference** to a variable of the same name becomes a link to that shared
  variable. A server-level shared variable is offered to the project; Deplo has no server scope.
- **A `$` Coolify would have expanded** arrives as written, and the report names it.
- **An address stored without `http://` or `https://`** arrives on plain http.
- **A second service name in one Environment is renamed**: the second `db` becomes `<app>-db`,
  and its `depends_on`, variables and domain follow.
- **A network you created yourself is dropped.** Apps in the same Environment share one network.
- **Security headers stay off** on a moved app's domains. Turn them on under
  [Security headers](/guides/networking/domains-and-https#security-headers-and-cors).
- **Compose middleware labels** come across when their kind is supported, router labels never.
  See [Middlewares in a compose file](/advanced/compose-apps#middlewares-in-a-compose-file).
- **Published ports and host binds** need their own permission. A port under 1024 cannot be
  published; use a domain.

## What is left behind

- **KeyDB and Dragonfly** databases, named in the report.
- **Coolify's own `COOLIFY_*` variables.**
- **Deploy keys and connected-source credentials.** Attach a [git connection](/guides/git-providers);
  that also turns on auto-deploy.
- **Registry passwords.** Add the registry under [Registries](/operations/servers/container-registries).
- **A volume's own backup to S3.** Coolify's API does not list it. One app backup here covers
  every volume.
- **A database backup kept only on Coolify's disk.** Set a destination under **Backups**.
- **Custom labels, docker run options, network aliases, pre- and post-deploy commands, www
  redirects, CPU pinning and swap limits.** Each is named in the report.

## Backing out

The general rules are in [Migrations](/migrations#stopping-data-and-going-back). For a takeover:

- **Before the ports move:** **Cancel and remove Deplo** starts what the migration stopped, starts
  Coolify again, removes what Deplo created and uninstalls Deplo. It asks for the token again.
- **After the ports move:** only the snapshot. If the move itself fails, Deplo puts the ports
  back, starts Coolify again and offers **Try again** with the reason.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| **Coolify's API is turned off on that instance** | Turn it on in Coolify's **Settings**. |
| **Coolify only accepts API calls from an allowed IP** | Add this Deplo's address to that list. |
| **This token cannot read values**, or **cannot read compose files** | Create a token with `root`, from an admin or owner. |
| **This token cannot stop a service** | The token has no `deploy`. Create one with `root`. |
| **That token does not carry the permissions this needs** | Add `read` and `read:sensitive`, or use `root`. |
| **Coolify refused the token** | It expired or was revoked. Create a new one under **Keys & Tokens**. |
| **Coolify kept rate limiting Deplo** | Coolify allows 200 requests a minute. Wait for other API users to quieten down. |
| **would not answer for the** team, project or environment **shared variables** | An older Coolify has no endpoint for that level. Copy those variables in by hand. |

Agents, volumes and the takeover: see [Migrations](/migrations#troubleshooting).
