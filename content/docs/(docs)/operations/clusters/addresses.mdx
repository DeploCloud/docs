An app on a [cluster](/operations/clusters) can end up on another server. Whether its address
follows it depends on where the domain lives.

| The app is reached at | After a failover |
| --- | --- |
| A domain in a Cloudflare zone connected for [automatic DNS](/guides/networking/automatic-dns) | **Same address.** Nothing to do: the cluster answers it, or the app's tunnel |
| A generated `deplo.site` address | Deplo gives the app a **new address** for the new server. **While Deplo is down, the moved app answers at none**, see [A generated address](#a-generated-address) |
| A domain of your own with **Answer on every server** on | **Same address.** Every server answers it, see [Answer on every server](#answer-on-every-server) |
| A domain of your own that is not on Cloudflare | **Stops answering** until you point its DNS at the new server |

Deplo says so before you rely on it:

> This App's address changes when it fails over to another server. A domain on Cloudflare keeps
> one address.

The warning has a **Connect Cloudflare** link and shows:

- **before placing**: in the **Move** dialog and on the new app page under **Deploy to**, once a
  cluster is picked
- **after**: at the top of the app's **Overview** and of its **Domains** page

It goes away once one of the app's domains is in a connected Cloudflare zone.

**Each domain that does not follow says so on its own row** in **Domains**, even when another domain
of the app is on Cloudflare:

> Answers only through **server-a**: if it stops, this domain stops answering until it is back,
> even when the App moves.

The row has an **Answer on every server** button next to it.

## Keep one address with Cloudflare

**Nothing to set up beyond connecting the domain to Cloudflare**, the way
[automatic DNS](/guides/networking/automatic-dns#connect-a-domain) already asks. **Add Domain** then
offers two choices:

| Choice | Who answers | Needs |
| --- | --- | --- |
| **Let the cluster answer** (default) | Every server of the cluster, its app's server first | Port 53 open on the servers. The first domain needs an instance admin, who makes the cluster's zone |
| **Cloudflare Tunnel** | Cloudflare, through the app's own tunnel | The tunnel permission on the API token |

**Let the cluster answer** is [The cluster's own DNS](/operations/clusters/dns-zone#a-domain-connected-to-deplo),
made and kept in Cloudflare by Deplo: two records, DNS only, and
[Answer on every server](#answer-on-every-server) on. If the cluster cannot answer yet, the domain
goes on the tunnel and its row says why. **Let the cluster answer** on the row moves it once fixed.

What Deplo does for each app on a cluster with a tunnel domain:

1. **The app gets its own Cloudflare Tunnel.**
2. **The tunnel's connector runs beside the app**, wherever the app runs, and starts only once
   the app is ready.
3. **The DNS record becomes a proxied CNAME to the tunnel**, and does not change again.

Cloudflare hands each hostname to the server's own proxy, so
[basic auth, headers, path routing and redirects](/guides/networking/domains-and-https) work as
before.

**No certificate to manage.** The domain editor hides the HTTPS fields and says: "Cloudflare
serves this domain through a tunnel, HTTPS included: it needs no certificate of its own."

## Answer on every server

**Keeps a domain answering through a failover without Cloudflare.** Every server of the cluster
answers the domain and passes each visitor, still encrypted, over the cluster's
[private network](/operations/clusters/private-network) to the server that runs the app.

Turn it on from the domain's row in **Domains**: **Answer on every server**. The row then says:

> Answers on every server of the cluster, and keeps answering when the App moves.

**Turn off** on the same row puts it back on the app's own server.

- **A visitor never sees a page not found** for an app that exists. A connection still open when the
  app moves is closed once it runs on another server, and the browser opens a new one, to the app.
- **A new domain answers within seconds** of the app being ready. A resolver that asked for it before
  keeps "no such name" for 5 seconds at most.

### What it needs

- **The app is on a cluster**, and the domain uses **HTTPS**. Over plain HTTP the app would lose
  every visitor's address, so the switch says so and stays off.
- **A whole hostname.** A hostname that another route serves a path of (`shop.example.com` on `/`
  and on `/api`) cannot be split this way, and a path cannot be added to one that has it on.
- **Not the app's Cloudflare tunnel.** A domain on the tunnel already follows the app.
- **Not a generated `deplo.site` address**, which names one server by design.
- **At most 200 apps per cluster.** Past that the switch says: "This cluster already has 200 Apps
  that answer on every server, the most its servers carry. Turn it off on one of them first."
- **No HTTP/3 on a server's proxy.** Deplo's proxy has none; a proxy edited by hand to offer it
  stops the switch, naming the server.

### The DNS records

DNS must name **every healthy server**, one `A` record (and `AAAA` for IPv6) each.

<Tabs items={['Domain connected to Deplo', 'The cluster answers', 'Any other DNS']}>
<Tab value="Domain connected to Deplo">
Nothing to do. Deplo makes the cluster's own DNS zone and points the domain at it, so the servers
answer it themselves, naming only the healthy ones:
[A domain connected to Deplo](/operations/clusters/dns-zone#a-domain-connected-to-deplo).
</Tab>
<Tab value="The cluster answers">
Delegate a zone to the cluster once, and its servers answer the domain's DNS themselves, naming only
the healthy ones: [The cluster's own DNS](/operations/clusters/dns-zone).
</Tab>
<Tab value="Any other DNS">
Add one record per server where your DNS is managed. The domain's row lists them, each with a copy
button, for example:

```
shop.example.com.  60  IN  A  203.0.113.10
shop.example.com.  60  IN  A  203.0.113.11
shop.example.com.  60  IN  A  203.0.113.12
```

The domain's check verifies every one is there, and the row says which to add or remove when the
cluster changes. **A server that stops stays in your records** until you remove it: a browser
that tries it first moves on to the next address after a few seconds, on each visit.
</Tab>
</Tabs>

### The certificate travels with the app

The certificate is issued on the server that runs the app, the usual way. Deplo then copies it,
key included, into what the cluster keeps to restart the app elsewhere, encrypted.

- **After a failover the new server answers with the same certificate at once.** No new
  certificate is ordered, so moving back and forth never runs into Let's Encrypt's limit of 5
  identical certificates a week.
- **The new server renews it itself** when its time comes. To take it over, that server's proxy
  restarts once, at its quietest hour before the renewal is due (04:00 server time until it has a
  week of traffic to go by). Open connections to that server reconnect, and Activity says:

  `Deplo restarted the proxy on server-b 2026-12-20 at 04:00 UTC, its quietest hour before the
  renewal window, so it renews the certificate of shop.example.com itself. Visitors' open
  connections to that server reconnected.`

- **The server the app left orders nothing when it comes back**, after a power cut or weeks away.
  Before its proxy starts, the app's certificate is set aside: it is still served, never renewed,
  and goes away once the cluster says the app runs elsewhere.
- **Until the certificate is copied, failover is not ready**, and the row says: "Failover is not
  ready yet: Deplo copies its certificate once the App's server has one."
- **Turning the switch off** removes the key from what the cluster keeps.

### What it costs

- **One server per app, unless every server holds the certificate.** Every server answers the
  domain. With a certificate checked over HTTP, every visitor reaches the one server that runs the
  app, and its replicas stay there. Checked through the cluster's
  [DNS zone](/operations/clusters/dns-zone#certificates), every server holds it, and
  [load balancing](/operations/clusters/load-balancing#without-cloudflare) runs the app on all of
  them, with no Cloudflare.
- **Visitors per server, set in the cluster's settings** under **Visitors per server** (shown once
  a domain of the cluster answers on every server):

  | Limit | Default | What happens past it |
  | --- | --- | --- |
  | Connections at once, all such domains together | 2,048 | The visitor is turned away at once |
  | Of those, waiting during a failover | a quarter (512) | The visitor is turned away at once |
  | Waiting for one app | 128 | The visitor is turned away at once |

  **Open keep-alive and WebSocket connections count** for as long as they are open. Each costs a
  server up to 64 KB of memory, so no more than a quarter of the smallest server's memory is
  accepted. **Activity says when a limit was reached**, within about two minutes.
- **During a failover a visitor waits up to 30 s** for the app to answer on its new server, then the
  connection closes. Past the waiting limit, visitors are turned away instead. Give the app a
  [health check](/guides/observability/health-checks): without one it counts as ready 3 s after it starts,
  and the row suggests adding one.
- **An update of a server agent closes the connections open through it**, on that server. New
  connections barely notice.

## When an app joins a cluster

Placing an app on a cluster gives its Cloudflare domains the same answer as **Add domain**: the
cluster's own DNS answers each one when its zone is delegated and you may use it, and the rest move to
the tunnel, with the reason on the row. Nothing makes a zone for it. **The hostname stays the same.**

- **Nothing is offline in between.** DNS switches only once the connector has connected.
- **Deplo retries on its own** every 10 minutes.
- **A domain added later** to an app that is already on a cluster is answered by the cluster by
  default, or by the tunnel if you pick it, see [Keep one address with Cloudflare](#keep-one-address-with-cloudflare).
- **A domain on the tunnel** moves to the cluster with **Let the cluster answer** on its row.
- **An app whose server joined a cluster** is switched right away, with no redeploy.
- **Domains of apps already on the cluster** stay where they are.
- **A change of domain re-applies routes only.** Adding, removing or editing a domain recreates only the
  container whose route changed, never its database or any other service.

## When an app leaves a cluster

Moving the app to a server outside the cluster:

- points each domain back at that server: an address record, or the server's tunnel if the domain
  used one before. A domain the cluster answered gets an address record too
- deletes the app's tunnel

Deleting the app deletes the tunnel and the records Deplo made. Deleting the cluster does the
same as leaving it. After leaving, the domain's certificate choice goes back to the default for
its DNS.

## Limits

- **One tunnel per app lives in one Cloudflare account.** A domain in a zone of another
  Cloudflare account keeps an address that changes.
- **A hostname shared with another app** (one app on `/`, another on `/api`) is not switched.
- **A record Deplo did not make is never replaced.** If the hostname already has a record that
  does not point at one of your servers, delete it in Cloudflare or pick another name.
- **A pull request preview** is not served through the app's tunnel.
- **Off Cloudflare, a domain follows the app only with [Answer on every server](#answer-on-every-server).**
  Deplo does not rewrite records at another DNS provider when an app moves; to have no records to
  keep at all, let [the cluster answer its DNS](/operations/clusters/dns-zone).

## A generated address

A `deplo.site` address names the server the app runs on. After a failover Deplo makes a new one
as soon as it sees the app running on the new server, and Activity says:

`web moved to another server of its cluster, so its generated address is now
web-calm-fox-cb007118.deplo.site`

If the new server refuses the new routes, Activity says `web runs on server-b, but its generated
address could not be updated yet`, followed by the reason, and Deplo tries again on its own.

**A generated address follows a moved app only while Deplo is up.** Only Deplo makes the new one,
and the old one names the server the app left.

- **With Deplo down**, the app runs on its new server but is not reached at any generated address.
- Measured: it ran there about 9 seconds after its server stopped, and was served at the new
  address **12 to 29 seconds after Deplo was back**.
- **A domain on Cloudflare keeps answering** the whole time. That is the address to give visitors.

## What Activity says

| Entry | Meaning |
| --- | --- |
| `Gave web its own Cloudflare Tunnel. Its domains switch to it once it is running on the cluster` | The app joined. It adds `; 1 in another Cloudflare account keep an address that changes` when that applies |
| `Switched app.example.com to web's Cloudflare Tunnel: the address stays the same wherever it runs` | Done |
| `Could not switch these to web's Cloudflare Tunnel, so they stop answering when it fails over: app.example.com (This App's Cloudflare Tunnel is in another Cloudflare account, so this domain cannot use it)` | Each domain with its reason, said once per reason. Fix the reason; Deplo retries |
| `Pointed app.example.com back at web's server` | The app left the cluster |
| `Could not point these back at web's server, so they still use its Cloudflare Tunnel` | Leaving did not finish for the domains it lists, each with its reason |
| `Could not set up this App's Cloudflare Tunnel, so its domains keep their address` | The tunnel could not be made, for the reason it gives. The move still went through |

## Good to know

- **The tunnel's token is a secret.** It is never shown, it is masked wherever Deplo displays the
  app's stack, and it is deleted with the tunnel.
- **A server whose server agent is too old refuses the deploy**: "the server agent on this server
  is too old to start the App's tunnel once it is ready - Deplo updates it on its own".
- **How fast Cloudflare stops sending visitors to a server that lost power is Cloudflare's to
  decide.** Deplo has not measured it and promises no figure.
