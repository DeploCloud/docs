Every [cluster](/operations/clusters) has a **leader**: it decides which server runs what, and it
is what moves apps off a server that stopped. You never install or update it by hand.

- **It runs on one of the cluster's own servers.** Deplo picks the server that reaches every other
  one directly and has the most free memory, within a minute of the servers reporting their paths.
  A cluster that was led from Deplo's own machine moves its leader there on its own, and a leader
  whose server comes to reach the others only through Deplo's relay moves to one that does not.
- **Two servers stand next in line**, each with a leader of its own ready to take over. See
  [The line of succession](#the-line-of-succession).
- **Deplo's own machine stands in last**, only when no server of the line can.
- **Failover works while Deplo is down** when the cluster has **three servers or more**, more than
  half of them up.
- **The leader keeps leading only while enough servers answer it**: more than half of the
  cluster's servers, or exactly half of them and Deplo itself. Otherwise it moves nothing. See
  [When a cluster is cut in two](/operations/clusters/failover#when-a-cluster-is-cut-in-two).

## Reading the banners [#reading-the-banners]

Open the cluster under **Settings -> Servers**. The server the leader runs on shows a crown; the
servers next in line show a grey one, whose tip says **Next in line** or **Second in line**. Their
pages carry the same words. When the leader runs on Deplo's own machine, no server shows it.

**No banner means the leader runs and enough servers answer it.** Otherwise the banner
**Failover is not working right now** says why:

| It says | What to do |
| --- | --- |
| "Only 1 of 3 servers answers this leader, so nothing moves. Failover works again once 2 do." | Bring the servers back. See [When a cluster is cut in two](/operations/clusters/failover#when-a-cluster-is-cut-in-two) |
| "The leader is installed but not running." or "The leader is not installed yet." | **Try again** starts it |
| "Deplo could not reach the server the leader runs on." | **Try again**, or bring that server back |
| "Deplo's own machine is not connected as a server yet, so there is nowhere to start the leader." | Connect Deplo's own machine as a server |
| "This leader is older than this Deplo accepts. Deplo updates it on its own." | Nothing: wait |

Deplo checks every 30 seconds, and at once after you move or start the leader.

## The line of succession [#the-line-of-succession]

Every order the leader sends names who leads after it: **the heir first, then the next server,
Deplo's own machine last.** Every server of the cluster always knows it.

- **Only servers that reach every other one directly** are in the line, at most two.
- **Each holds a leader of its own**, standing by, and the sealed copy of what a failover needs.
- **A server the leader stops hearing leaves the line** at the next order, a second or so later,
  and the next one moves up. Back, it rejoins at the end of the line, as an ordinary server.

### When the leader's server stops [#when-the-leaders-server-stops]

**The heir takes over on its own, with or without Deplo.**

<Steps>
<Step>

#### The servers stop hearing the leader

After 5 seconds each server stops its databases and apps with a Volume, as it does whenever its
leader is silent.

</Step>
<Step>

#### The heir asks

10 seconds after the leader's last order, the heir asks the others whether they would follow it.
The next server in line asks 5 seconds later, only if the heir did not.

</Step>
<Step>

#### More than half say yes

The heir leads, about 12 seconds after the leader's server stopped. The servers start what they
stopped again, and the leader's own server's apps move on the usual clock: their apps with data
about 30 seconds after the stop, then their own start.

</Step>
</Steps>

**A server says no while it still hears the leader.** So:

- **A cut between the leader and the heir only** changes nothing: the others still hear the leader,
  and the next order names another heir.
- **The heir cut off alone** takes nothing over. Its own databases and apps with a Volume stop and
  move, as for any server cut off.
- **A planned leader restart** (an update) is not taken over: the servers' time is extended first.
- **The rule for leading is unchanged**: more than half of the servers, or exactly half and Deplo.
- **Exactly half left** (the leader's server and the heir's both stopped): the next server in line
  asks, and **Deplo gives it its word**, so it leads with half, about 20 seconds after the stop.
  Deplo's own machine does not stand in.
  Activity: `eu-1 stopped answering, so Deplo gives its word to eu-3, next in line, to lead cluster eu`.

Measured on a cluster of three (Deplo 0.8.2-canary.80, server agent 0.5.3-canary.43, leader
0.1.0-canary.18), with a power cut:

| Case | The next leader leads | Every app served again |
| --- | --- | --- |
| The leader's server stops | After 13 seconds | After 44 seconds at most |
| Then the heir's server stops too, half left | After 20 seconds, on Deplo's word | After 55 seconds at most |
| The leader's server stops while Deplo is cut off | After 12 seconds | After about 41 seconds |
| The leader's server stops right after **OK for production again** | After 10 seconds | After 40 seconds |

Activity, by Deplo, once it hears of it, usually within 15 seconds of the leader's server stopping:
`eu-1 stopped answering its servers, so eu-2, next in line, leads cluster eu`. The line carries the
time eu-2 took over, also when Deplo was cut off and reads it later, and so does every event eu-2
recorded meanwhile.

A cluster with a server whose agent is too old for this has no line until Deplo has updated it:
Deplo's own machine stands in, as before.

## Move the leader to another server [#run-the-leader-on-another-server]

**Why**: to pick the server yourself. **Failover without Deplo takes three servers or more.** The
picker offers the cluster's own servers only. The confirmation says which case you are in:

| Cluster | It says |
| --- | --- |
| Three servers or more | "Failover keeps working while Deplo's own machine is down." |
| One or two servers | "Under three servers, failover still needs Deplo up wherever the leader runs." |

Even with three servers, a leader on another server keeps failover working only as long as it
still reaches **more than half of the cluster's servers**.

<Steps>
<Step>

### Open the cluster

**Settings -> Servers**, then open the cluster.

</Step>
<Step>

### Make leader

In the menu of the server that should run it, **Make leader**. The confirmation reads **Run the
leader on server-b?**

- An offline server cannot be picked: "server-b is offline. Bring it back online first."
- A server with no proxy carries a note: "server-b has no proxy, so a leader there still needs
  Deplo's machine up to move anything."
- A server that cannot run a leader yet is refused: "The server agent on this server is too old
  to run a cluster leader. Deplo updates it on its own: try again in a few minutes."

</Step>
<Step>

### Confirm

There is no command to run: that server installs the leader on its own. Toast: "The leader now
runs on server-b". Activity: `Moved the leader of cluster eu to server-b`.

</Step>
</Steps>

Instance admins only. Deplo's own machine is offered only when it is a server of the cluster.

### Pick a server that answers on port 443

The leader reaches the other servers over the cluster's
[private network](/operations/clusters/private-network), directly wherever two servers can reach
each other, so it keeps leading without Deplo's machine.

A server that runs Deplo's proxy (it answers on 443) also runs a second **cluster relay** beside
the leader, for the pairs of servers that cannot reach each other directly. Every server connects
to it too.

A server with no proxy runs the leader alone. **A pair that can only meet through a relay then
still needs Deplo's machine**, and the confirmation says so before you pick it.

### When Cloudflare refuses Deplo's token [#when-cloudflare-refuses-deplos-token]

When the panel is served through [Cloudflare Tunnel](/operations/cloudflare-tunnel), servers
reach the relay on Deplo's machine through that tunnel. Deplo adds the route to it, which takes
the panel's Cloudflare API token.

If Cloudflare refuses that token, the banner **Failover may stop working** says: "Cloudflare
refused Deplo's change, so servers cannot reach the relay on Deplo's machine and failover stops
when the leader's server does. Give Deplo a working Cloudflare API token:", then Cloudflare's
reason. With a backup address on, servers still reach the relay through it, and the banner says
so.

To fix it, **Fix in Cloudflare** beside the banner:

<Steps>
<Step>

### Create the token

**Create the token in Cloudflare** opens Cloudflare's form with the three permissions filled
in, and a dated name like `Deplo panel 2026-11-14`. **Continue to summary**, **Create Token**,
then copy it.

</Step>
<Step>

### Paste it and save

Paste it under **New token**, then **Save**. Deplo keeps it only if Cloudflare accepts it for the
tunnel, its DNS zone and the relay route. Otherwise it says why and keeps the old token.

</Step>
<Step>

### Delete the old token

Deplo now uses the new token, the route is back and the banner goes away. **Open Cloudflare
tokens** lists your tokens: delete the **Deplo panel** token that is not the new one. Deplo does
not delete it for you.

</Step>
</Steps>

Activity: `Gave the panel's Cloudflare Tunnel a new API token`. Instance admins only.

### When no server of the line can lead [#when-the-leaders-server-stops-answering]

Deplo's own machine leads in its place, on its own, **25 to 40 seconds** after the leader's
server stopped answering Deplo, and only once the servers no longer hear it either. **It stands in
only when no server of the line answers Deplo**: a server of the line that answers either asks to
lead, and gets Deplo's word, or is still led by the leader.

- The banner **Deplo's own machine leads this cluster** says: "Until server-b answers again."
- Activity: `server-b stopped answering Deplo, so Deplo's machine leads cluster eu once its servers
  stop hearing server-b too, until it answers again`, then `server-b answers again, so it leads
  cluster eu again`.
- **Servers it does not hear** are said as it sees them: `Deplo's machine, standing in as the leader
  of cluster eu, hears server-c: server-a is off, or cut off from it.` It cannot tell the two apart.
- **What server-b did meanwhile is said too**, at the time it did it: a cut between it and Deplo
  does not stop it leading the others. See
  [If Deplo was down](/operations/clusters/failover#if-deplo-was-down).
- **Nothing runs twice during a change of hands**, and a change of hands never causes a failover
  by itself: a leader that takes over moves nothing of a server that answers it.
- For a server it has **not heard from at all**, it starts that server's databases and apps with a
  Volume elsewhere about 17 seconds after it started leading (24 with a server agent older than 0.5.3-canary.43), once the servers that are left say
  no extra time it was given can still be running. In two cases it waits about 6 minutes 21
  seconds instead. See
  [The slower case](/operations/clusters/failover#the-slower-case).

- **Anything that was waiting for room is not started a second time.** The new leader first hears
  from every server, and leaves each app with the server that still has it.

<Callout type="warn">
  **The limits.** With the leader's server offline **and** Deplo's machine down at the same time,
  nothing fails over. Apps keep running where they are. A server that stops in that window is not
  replaced until either one is back. The same holds for a leader that reaches too few servers:
  with half of them or fewer answering it and Deplo out of reach, it moves nothing.
</Callout>

## When Deplo's own server is in the cluster [#when-deplos-own-server-is-in-the-cluster]

Deplo's own server can be a member of a cluster like any server: drag it onto the cluster,
its apps and databases come along, and it can be removed. This is how a first cluster
starts with one rented server.

**Deplo itself, its database and its proxy are never part of the cluster.** Nothing places,
moves, stops or empties them.

While Deplo's own server is a member **and** the leader runs on it, the banner **Failover may
stop working** says:

> If Deplo's own server stops, its Apps cannot move. Run the leader on another server to fix this.

The leader is what moves apps off a server that stopped, and here it stops with that server.
**Make leader** on any other server of the cluster makes the warning go away.

On a cluster of **one or two servers** the warning reads differently, because moving the leader
alone does not fix it:

> If Deplo's own server stops, its Apps cannot move. Fixing this takes three servers, with the
> leader on another one.

Removing Deplo's own server leaves the leader and the relay running there.

## Updates [#updates]

**Nobody updates a leader or a relay by hand.** After a Deplo update, Deplo brings each one to the
version it ships with, on its own: one server at a time, a leader on another server first, Deplo's
own machine last. It only ever moves forward.

- **A leader update costs no failover.** Before it restarts, the leader gives every server of its
  clusters five more minutes, so nothing stops and nothing moves while it is away. Five minutes is
  the most a server ever accepts.
- **A server whose server agent is still being updated** gets that update first, then the leader's.
- **The server agent of the leader's own server** updates after the other servers of its line. First
  the leader moves to the next server in line, so no server waits for it while that agent restarts.
  Activity, by Deplo: `The leader of cluster eu now runs on server-c, next in line, while server-b
  updates its server agent`.
- Activity, by Deplo: `Updated the cluster leader and relay on server-b to v0.3.0`.

### When an update fails

Deplo tries again on its own, waiting 1, 2, 4 and up to 60 minutes between tries. Until it works,
the banner **Failover may stop working** shows "Deplo could not update the leader on server-b to
v0.3.0:", then the reason, then "It retries on its own."

Two reasons you can meet:

- "A server of cluster eu is not answering, and a leader is not restarted while its Apps may be
  moving." Deplo waits until that server answers, or 45 minutes have passed.
- "It took the new version but did not start on it. The other servers wait until it does." No
  other leader is updated until this one runs again.

### A leader too old for this Deplo

The banner **Failover is not working right now** says: "This leader is older than this Deplo
accepts. Deplo updates it on its own." When that leader runs on another server, Deplo's own
machine leads the cluster meanwhile, and the banner **Deplo's own machine leads this cluster**
says: "Until server-b is updated."

There is no update button, and none is needed. **Try again** is only offered for a leader that is
not running.

## Good to know

- **A server that runs a cluster's leader cannot be removed from Deplo**: "Move the leader of
  cluster eu to another server first."
- **After [moving Deplo](/operations/move-deplo) to another machine**, the new machine starts its
  own leader, and a leader on another server keeps leading.
- **What each leader needs to restart an app** (its last deployed version and variables) is kept
  sealed for the leader, the servers next in line and Deplo's machine, each with its own key.
  Moving the leader hands it over to the new one.
- **Deleting the last cluster** removes the leader and the relay from Deplo's own machine.
- **A leader left on a server that was offline** when its cluster was deleted, or when the leader
  moved away, is removed as soon as that server answers.
- **A server of a cluster takes orders only from the leaders Deplo named for that cluster**: the
  leader, the servers next in line and Deplo's machine, and from one of them at a time.
- **Over the API**: `moveClusterLeader(id, serverId)`, `Cluster.leader`, `Cluster.leaderChoices`
  and `ClusterMember.nextInLine`, instance admin only. Over MCP, `get_cluster` says each server's
  place in the line.
