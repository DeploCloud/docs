## A server is stuck provisioning

`provisioning` means the agent has never called home. On the machine, run:

```bash
systemctl status deplo-agent
journalctl -u deplo-agent -f
```

| What you see | Cause |
| --- | --- |
| The unit does not exist | The install command never ran, or failed early |
| `Refusing to run an unverified binary` | The download did not match its checksum. Retry; if it persists, something is intercepting it |
| The unit runs but nothing happens | It cannot reach the panel. Check that the machine is connected to the internet, and the address in the command |
| `bootstrap token` errors | The token was used already, or it expired. Issue a new one from the server's menu |
| `status=216/GROUP` | The unit wants the docker group and Docker is not installed. That is expected on a backups-only host, and its unit is installed without it |

## A server is offline

`offline` means the server has not been connected to Deplo for about 10
seconds. Deplo never calls a server, so there is no port to open: the server
connects to Deplo by itself, and is back online within seconds of reaching
the internet again.

Its card says what brings it back:

| Its card says | What to do |
| --- | --- |
| `Check that the machine is on and connected to the internet.` | Start the machine or reconnect it. If it is on and online, check the server agent on it: `systemctl status deplo-agent`, then `journalctl -u deplo-agent -f` for why it can't reach Deplo |
| `This server can't reach Deplo at deplo.example.com. Check that it's connected to the internet.` | It has never connected since it was added. See [A server hasn't connected to Deplo yet](#a-server-hasnt-connected-to-deplo-yet) |
| `This server can't be used until its server agent is reinstalled. An instance admin can do it from the server's Advanced tab.` | See [A server agent needs to be reinstalled](#a-server-agent-needs-to-be-reinstalled) |

If the panel's address changed while it was off, see [below](#a-server-was-off-while-the-panels-address-changed).

## A server was off while the panel's address changed

A connected server learns a new panel address at once. One that was off at
the time still knows the panel's backup address, the generated one like
`deplo-cb00710a.deplo.site`, and connects there.

It cannot find the panel when neither address it knows works any more: the
domain changed while the backup address was off, or the panel has no domain
of its own and its generated address changed. Then [reinstall its server agent](#a-server-agent-needs-to-be-reinstalled)
with a fresh install command. A panel domain, with the backup address left
on, avoids this.

## A server hasn't connected to Deplo yet

The server was added and its server agent enrolled, but it has never connected to Deplo since.
Deplo never calls a server, so nothing reaches it: it is **unusable** until it connects. Its
apps keep running.

- Its card shows **Offline**:
  `This server can't reach Deplo at deplo.example.com. Check that it's connected to the internet.`
- On its page, the server agent line says `Unusable - it hasn't connected to Deplo yet`.
- Instance admins see a banner: `edge-2 hasn't connected to Deplo yet.`

It connects by itself as soon as it can reach Deplo. Nothing has to be reinstalled:

| What you see | What to do |
| --- | --- |
| The machine is off, or has no internet | Start it or reconnect it |
| It is online, but its network only lets some sites through | Let it reach `https://deplo.example.com`, like a browser would. A company proxy or an outbound firewall rule is the usual cause |
| Still offline | Check the server agent on it: `systemctl status deplo-agent`, then `journalctl -u deplo-agent -f` for why it can't reach Deplo |

A server you no longer use can be [removed](/operations/remove-a-server-or-uninstall) instead.

While Deplo is on v0.6.0, the Updates tab also lists these servers, and the next update waits
for them: see [Updating through v0.6.0](/operations/update#updating-through-v060).

## A server was left behind

An instance admin left this server behind while Deplo updated through v0.6.0, so the update
could go ahead without it.

- **Before the update past v0.6.0,** nothing changes for it. If it connects by itself, it
  drops off the list and works normally.
- **After that update,** it is **unusable** until it connects. Its apps keep running, and its
  apps and settings stay in Deplo.

Its line on its page says which case it is:

- `Unusable - reinstall its server agent`: only a reinstall brings it back. See
  [A server agent needs to be reinstalled](#a-server-agent-needs-to-be-reinstalled).
- `Unusable - it hasn't connected to Deplo yet`: its server agent can still connect by itself.
  See [A server hasn't connected to Deplo yet](#a-server-hasnt-connected-to-deplo-yet).

Reinstalling its server agent brings it back either way, as it was, with its apps. A server you
no longer need can be [removed](/operations/remove-a-server-or-uninstall) instead.

## A server says warning, error, offline, or Unknown

| Value | Means | Where to look |
| --- | --- | --- |
| `warning` | The agent is up and trusted, Docker is not answering | `systemctl status docker` on the host |
| `error` | Something answered, but its agent is wrong: untrusted certificate, unsupported contract, or an application error | Re-run the install command to re-enroll |
| `offline` | Not connected to Deplo for about 10 seconds | [A server is offline](#a-server-is-offline) |
| `Unknown` | The stored reading is stale | Click **Refresh** |

<Callout type="info">
Health is a stored reading. A deploy performs a live handshake, so a green
card and a failing deploy can still happen together.
</Callout>

## Check readiness instead of guessing

Use **Check readiness** in the server's menu for one live check of the agent,
Docker, routing, capacity, build methods, and Deplo configuration.

`fail` blocks a deploy. `warn` means it can deploy but is not fully usable.
`skip` means the check could not be evaluated, not that it passed.

## Metrics show dashes

The telemetry stream is not connected. Refresh the server health first.
History is held in memory and starts empty after a panel restart.

## A deploy says Docker cannot create a network

Deplo uses one Docker network per **Environment**. If the installer could not
restart Docker because containers were running, the configured address pool is
not active yet. Restart Docker in a maintenance window; the file is already
correct.

## A deploy fails with No chain DOCKER-FORWARD

Docker's forwarding chains were removed underneath it. Restart Docker to
recreate them.

## A removed container still appears

Deplo retries an unconfirmed teardown and raises an alert if it gives up.
Removing the server drops its pending teardowns.

## The install command returns 503 or cannot resolve a release

The panel cannot reach `github.com` to resolve or checksum the agent release.
Restore outbound access from the panel's machine, then run the command again.

## The install command contains 127.0.0.1

That address is for the machine running the panel. Paste it there only;
another server needs the panel's public address.

## A server agent needs to be reinstalled

The server is **unusable**, and nothing Deplo does can bring it back:

- Its card shows **Offline**:
  `This server can't be used until its server agent is reinstalled. An instance admin can do it from the server's Advanced tab.`
- On its page, the server agent line says `Unusable - reinstall its server agent`, with no
  **Retry now**.
- Instance admins see a banner: `edge-2 is unusable until its server agent is reinstalled.`

Either its server agent is older than `0.5.1-canary.10`, too old to connect to Deplo, or it was
[left behind](#a-server-was-left-behind) while Deplo updated through v0.6.0. Its apps keep
running, and its apps and settings stay in Deplo.

An instance admin reinstalls it:

1. Open the server under **Settings -> Servers**, then **Advanced -> Install command**.
2. Click **Reissue install command**, and run the command it shows on the server.

The server agent connects to Deplo by itself and the server comes back as it was, with its
apps. Always reissue first: the installer clears the old certificates, so a spent or expired
token leaves the server agent with `unknown-token`.

## A server is permanently gone

Remove it in Deplo. This revokes trust and does not require the machine to
answer. See
[Remove or uninstall](/operations/remove-a-server-or-uninstall).
