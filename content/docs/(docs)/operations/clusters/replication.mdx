title: Replication
description: Stream every change of a cluster's apps and databases to its other servers as it happens, so an app with a Volume fails over too, with almost nothing lost.

<Callout type="info" title="Beta">
This feature is currently beta/experimental and subject to change. It is
not recommended for production. Try it out and share your feedback on
[our GitHub](https://github.com/DeploCloud/deplo/issues).
</Callout>

<Callout type="info" title="Experiment">
An instance admin turns them on for every team in [Settings -> Deplo -> Experiments](/operations/experiments).
Until then, clusters stay hidden.
</Callout>

**Replication** keeps a copy of everything a [cluster](/operations/clusters) stores on its other
servers, **as it changes**:

| What | How it follows |
| --- | --- |
| An app's **Volumes** and **Files** | Every file that changes is sent to the other servers within about half a second |
| A **database** | Its engine's own log streams to a [standby copy](/operations/clusters/standby-copy) on another server |

- **It is the only way an app with stored data fails over.** Without it, such an app
  [waits for its server](/operations/clusters/apps-with-stored-data).
- **Off by default.** An instance admin turns it on per cluster, like [failover](/operations/clusters#turn-failover-off).
- **It is asynchronous**: a failover loses what had not reached the copy yet, usually under a second.

## Turn it on [#turn-it-on]

- **Inside the cluster**, the **Replication** switch beside **Failover**.
- **On the Servers page**, the cluster's menu, **Turn replication on**.

The toast says `Replication on for eu`, and Activity records `Turned replication on for cluster
eu`. Instance admins only.

Each app's data is copied whole once, then every change follows. When the first whole copy is on
another server, Activity, by Deplo:

```
Replicated web's data to server-b and server-c: it can fail over now
```

## How an app's data follows

<Steps>
<Step>

### The server the app runs on watches its data

Every file written, renamed or removed in its Volumes and Files is noticed at once. Nothing is
paused.

</Step>
<Step>

### Each other server keeps a copy

The change goes straight from server to server over the cluster's
[private network](/operations/clusters/private-network), so it keeps following **while Deplo
itself is down**. The copy is kept apart: it is never the app's live data.

</Step>
<Step>

### A failover puts the copy in place

The server that takes the app over stops following, puts its copy where the app keeps its data,
and starts it. A server that never held a whole copy refuses, and the cluster picks the next.

</Step>
</Steps>

A server that comes back after a failover holds its old copy of the app as its own data: what it
still held is [saved as a backup](/operations/clusters/failover#data-left-on-the-server), and only
then does it follow again, from the server the app runs on now.

## What is replicated

| The app keeps | Replicated |
| --- | --- |
| A **Volume** | Yes |
| A **File** written in Storage | Yes |
| A Compose app's own volume | Yes |
| A **Bind** | Never: the folder lives on one machine. See [An app with a Bind](/operations/clusters/apps-with-stored-data#an-app-with-a-bind-never-fails-over) |
| A **database** | Through its standby copy, see below |

## Databases [#databases]

With replication on, **every database of the cluster keeps a standby copy**, made by Deplo:
Postgres streams its write-ahead log, MySQL and MariaDB their binary log, MongoDB runs as a replica
set and Redis follows its primary. A failover promotes the copy, losing about a second of writes.
See [Standby copy](/operations/clusters/standby-copy).

- Activity: `Keeps a standby copy of main on server-b: cluster eu replicates its databases`.
- The database's **Keep a standby copy** switch reads "Cluster eu replicates its databases, so it
  keeps this copy." and cannot be turned off while replication is on.
- A database whose engine or version cannot keep one still fails over from its
  [15-minute backup](/operations/clusters/databases#the-failover-backup).

## What the app's page says

**The first copy starts the moment the app first runs on the cluster.** Until a server holds an
up-to-date copy, the app cannot move there.

The **Failover** card on the app's **Overview**:

| Replication | The card says |
| --- | --- |
| On, a whole copy elsewhere | "web moves to another server on its own if its server stops, with its data replicated there as it changes." Then **Copies: 2 of 2 up to date** |
| On, first copy under way | "web fails over once a whole copy of its data is on another server. Deplo is making it now." |
| Off | "web waits for server-a if it stops: cluster eu does not copy its data. You can bring it back on another server from its latest backup." |

The copies line reads one of:

- **Copies: 2 of 2 up to date**
- **Copying to server-b and server-c**
- **Not copied yet: this App cannot move if server-a goes off**

Under **Advanced**, one row per server: its state (Up to date, Copying, Behind, Queued, Not copied), its
last copy, how far behind it is, its size on that server's disk, and how it travels: `sent server to
server`, or `sent through Deplo` when no direct path joins the two servers. Activity uses the same words:
`web: Copies: 2 of 2 up to date. It can move if server-a goes off.`

When it moves, Activity says: `Moved web to server-b with its data replicated there: server-a
stopped answering`.

## One copy at a time on each server

A server makes **one copy at a time**, sent or received, so the apps it runs keep answering. Every
copy that moves data counts: a first copy, one catching up on a lot the app wrote at once, and the
data an app that was empty at its first copy writes later. A copy and a
[backup](/guides/data/backups-and-restore) wait their turn while either of their two servers copies
something else. A move never waits: its app is offline until it lands, so it goes at once and the
others wait for it.

- A copy that waits reads **Queued**, with what it waits for:
  `Queued: server-b is busy with a copy of shop`.
- A backup that waits reads **Queued** on its run, with
  `Waits its turn: server-b is busy with a copy of shop`.

A copy a server already holds keeps following the app's small changes as they come. One that waits
its turn stays whole on that server and stops following until its turn comes, so a failover can
still use it. A copy that waits more than 30 minutes goes anyway.

## The banners

Inside the cluster, on the Servers page:

| Banner | It says |
| --- | --- |
| **Replication is not ready for 1 App yet** | "A whole copy of their data is not on another server yet: web. Until it is, they wait for their own server." |
| **Replication is behind for 1 App** | Why a server's copy does not follow, such as "web: This server's agent is too old to keep a copy. Deplo updates it on its own." |

A copy that heard nothing from the app's server for 30 seconds, as its server says, counts as
behind.

## Turn it off

The same switch, or **Turn replication off** in the cluster's menu. Then:

- every server removes its copies of the apps' data
- apps with stored data wait for their server again
- the standby copies replication made are removed; one a person turned on stays
- [load balancing](/operations/clusters/load-balancing) is turned off too: `Turned replication off
  for cluster eu, and load balancing with it`

## What it costs

- **Disk**: each server keeps a full copy of every other server's apps with data, and of each
  database it holds the standby copy of. A copy starts only if it leaves a tenth of the server's
  disk free, the dated copies already on it counted. Until there is room, the server shows a warning
  on its row and its page, for example
  `eu-1 has 1.2 GB free, too little for a copy of shop (about 2.8 GB) and a tenth of its disk free. Free some space on it, and the copy starts.`
  Activity says it once, in the app's team. A copy that grows past that room while it is made (the app
  writes more meanwhile) stops at a tenth free and shows the same warning. Once held back, it starts
  again only with a fifth more room than it takes, so it never starts and stops over and over.
  Free space is what a copy may write: the part of the disk the system keeps for itself does not count.
  A copy a server already holds whole is never held back.
- **A big file that changes counts twice.** A changed file is rebuilt beside the old one, which goes
  only once the new one is whole, so for a moment the copy holds both. A copy starts only if a tenth
  of the disk stays free with the app's biggest file held twice, and a rebuild starts only if the old
  and the new file fit; otherwise it waits with the same warning.
- **A backup that does not fit shows there too**: a server whose disk holds backups shows the warning
  for the latest backup of an app that was refused or stopped for room, for example
  `Backup of shop: eu-2 has 1.2 GB free, too little for this backup (about 2.0 GB) and a tenth of its disk free, so it did not start.`
- **Memory**: a standby copy of a database takes as much as the database.
- **CPU and disk of the server**: copies, backups, restores and moves run last. While an app on the
  server waits for the CPU or the disk, or a visitor's request crosses it, a copy steps aside, so the
  apps there keep answering; the copy takes longer instead.
- **Network**: every change travels to every other server, and only the part of a file that
  changed travels: a few bytes written into a 10 GB file send about a hundred kilobytes, not
  10 GB. A file the app copies sends almost nothing, since the copy already holds its bytes.

<Callout type="info">
  Replication is not the same as the **version copies** a cluster always makes: after each
  deploy, every server gets the app's latest version so it can start it. Replication copies what
  the app **stores**.
</Callout>

**Over the API**: `setClusterReplication`, `Cluster.replicationEnabled` and `Cluster.replication`,
and `App.failover.replicatedTo`. Over MCP: `set_cluster_replication` and `get_cluster`.
