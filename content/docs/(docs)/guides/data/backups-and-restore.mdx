Scheduled, encrypted copies of a database or an app, sent to an S3 bucket or to a folder on one of
your servers, with a restore that puts them back.

- A **destination** is where the copies go.
- A **schedule** says what to copy, where, how often and how many to keep.
- A **run** is one execution. It produces one **artifact**, listed as a restore point.

The server that holds the data runs the backup. It is compressed and encrypted with `age` before it
leaves that server, with one key pair per destination. Nothing in between can read it.

- **An app backup** holds its Volumes, its Files, and a snapshot of its compose file and variables.
- **A database backup** is a dump of that database alone.

## Add a destination

**Storage -> Destinations -> Add Destination**, then pick the type and a **Name**.

<Tabs items={['Server', 'S3 bucket']}>
<Tab value="Server">

A folder on any of your servers, including a [storage-only](/advanced/server-roles) one. Backups of
apps on other servers are copied there.

Inside a [cluster](/operations/clusters/failover#data-left-on-the-server), one kind of backup
reaches that server without passing through Deplo: what a server still held when it came back
after a failover. It is encrypted the same way before it leaves.

Leave **Advanced -> Folder** empty and Deplo manages it. A custom folder (instance admins only) is
an absolute path that already exists and is empty the first time.

</Tab>
<Tab value="S3 bucket">

| Field | What to enter |
| --- | --- |
| **Provider** | Amazon S3, Cloudflare R2, Backblaze B2, DigitalOcean Spaces, Wasabi, MinIO, or Other S3-compatible. Pre-fills the endpoint format |
| **Endpoint**, **Region**, **Bucket** | As your provider documents them. **Region** defaults to `auto` |
| **Access Key ID**, **Secret Access Key** | Encrypted, never returned |
| **Advanced -> Additional flags** (beta) | Provider workarounds such as `--s3-force-path-style=true`. Unknown flags are refused |
| **Advanced -> This bucket is on my own network** | Instance admins only. Allows a private endpoint such as `10.0.0.5` |

</Tab>
</Tabs>

**Test connection** in the destination's menu runs a real probe from an agent: a small write and a
delete on a bucket, a write and a free-space check on a folder. A read-only key fails. A failed
test is a normal result: **Connection log** in the same menu shows every step and the commands to
repeat it by hand.

## Read the destinations list

Opening **Storage -> Destinations** tests every destination. One that cannot be reached keeps its
last figures and turns red.

- **A folder on a server** shows a bar: your backups, everything else on that disk, and free
  space. It turns amber past 80% used.
- **A bucket** shows the total: `48.2 GB in 137 backups`.
- **The refresh icon** re-tests one destination. The toolbar has search, filters, and a switch
  between cards and a table.
- **Remove** deletes the destination's schedules and restore points. The backup files stay unless
  you tick **Also delete**, but the key that opens them goes: save it first.

## Save the recovery key

**Download recovery key** in the destination's menu. Deplo offers it right after you add one, and
the card keeps reminding you until somebody downloads it. It needs `manage_backup_destinations`
and `reveal_secrets`, and the download is recorded in **Activity**.

You need it when `DEPLO_SECRET` was rotated or lost, or when the control plane itself is gone.
With the file, any artifact from that destination decrypts anywhere:

```bash
age -d -i deplo-recovery-key.txt backup.tar.gz.age > backup.tar.gz
```

Artifacts are named `deplo/<team>/<app|database>/<id>/<when>-<run>.<ext>.age`. An app backup
unpacks to `volumes/`, `files/` and `snapshot/`.

**Keep** is a count, not a number of days. `Keep 7` (the default) keeps the seven most recent

## Restore

Every successful run is a restore point, listed under **Restore points** on the target's
**Backups** tab. Each row's menu has **Download**, **Restore** and **Delete**.

<Image
  src={`${basePath}/screenshots/backups-and-restore/03-app-backups.png`}
  alt="One app's Backups tab: schedules and restore points"
  width={1728}
  height={1080}
  className="w-full rounded-lg"
/>

**A restore replaces the current data** and cannot be undone. It asks you to type the target's
name, and checks the artifact's checksum first.

- **A database** is dropped and recreated from the dump.
- **An app** is stopped, its data cleared, the artifact unpacked, and the app started again. It
  shows `restoring` meanwhile.

**Back up -> Restore from file** (beta) restores a `.gz`, `.tgz` or `.age` file from your computer.
For an encrypted one, paste the destination's recovery key.

**A backup labelled "Left on server-a after the failover at 14:32"** is what a server of a
[cluster](/operations/clusters/failover#data-left-on-the-server) still held when it came back. No
schedule ever deletes it, and restoring it loses everything written since the failover.

**Download** decrypts the artifact on the way out. It needs `restore_backups`; an **app** archive
also needs `reveal_secrets`, because it contains the app's variables.

## Good to know

- **An app schedule does not include its databases.** Schedule the database separately.
- **A skipped hour on a DST change shows a warning.**
- **`delete_backups` is a separate capability**, because deleting runs can leave a target with no
  restore point.
- **Deleting a schedule does not delete its backups.** They stay under **Restore points** until you
  delete them.
- **Deleting the app or database deletes its backups too.** If a destination cannot be reached, the
  delete is refused.
- **A destination on the same server as the data is lost with that server.** Put at least one copy
  elsewhere.
- **On a cluster, backups belong to the app or database, not to a server**: the list is the same
  before and after a failover. See [Backups](/operations/clusters/logs-metrics-and-previews#backups).
- **A PostgreSQL database on a cluster takes base backups**, files ending in `.base.tar.gz`, for
  its **Failover backup** schedule. They restore from the Backups tab, not with `pg_restore`. See
  [Databases on a cluster](/operations/clusters/databases#postgresql-loses-about-a-minute).

## Troubleshooting

- **Test connection fails on a bucket** - usually the key is read-only, or the endpoint and region
  do not match the bucket. Read the **Connection log**.
- **Runs fail with no space** - the destination server's disk is full.
- **Restore refuses** - the checksum did not match, or the artifact is encrypted with a key this
  destination does not hold. Use **Restore from file** with the recovery key.

More in [Databases and backups](/troubleshooting/databases-and-backups).
