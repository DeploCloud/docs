title: Load balancing
description: Run each app on every server of a cluster and send each visitor to the nearest server, or to the one with the most room.

This feature is currently beta/experimental and subject to change. It is
not recommended for production. Try it out and share your feedback on
[our GitHub](https://github.com/DeploCloud/deplo/issues).
</Callout>

<Callout type="info" title="Experiment">
An instance admin turns them on for every team in [Settings -> Deplo -> Experiments](/operations/experiments).
Until then, clusters stay hidden.
</Callout>

**Load balancing** runs an app on every server of a [cluster](/operations/clusters) and shares its
visitors between them. You choose where each visitor goes:

| Mode | Every visitor goes to |
| --- | --- |
| **Nearest server** (the default) | The server closest to them |
| **Most available server** | The server with the most free memory and processor |

- **It needs [replication](/operations/clusters/replication) on.** Otherwise the switch is
  refused: "Turn on replication first: load balancing needs it."
- **Off by default.** An instance admin turns it on per cluster.

## Turn it on

<Steps>
<Step>

### Open the cluster

**Settings -> Servers**, then open the cluster.

</Step>
<Step>

### Switch on Load balancing

Beside **Failover** and **Replication**. The toast says `Load balancing on for eu`.

</Step>
<Step>

### Pick where visitors go

**Nearest server** or **Most available server**, in the list beside the switch. Change it any
time: `eu sends visitors to the most available server`.

</Step>
</Steps>

Activity records it: `Turned load balancing on for cluster eu: visitors go to the nearest server`.

## Which apps it reaches

An app is load balanced when **all** of these are true:

- visitors can reach every server: it has a **Cloudflare domain**, or a domain that
  [answers on every server](/operations/clusters/addresses#answer-on-every-server) and whose
  certificate every server holds (below)
- it keeps **no data on its server**: no Volume, no File, no published port
- it is **not a Compose app**

From its **next deploy**, such an app runs on every server of the cluster: at least one
[replica](/advanced/replicas) on each, more if its replica count is higher. **Settings ->
Advanced -> Replicas** says: "Load balancing runs it on 3 servers: visitors are shared between
them".

### Without Cloudflare

A domain that answers on every server needs no Cloudflare, once **every server holds its
certificate**. That is the case when its certificate is checked through the cluster's
[DNS zone](/operations/clusters/dns-zone#certificates):

| Domain | Every server holds its certificate |
| --- | --- |
| `shop.go.example.com`, inside the zone | Yes: the zone's certificate |
| `a.b.go.example.com`, two labels down | Yes: its own, renewed by one server |
| `shop.example.com` with its `_acme-challenge` record | Yes: its own, renewed by one server |
| `shop.example.com` without that record | No: checked over HTTP, on one server |

One name checked over HTTP keeps the app on one server, and **Settings -> Advanced -> Replicas**
says which one and how to lift it:

> It runs on one server: shop.example.com has its certificate on that server only. Add the
> _acme-challenge record its domain offers, and from its next deploy it runs on every server.

Each server serves its visitors from **its own copy** of the app. With
[nearest servers first](/operations/clusters/dns-zone#nearest-servers-first), a visitor lands on
the server closest to them and is served there.

<Callout type="info">
  **An app with stored data stays on one server.** Its data has one writer: two servers writing
  the same files would lose one's changes. Replication keeps that data ready on the other servers
  for a failover.
</Callout>

## Nearest server

Each server runs the app beside its own Cloudflare connector, and **Cloudflare sends each visitor
to the server closest to them**. When a server stops, its visitors go to the next closest at once:
the others were already answering.

Without Cloudflare, the cluster's [DNS zone](/operations/clusters/dns-zone#nearest-servers-first)
does the same: it names the servers nearest each visitor, and stops naming a server within about
10 seconds of it stopping.

## A server that comes back

When a server stops, its copy starts on another server, beside the one already running there, and
its visitors are served by the others meanwhile.

**Once the server is back and has stayed up for 2 minutes**, Deplo starts its copy there again:

- **only on that server**. No other copy restarts, so no visitor notices
- **visitors there are passed to the other servers until its copy is ready**, then served from it
- the extra copy the failover started stays where it is until the app's next deploy

A server that stops again within those 2 minutes gets nothing back, and its wait starts over the
next time it is back. Activity says it:
`eu-1 runs its own copy of web again: it has been back for 2 minutes`.

An app with stored data is not load balanced, so it stays where the failover put it.

## Most available server

It applies to apps on a Cloudflare domain. An app reached through domains that answer on every
server is shared out by the cluster's DNS answers instead.


The app still runs on every server, ready to take over, but **only one server takes its visitors**:
the one with the most room.

- Deplo looks at each server's free memory and processor **every 30 seconds**.
- It changes server only when another one has **clearly more room**, so visitors do not bounce
  between two that are about the same.
- The new server starts taking visitors **before** the old one stops, so none are dropped.
- If that server stops, another one takes the visitors within about 30 seconds.

## Turn it off

The same switch. With **Most available server**, every server takes visitors again at once. Apps
go back to their own replica count at their next deploy.

Turning [replication](/operations/clusters/replication#turn-it-on) off turns load balancing off
too.

**Over the API**: `setClusterLoadBalancing`, `Cluster.loadBalancingEnabled` and
`Cluster.loadBalancingMode`. Over MCP: `set_cluster_load_balancing`.
